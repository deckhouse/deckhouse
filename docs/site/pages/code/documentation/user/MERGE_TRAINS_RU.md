Цепочка слияния ставит запросы на слияние в очередь для целевой ветки и проверяет каждый из них вместе с изменениями, стоящими в очереди перед ним, прежде чем разрешить слияние. Для каждого запроса в очереди запускается пайплайн, который выполняется для объединения целевой ветки, изменений запросов, стоящих впереди, и собственных изменений запроса. Пока запросы на слияние сливаются через цепочку, в целевую ветку попадает только код, проверенный ровно в том состоянии, в котором он будет слит.

Цепочки слияния работают на основе сборочных линий для результатов слияний (merged results pipelines). Такая сборочная линия проверяет один запрос на слияние вместе с текущим состоянием целевой ветки, а цепочка слияния проверяет всю очередь. Поэтому два запроса, которые проходят проверки по отдельности, но конфликтуют при объединении, будут обнаружены до того, как любой из них попадёт в целевую ветку.

Цепочки слияния настраиваются отдельно для каждого проекта. В проекте существует по одной цепочке на каждую целевую ветку.

## Как работает цепочка слияния

Запросы на слияние в очереди упорядочены по времени добавления, самый старый из них находится в голове цепочки:

1. Запрос на слияние, для которого включено автослияние, встаёт в конец очереди.
1. Deckhouse Code создаёт для запроса временный Git-ref, содержащий целевую ветку, изменения всех запросов, стоящих впереди в очереди, и собственные изменения запроса, и запускает пайплайн для этого ref.
1. Когда пайплайн запроса, стоящего в голове очереди, завершается успешно, этот запрос сливается и покидает очередь.
1. В голову очереди встаёт следующий запрос. Если слитые изменения сделали состояние, для которого проверялся запрос в очереди, неактуальным, его пайплайн отбрасывается и пересоздаётся для нового состояния, а пайплайны всех запросов за ним пересоздаются тоже.

Цепочка не хранится как отдельный объект: она определяется запросами на слияние, стоящими в очереди для одной целевой ветки одного проекта. Позиции пересчитываются по мере того, как запросы покидают очередь, поэтому слитый или удалённый из очереди запрос больше не влияет на позиции остальных.

## Предварительные требования

- В проекте должен быть включён CI/CD.
- Конфигурационный файл CI/CD должен создавать пайплайны запросов на слияние. Подробнее — в разделе [Непрерывная сборка и поставка ПО (CI/CD)](/products/code/documentation/user/delivery.html).
- В проекте должны быть включены сборочные линии для результатов слияний.
- Для изменения настроек проекта нужна роль **Мейнтейнер** или **Владелец**.

Настройки цепочек слияния доступны только если функциональность включена для экземпляра Deckhouse Code. Если их нет на странице настроек «Запросы на слияние», обратитесь к администратору.

## Включение цепочек слияния

Чтобы включить цепочки слияния:

1. Откройте проект.
1. Перейдите в «Настройки» → «Запросы на слияние».
1. В разделе «Параметры слияния» установите флажок «Включить сборочные линии для результатов слияний».
1. Установите флажок «Включить цепочки слияния».
1. Нажмите «Сохранить изменения».

Перечисленные ниже настройки отображаются под флажком «Включить цепочки слияния» и действуют только пока он установлен:

| Настройка | Описание |
|-----------|----------|
| **Сливать немедленно без перезапуска цепочки слияния** | Добавляет варианты немедленного слияния, описанные в разделе [Немедленное слияние](#немедленное-слияние). Флажок недоступен, если проект требует ускоренного (fast-forward) или полулинейного слияния, а также пока установлено требование слияния через цепочку |
| **Требовать слияния запросов только через цепочку слияния** | Отклоняет все прямые слияния в проекте. Подробнее см. в разделе [Обязательное слияние через цепочку](#обязательное-слияние-через-цепочку) |
| **Максимальное количество параллельных пайплайнов на цепочку слияния** | Ограничивает количество одновременно выполняемых пайплайнов цепочки. Подробнее см. в разделе [Ограничение на параллельные пайплайны](#ограничение-на-параллельные-пайплайны) |

Снятие флажка «Включить цепочки слияния» не очищает существующую очередь за один шаг. Очередь освобождается по мере того, как цикл обновления доходит до каждого запроса на слияние, поэтому запросы могут ещё некоторое время отображаться в очереди после сохранения настройки.

## Добавление запроса на слияние в цепочку

Чтобы добавить запрос на слияние в цепочку, нажмите «Установить автоматическое слияние» на странице запроса. Если в проекте включены цепочки слияния, автослияние ставит запрос в цепочку вместо прямого слияния. В зависимости от состояния запроса на слияние используется один из вариантов:

| Вариант | Описание |
|---------|----------|
| **Добавить в цепочку слияния** | Запрос сразу попадает в очередь. Вариант используется, если запрос можно слить и пайплайн для текущего `HEAD` SHA завершён |
| **Добавить в цепочку слияния после прохождения всех проверок слияния** | Запрос ожидает прохождения проверок слияния и затем попадает в очередь |

Рядом с кнопкой слияния отображается, какой вариант будет использован. Если запрос на слияние уже проверялся пайплайном цепочки слияния, отображается текст «Повторно добавить в цепочку слияния».

Если последний пайплайн запроса на слияние завершился с ошибкой, Deckhouse Code запрашивает подтверждение перед постановкой запроса в очередь.

Запрос на слияние также можно поставить в очередь через API:

```shell
curl --request POST --header "PRIVATE-TOKEN: <token>" \
  "https://<host>/api/v4/projects/<id>/merge_trains/merge_requests/<merge_request_iid>"
```

| Параметр | Описание |
|----------|----------|
| `sha` | SHA, который вы ожидаете увидеть в исходной ветке. Если ветка изменилась, запрос отклоняется |
| `squash` | Объединяет коммиты исходной ветки в один при слиянии запроса. При слиянии через цепочку также учитывается настройка squash самого запроса на слияние |
| `auto_merge` | Ставит запрос в очередь после прохождения проверок слияния вместо немедленного добавления в цепочку |

Эндпоинт возвращает:

- `201`, если запрос на слияние поставлен в очередь.
- `202`, если запрос на слияние только ожидает прохождения проверок слияния и ещё не попал в очередь.
- `400`, если цепочки слияния отключены в проекте или запрос нельзя поставить в очередь в его текущем состоянии.
- `401`, если запрос выполнен без аутентификации.
- `403`, если ваша роль не позволяет читать цепочку или слить этот запрос на слияние.
- `404`, если проект или запрос на слияние не найден.
- `409`, если для запроса на слияние уже включено автослияние.

## Просмотр цепочки слияния

Чтобы открыть страницу цепочек слияния проекта:

- из запроса на слияние, стоящего в очереди, — перейдите по ссылке «Просмотреть цепочку слияния»;
- со страницы пайплайна цепочки слияния — перейдите по ссылке «View merge train details» в заголовке страницы.

Страницу также можно открыть напрямую по адресу `https://<host>/<namespace>/<project>/-/merge_trains` или прочитать цепочку, не открывая страницу, — через [API](#чтение-цепочки-через-api).

На странице отображаются:

- Фильтр для выбора целевой ветки. Изначально выбрана ветка по умолчанию проекта.
- Вкладка «Активные» с запросами на слияние, которые ещё стоят в очереди, и вкладка «Слитые» с уже слитыми запросами. На каждой вкладке указано их количество.
- Строка для каждого запроса на слияние: статус пайплайна, заголовок, время добавления или слияния и пользователь, который его добавил или слил.

### Позиция запроса на слияние в цепочке

Пока запрос на слияние стоит в очереди, на его странице отображается позиция в цепочке:

- Если перед ним ничего нет: «Запущена новая цепочка слияния, и этот запрос на слияние стоит первым в очереди.»
- В остальных случаях — позиция запроса, например: «Этот запрос на слияние занимает позицию 2 из 5 в очереди.»

### Чтение цепочки через API

```shell
# Все цепочки проекта
curl --header "PRIVATE-TOKEN: <token>" "https://<host>/api/v4/projects/<id>/merge_trains"

# Цепочка одной целевой ветки
curl --header "PRIVATE-TOKEN: <token>" \
  "https://<host>/api/v4/projects/<id>/merge_trains/<target_branch>"

# Статус одного запроса на слияние в очереди
curl --header "PRIVATE-TOKEN: <token>" \
  "https://<host>/api/v4/projects/<id>/merge_trains/merge_requests/<merge_request_iid>"
```

Первые два эндпоинта принимают следующие параметры:

| Параметр | Описание |
|----------|----------|
| `scope` | Ограничивает ответ запросами, которые ещё стоят в очереди (`active`), или запросами, покинувшими очередь (`complete`) |
| `sort` | Задаёт порядок запросов по их позиции в очереди: `asc` — сначала самые старые, `desc` — сначала самые новые. Значение по умолчанию — `desc`, то есть сначала возвращаются самые новые |

Оба эндпоинта поддерживают постраничную разбивку с помощью параметров `page` и `per_page`. В ответе первого эндпоинта запросы на слияние разных целевых веток перемешаны, поэтому, если важна очередь одной ветки, читайте цепочку этой ветки.

GraphQL API также предоставляет цепочки слияния и их очереди для проекта. Обзор интерфейсов Deckhouse Code приведён в разделе [API](/products/code/documentation/user/api.html).

## Статусы в очереди

Каждый запрос на слияние в цепочке имеет один из следующих статусов, которые возвращают REST API и GraphQL. Страница цепочек слияния не показывает их напрямую: она распределяет запросы по вкладкам «Активные» и «Слитые».

| Статус | Описание |
|--------|----------|
| `idle` | Стоит в очереди, пайплайн ещё не запущен |
| `fresh` | Пайплайн соответствует текущему результату слияния |
| `stale` | Изменилось состояние впереди в очереди, пайплайн пересоздаётся |
| `merging` | Слияние выполняется |
| `merged` | Слит через цепочку и покинул очередь |
| `skip_merged` | Слит немедленно без перезапуска цепочки и покинул очередь |

Запросы на слияние со статусами `idle`, `fresh` и `stale` отображаются на вкладке «Активные», их можно удалить из очереди. Запросы со статусами `merged` и `skip_merged` отображаются на вкладке «Слитые». Пока выполняется слияние, запрос имеет статус `merging` и не отображается ни на одной из вкладок.

## Удаление запроса на слияние из цепочки

Чтобы удалить запрос на слияние из цепочки, используйте один из способов:

- Отмените автослияние на странице запроса на слияние.
- Удалите запрос из очереди на странице цепочек слияния: в строке запроса нажмите значок удаления, затем нажмите «Удалить из цепочки слияния».

При удалении запроса из очереди пайплайны запросов, стоящих за ним, пересоздаются, потому что они были проверены для очереди, которой больше не существует.

Запрос на слияние, слияние которого уже выполняется, удалить нельзя. В этом случае Deckhouse Code отклоняет удаление, и цепочка завершает слияние.

Deckhouse Code также автоматически удаляет запрос на слияние из цепочки, если запрос перестал быть пригодным для слияния. Подробнее см. в разделе [Запрос на слияние удалён из цепочки](#запрос-на-слияние-удалён-из-цепочки).

## Немедленное слияние

Если в проекте установлен флажок «Сливать немедленно без перезапуска цепочки слияния», на странице запроса на слияние, стоящего в очереди, рядом с кнопкой слияния появляются два дополнительных варианта:

| Вариант | Описание |
|---------|----------|
| **Слить сейчас и перезапустить цепочку** | Запрос на слияние сливается немедленно, а пайплайны запросов, стоящих за ним в очереди, пересоздаются с учётом слитых изменений |
| **Слить сейчас без перезапуска цепочки** | Запрос на слияние сливается немедленно, и цепочка продолжается без пересборки. Изменения, уже стоящие в очереди, не проверяются вместе со слитыми изменениями |

Оба варианта требуют подтверждения.

Используйте вариант «Слить сейчас без перезапуска цепочки» только если слитые изменения не могут повлиять на изменения в очереди. Оба варианта обходят очередь. Поэтому флажок «Сливать немедленно без перезапуска цепочки слияния» недоступен, если проект требует ускоренного (fast-forward) или полулинейного слияния, а требование слияния через цепочку убирает эти варианты полностью.

Запрос на слияние, слитый с помощью варианта «Слить сейчас без перезапуска цепочки», отображается на вкладке «Слитые» со статусом `skip_merged`. Запрос, слитый с помощью варианта «Слить сейчас и перезапустить цепочку», сливается напрямую и на эту вкладку не попадает: цепочка удаляет его из очереди так же, как любой запрос, который больше не открыт, и это удаление записывается в его активность.

### Немедленное слияние через API

Эндпоинт слияния принимает параметр `skip_merge_train`, который даёт то же поведение, что и описанные выше варианты:

```shell
curl --request PUT --header "PRIVATE-TOKEN: <token>" \
  "https://<host>/api/v4/projects/<id>/merge_requests/<merge_request_iid>/merge?skip_merge_train=true"
```

| Значение | Описание |
|----------|----------|
| `true` | Запрос на слияние сливается немедленно, и цепочка продолжается без пересборки, как при варианте «Слить сейчас без перезапуска цепочки» |
| `false` | Запрос на слияние сливается немедленно, а пайплайны запросов, стоящих за ним в очереди, пересоздаются, как при варианте «Слить сейчас и перезапустить цепочку». Значение по умолчанию |

Параметр действует только если в проекте установлен флажок «Сливать немедленно без перезапуска цепочки слияния». В остальных случаях он игнорируется. Если слияние через цепочку обязательно, само слияние отклоняется.

## Обязательное слияние через цепочку

Установите флажок «Требовать слияния запросов только через цепочку слияния», чтобы отклонять все прямые слияния в проекте. Когда требование включено:

- страница запроса на слияние не предлагает варианты немедленного слияния;
- слияние через API отклоняется, если слияние идёт не через цепочку, то есть если для запроса не включено автослияние;
- внутренние слияния, которые выполняет сама цепочка, не затрагиваются.

Установка требования также снимает и блокирует флажок «Сливать немедленно без перезапуска цепочки слияния»: обход очереди был бы отклонён при слиянии, поэтому он не предлагается. При снятии требования ранее сохранённое значение этого флажка восстанавливается.

Требование действует только пока в проекте включены цепочки слияния, поэтому при отключённых цепочках слияния не блокируются.

Требование действует для всех пользователей, включая владельцев проекта и администраторов.

## Ограничение на параллельные пайплайны

Цепочка запускает несколько пайплайнов одновременно, чтобы очередь не продвигалась по одному пайплайну. Действующее ограничение равно меньшему из двух значений:

- ограничение экземпляра на количество параллельных пайплайнов цепочки слияния, которое задаёт администратор (по умолчанию — `20`);
- значение настройки проекта «Максимальное количество параллельных пайплайнов на цепочку слияния».

Оставьте поле проекта пустым, чтобы использовать ограничение экземпляра. Значение проекта должно быть в диапазоне от `1` до `500`. Проект может только уменьшить ограничение, но не может превысить ограничение экземпляра.

## Пайплайны цепочки слияния

Пайплайн цепочки слияния выполняется для временного Git-ref, который Deckhouse Code создаёт для запроса на слияние в очереди, а не для исходной ветки запроса. В списках пайплайнов такие пайплайны помечаются как `merge train`, что отличает их от сборочных линий для результатов слияний.

Завершённый пайплайн цепочки слияния нельзя перезапустить: он проверял состояние очереди, которого больше нет. Чтобы получить новый пайплайн, добавьте запрос на слияние в цепочку заново.

Пайплайн цепочки слияния отбрасывается и заменяется, когда:

- в исходную ветку запроса на слияние добавлены новые коммиты;
- запрос, стоящий впереди в очереди, слит, удалён из очереди или получил новый пайплайн;
- пайплайн запроса, стоящего непосредственно впереди в очереди, завершился с ошибкой;
- изменения отправлены напрямую в целевую ветку — в этом случае пересоздаются пайплайны всей очереди, начиная с запроса в голове очереди.

### Запуск заданий только в пайплайнах цепочки слияния

В пайплайне цепочки слияния переменная `CI_MERGE_REQUEST_EVENT_TYPE` имеет значение `merge_train`. С её помощью можно запускать задание только в пайплайнах цепочки слияния:

```yaml
integration-tests:
  script: ./run-integration-tests.sh
  rules:
    - if: $CI_MERGE_REQUEST_EVENT_TYPE == "merge_train"
```

Обратное условие позволяет пропускать задание в пайплайнах цепочки слияния:

```yaml
quick-lint:
  script: ./lint.sh
  rules:
    - if: $CI_MERGE_REQUEST_EVENT_TYPE != "merge_train"
```

## Активность запроса на слияние

Deckhouse Code записывает, что происходит с запросом на слияние в цепочке, в виде системных заметок в разделе «Активность» запроса на слияние:

- запрос запустил цепочку или был добавлен в цепочку на определённую позицию в очереди;
- запрос удалён из цепочки пользователем;
- запрос удалён из цепочки системой, с указанием причины;
- автоматическое добавление в цепочку после прохождения проверок включено, отменено или прервано, с указанием причины.

Если запрос на слияние удалён из цепочки системой, его участники также получают элемент в списке задач.

## Доступ к цепочкам слияния

Доступ к цепочкам слияния зависит от роли в проекте и от настроек проекта:

| Действие | Требования |
|----------|------------|
| Смотреть страницу цепочек слияния и читать цепочки через API | В проекте включены цепочки слияния, и у вас есть доступ на чтение запросов на слияние и пайплайнов. В стандартных ролях это доступно пользователям с ролью **Наблюдатель** или выше |
| Читать статус цепочки для отдельного запроса на слияние | Те же требования, что и для чтения цепочки |
| Добавить запрос на слияние в цепочку | Вы можете слить этот запрос на слияние. В стандартных ролях это доступно пользователям с ролью **Разработчик** или выше |
| Удалить запрос на слияние из очереди на странице цепочек слияния | Вы можете отменять пайплайны, изменять запрос на слияние и сливать в целевую ветку. В стандартных ролях это доступно пользователям с ролью **Разработчик** или выше |
| Изменять настройки цепочек слияния в проекте | **Мейнтейнер** или **Владелец** |

И страница цепочек слияния, и API требуют входа в систему. Цепочки слияния недоступны анонимным пользователям даже в публичных проектах.

## События аудита

Deckhouse Code записывает события аудита при изменении настроек цепочек слияния в проекте.

| Событие аудита | Описание |
|----------------|----------|
| `project_cicd_merge_trains_enabled_updated` | Настройка цепочек слияния в проекте изменена |
| `project_cicd_merge_train_enforced_updated` | Настройка обязательного слияния через цепочку изменена |

## Устранение проблем

### Запрос на слияние удалён из цепочки

Запрос на слияние, который перестал быть пригодным для слияния во время выполнения пайплайна, удаляется из очереди, а не блокирует её. Причина записывается системной заметкой в разделе «Активность» запроса на слияние.

Наиболее частые причины:

- цепочки слияния отключены в проекте;
- запрос на слияние закрыт;
- запрос на слияние помечен как черновик;
- изменена целевая ветка запроса на слияние;
- запрос на слияние стал непригодным для слияния, например из-за конфликта;
- автослияние отменено для запроса на слияние;
- пайплайн цепочки слияния для этого запроса завершился с ошибкой;
- удалена учётная запись, поставившая запрос в очередь.

Пока запрос на слияние ожидает прохождения проверок слияния, он также удаляется, если становится черновиком или его пайплайн завершается с ошибкой до прохождения проверок.

Дискуссии и апрувы проверяются при постановке запроса на слияние в очередь. Если запрос уже стоит в очереди, дискуссия, открытая после этого, не блокирует слияние, даже если в проекте требуется закрыть все дискуссии: при слиянии вносится ровно то, что проверил пайплайн, иначе один комментарий удалял бы запрос из очереди и заставлял бы заново собирать все запросы за ним. Отозванный обязательный апрув слияние блокирует. Запрос сохраняет своё место в очереди, доходит до её головы, и там при попытке слияния удаляется из цепочки.

Устраните причину, указанную в заметке, и добавьте запрос на слияние в цепочку заново.

### Кнопка слияния не предлагает варианты цепочки слияния

Проверьте следующее:

- в настройках проекта включены сборочные линии для результатов слияний и цепочки слияния;
- конфигурационный файл CI/CD создаёт пайплайны запросов на слияние;
- у запроса на слияние есть пайплайн для текущего `HEAD` SHA исходной ветки, и этот пайплайн завершён;
- ваша роль позволяет слить этот запрос на слияние.

### Слияние отклонено в проекте, требующем цепочку слияния

Если установлен флажок «Требовать слияния запросов только через цепочку слияния», прямое слияние отклоняется, в том числе через API. Вместо этого добавьте запрос на слияние в цепочку.

Требование действует для всех пользователей, поэтому владелец проекта не может его обойти. Чтобы снова разрешить прямые слияния, снимите флажок в настройках проекта.

### Пайплайн цепочки слияния нельзя перезапустить

Завершённый пайплайн цепочки слияния перезапустить нельзя: он проверял состояние очереди, которого больше нет. Вместо этого добавьте запрос на слияние в цепочку заново — будет создан пайплайн для текущего состояния.

### Слияние выглядит зависшим

Прервавшееся слияние восстанавливается запланированной задачей: запрос на слияние возвращается в очередь, и цепочка продолжает работу. Действия пользователя не требуются.

### Цепочки слияния отключены, но очередь всё ещё отображается

Очередь освобождается циклом обновления, а не за один шаг. Запросы на слияние исчезают со страницы по мере того, как цикл доходит до них.

### Страница цепочек слияния пуста

Проверьте следующее:

- в фильтре выбрана целевая ветка этих запросов на слияние;
- для запросов на слияние включено автослияние;
- в проекте включены цепочки слияния. Если они отключены, страница недоступна, даже если очередь осталась с прежнего состояния.

### Действие удаления недоступно

Действие удаления отображается только на вкладке «Активные» и только если вы можете отменять пайплайны, изменять запрос на слияние и сливать в целевую ветку. Запрос на слияние, слияние которого уже выполняется, удалить нельзя.
