Статический анализ кода (SAST, Static Application Security Testing) в Deckhouse Code ищет уязвимости в исходном коде проекта. За ним стоит сканер [Semgrep](https://semgrep.dev/), а само сканирование называется `sast`.

Сканирование является *обязательным*: оно подмешивается в пайплайн проекта политикой исполнения сканирования, которая лежит в отдельном проекте политик безопасности, а не в `.gitlab-ci.yml` самого проекта. Что сканируется и что приводит к ошибке пайплайна, решает политика — то есть команда безопасности, — и проверяемый проект не может это переопределить своими настройками CI/CD.

{% alert level="warning" %}
Сканирование безопасности включается функциональным флагом уровня инстанса `fe_security_scan_policies`, который **по умолчанию отключён**. Пока он выключен, страницы политик и страницы настроек интеграций сканеров скрыты, а задачи сканирования в пайплайны не подмешиваются. Попросите администратора инстанса включить флаг.
{% endalert %}

## Что делает сканирование

Сканирование `sast` добавляет в пайплайн две задачи, обе на стадии `fe-security-scanner`:

| Задача | Что делает |
|--------|------------|
| `semgrep_sast_scan` | Запускает сканер по репозиторию и публикует его собственный JSON-вывод как артефакт. |
| `semgrep_sast_junit` | Читает этот JSON, строит из него отчёт для сводки тестов и отчёт безопасности и решает исход: задача завершается успешно, если ни одна находка не достигла порога блокировки, и с ошибкой в противном случае. |

Обе задачи выгружают артефакты с `when: always`, поэтому отчёты оказываются на диске раньше, чем вторая задача может завершиться с ошибкой, — заблокированный пайплайн никогда не лишает вас находок, которые его заблокировали.

Находки попадают туда же, куда и находки остальных сканеров политики:

| Отчёт | Где смотреть |
|-------|--------------|
| Тесты (JUnit) | Вкладка «Tests» пайплайна и сводка тестов в merge request |
| Отчёт безопасности (SAST) | Страница отчёта об уязвимостях |
| Находки, переданные в DefectDojo | DefectDojo, если эта интеграция настроена |

## Предварительные требования

Чтобы сканирование могло запуститься, убедитесь, что:

- администратор инстанса включил функциональный флаг `fe_security_scan_policies`;
- проект политик безопасности привязан к проекту или к группе выше него;
- доступен GitLab Runner с executor `docker`, и он может скачать образ сканера (см. раздел «Откуда берётся образ сканера»).

## Включение сканирования

Добавьте действие `sast` в файл `.gitlab/security-policies/policy.yml` проекта политик безопасности:

```yaml
scan_execution_policy:
  - name: SAST everywhere
    enabled: true
    rules:
      - type: pipeline
        branches: ["*"]
    actions:
      - scan: sast
```

Затем привяжите проект политик к нужному проекту или группе в разделе «Настройки» → «Политика безопасности». После этого каждый пайплайн, попадающий под правила политики, получает две задачи, описанные выше.

Параметры сканирования можно задавать и в редакторе политик — он формирует форму, описанную ниже.

## Что задаёт политика

Форма действия `sast` разбита на четыре блока. Все параметры принадлежат политике, а не проверяемому проекту: значения записываются в задачу сервером при формировании пайплайна, поэтому собственные переменные CI/CD проверяемого проекта их не меняют.

### Правила

Блок задаёт, какие правила выполняет сканирование.

<!-- TODO(screenshot): блок «Правила» с раскрытым списком «Набор правил». Тема навигации Neutral, подсветка Light. -->

| Поле | Что задаёт |
|------|------------|
| «Набор правил» | Откуда берутся правила. Один из четырёх источников, описанных ниже. По умолчанию — «Набор из поставки продукта». |
| «Путь к набору правил в образе» | Какой из наборов, лежащих в образе сканера, выполнять (см. раздел «Наборы правил в образе»). По умолчанию — `/rules/lgpl`. Если по этому пути набора нет, сканирование останавливается. |
| «Правила» | Сами правила, в YAML сканера. Показывается, когда источник — «Правила, заданные в политике». |
| «Путь к файлу правил» | Путь к файлу правил внутри проекта, из которого они читаются. По умолчанию — `.semgrep.yml`. |
| «Дополнять поставленный набор» | Включено по умолчанию: ваши правила выполняются *вместе* с поставленным набором. Если снять галочку, они выполняются *вместо* него, и всё, что покрывал поставленный набор, перестаёт проверяться. |

Четыре источника правил отличаются тем, кто владеет файлом:

| Источник | Где лежат правила | Кто ими распоряжается |
|----------|-------------------|-----------------------|
| «Набор из поставки продукта» | В образе сканера, по пути, указанному выше | Поставка продукта |
| «Файл в проекте политик безопасности» | Проект, где лежит политика, на его ветке по умолчанию | Команда безопасности |
| «Файл в проверяемом проекте» | Сканируемый репозиторий, на строящемся коммите | **Проверяемый проект** |
| «Правила, заданные в политике» | Сама политика | Автор политики |

Три источника из четырёх читает сервер и записывает в задачу; только «Файл в проверяемом проекте» читает сама задача, из своей рабочей копии, на строящемся коммите. Это же единственный источник, который пишет проверяемая сторона, — и относиться к нему стоит соответственно: коммит, переписывающий этот файл, переписывает правила сканирования, которое проверяет этот же проект. Включённая галочка «Дополнять поставленный набор» сохраняет базовую линию даже тогда, когда файл в проекте опустошён.

Файл правил, названный политикой, но не доставленный сканированию, — это ошибка, а не повод откатиться к умолчанию: задача печатает причину и останавливается, вместо того чтобы выполнить сканирование поставленным набором и отчитаться об успехе.

### Блокировка

Блок задаёт, что находка делает с пайплайном.

| Поле | Что задаёт |
|------|------------|
| «Порог блокировки» | Что приводит к ошибке пайплайна. Находки ниже порога всё равно попадают в отчёт и в отчёт об уязвимостях — порог решает только исход пайплайна и больше ничего. По умолчанию — «Высокий и выше». |

У порога четыре значения:

| Значение | Что приводит к ошибке пайплайна |
|----------|---------------------|
| «Высокий и выше» (по умолчанию) | Находка высокого уровня серьёзности. Средний и информационный уровни только попадают в отчёт. |
| «Средний и выше» | Средний и высокий уровни серьёзности. Информационный только попадает в отчёт. |
| «Любая находка» | Любая находка, какого бы уровня серьёзности она ни была. |
| «Только сообщать, ничего не блокировать» | Ничто. Находки всё равно попадают в отчёт, в отчёт об уязвимостях и в DefectDojo. |

Список короткий не случайно. У Semgrep три уровня серьёзности — ERROR, WARNING и INFO, — которые сканирование показывает как высокий, средний и информационный. Ни критического, ни низкого у него нет, поэтому порог с таким именем был бы порогом, которого не достигает ни одна находка: «критический» не блокировал бы ничего, выглядя при этом строгим, а «низкий» дублировал бы «средний». Значение «Только сообщать, ничего не блокировать» существует затем, чтобы отказ от блокировки был видимым решением в политике, а не побочным следствием выбора недостижимого уровня.

### Пути

Блок задаёт, на что сканирование смотрит, а на что нет.

| Поле | Что задаёт |
|------|------------|
| «Фильтры путей» | Откуда берутся списки путей, которые не нужно осматривать. По умолчанию — «Без фильтров». |
| «Путь к файлу фильтров» | Путь к файлу фильтров внутри проекта, из которого они читаются. По умолчанию — `.semgrepignore`. |
| «Исключить пути» | По одному пути или шаблону в строке: сторонний код, фикстуры, сгенерированные файлы. |
| «Только эти пути» | По одному пути или шаблону в строке. Всё остальное в сканирование не попадает. |
| «Учитывать .gitignore репозитория» | По умолчанию выключено. |

«Без фильтров» не значит, что не пропускается ничего: задача всегда добавляет к тому, что задала политика, свои встроенные исключения — `node_modules/`, `vendor/`, `dist/`, `build/`, `.venv/` и `.git/`, — поэтому собственный файл фильтров никогда не вернёт деревья зависимостей в сканирование незаметно.

У фильтров тот же выбор источника из четырёх пунктов, что и у правил:

| Источник | Где лежит список | Кто им распоряжается |
|----------|------------------|----------------------|
| «Без фильтров» | — | — |
| «Файл в проекте политик безопасности» | Рядом с политикой, применяется ко всем проектам, которые она покрывает | Команда безопасности |
| «Файл в проверяемом проекте» | Сканируемый репозиторий | **Проверяемый проект** |
| «Списки, заданные в политике» | Два списка в форме | Автор политики |

По умолчанию задача убирает любой `.semgrepignore`, найденный в сканируемом репозитории, — включая вложенные в подкаталогах, — перед началом сканирования. Выбор «Файл в проверяемом проекте» это и отключает, и подойти к нему стоит осознанно:

{% alert level="warning" %}
«Файл в проверяемом проекте» и «Учитывать .gitignore репозитория» одинаково отдают проверяемому проекту право решать, что осматривает обязательное сканирование. После этого коммит в проверяемом проекте может сузить сканирование, которое его же и проверяет, и в политике это сужение не видно. Оба варианта законны — команда безопасности вполне может решить, что каждый проект лучше знает свои каталоги стороннего кода, — но это именно делегирование, и политика есть то место, где такое решение фиксируется. По умолчанию не включён ни один из них.
{% endalert %}

Ещё две вещи про эти два списка:

- «Только эти пути» сильнее, чем «Исключить пути». Исключение убирает то, что названо; включение убирает всё остальное. Один шаблон `src/**` незаметно исключает из сканирования и `lib`, и `config`, и миграции.
- Применяются они в этом же порядке — сначала включения, потом исключения, — поэтому исключение действует и внутри того, что пропустило включение.

Шаблон, не совпавший ни с чем, — не синтаксическая ошибка, и форма его не поймает. Ловит его задача: она печатает, сколько файлов сканер прочитал на самом деле, и завершается с ошибкой, когда это число равно нулю.

### Дополнительно

Блок задаёт, какие уровни правил выполняются, и флаги, которых нет в форме.

| Поле | Что задаёт |
|------|------------|
| «Уровни правил» | Какие правила вообще выполняются: «Высокий» (ERROR), «Средний» (WARNING), «Информационный» (INFO). По умолчанию включены все три. |
| «Дополнительные параметры» | Флаги, передаваемые сканированию как есть, — для того, чего нет в форме. |

«Уровни правил» и «Порог блокировки» выглядят одинаково, а делают разное:

| Поле | На что влияет | Находка ниже уровня |
|------|---------------|---------------------|
| «Уровни правил» | Какие правила **выполняются** | Её не существует: правило не выполнялось |
| «Порог блокировки» | Какие находки **приводят к ошибке пайплайна** | Она есть в отчёте, но не блокирует |

Поэтому исключённый уровень убирает свои находки и из отчёта, а не только из блокировки, — и отчёт об уязвимостях, и DefectDojo становятся меньше, причём незаметно. Порог блокировки, выставленный ниже самого низкого выполняемого уровня, не сработает никогда; форма говорит об этом, когда так получилось.

«Дополнительные параметры» нужны для настройки ресурсов раннера — таймауты, лимиты памяти, максимальный размер файла, — а не для изменения того, чем является сканирование. Флаги, перенаправляющие или подавляющие отчёт, отклоняются, как и флаги, которыми форма распоряжается сама: форматы вывода и отчётов (`--json`, `--sarif`, `--junit-xml`, `--gitlab-sast`, `--gitlab-secrets`, `--output`, `--text` и парные к ним `*-output`), а также `--config`, `--metrics` и `--baseline-commit`.

## Наборы правил в образе

По умолчанию сканирование выполняет набор правил, лежащий внутри образа сканера, по пути `/rules/lgpl`. В образе лежит не один набор, и поле «Путь к набору правил в образе» выбирает между ними:

| Путь в образе | Правил | Языки |
|---------------|--------|-------|
| `/rules/lgpl` (по умолчанию) | 152 | `generic`, `java`, `javascript`, `typescript`, `kotlin`, `swift` |
| `/rules/lgpl-cc` | 97 | `generic`, `java`, `javascript`, `typescript`, `php`, `python`, `ruby`, `yaml` |
| `/rules` | 338 | `c`, `c++`, `c#`, `go`, `java`, `javascript`, `typescript`, `python`, `scala` |

Значения измерены в образе `registry.gitlab.com/security-products/semgrep:6.25.0` и относятся к нему; в более новом образе состав может быть другим. У каждого каталога в образе свой файл лицензии, и какой набор выполнять — ваш выбор.

{% alert level="warning" %}
Наборы не вложены друг в друга: `/rules/lgpl-cc` добавляет python, ruby и php, но теряет kotlin и swift, а `/rules` не покрывает ни kotlin, ни swift, ни php, ни ruby. Значит, набор по умолчанию не покрывает Python, Go, Ruby, C#, PHP и C/C++. Репозиторий на одном из этих языков, просканированный по пути по умолчанию, завершится успешно и без находок — и это сканирование честно говорит, что ни одно правило к нему не подошло, а не поломка. Но покрытия SAST у такого репозитория при этом нет никакого: для него нужно явно выбрать `/rules/lgpl-cc` или `/rules`, а не полагаться на путь по умолчанию.
{% endalert %}

Вторая половина ответа — собственные правила. Они задаются полем «Набор правил» и, если галочка «Дополнять поставленный набор» осталась включённой, выполняются вместе с тем набором, который даёт образ.

## Откуда берётся образ сканера

Образ, в котором выполняется сканирование, разрешается сервером один раз, до старта задачи, и записывается в неё готовым значением. Переменной CI/CD он не становится, поэтому настройки проверяемого проекта не могут направить сканирование на другой сканер.

Источники перечислены от самого слабого к самому сильному — каждый следующий, если задан, перекрывает предыдущий:

1. Версия из поставки продукта. Она же используется, когда не задано ничего другого.
1. Переменная окружения инстанса `FE_SCANS_SEMGREP_IMAGE` — решение администратора всей установки.
1. Интеграция Semgrep у группы, которой принадлежит политика, или у группы выше (см. ниже).
1. Версия, названная в самой политике, в поле «Версия сканера».

Исключение ровно одно: если интеграция называет не реестр, а готовый образ полной ссылкой — с тегом или дайджестом, — используется именно он, и версии из политики уже нечего заменять.

Запись интеграции самого проверяемого проекта в расчёт не идёт. Образ решает, что вообще значит «сканирование прошло», а проверяемая сторона на этот вопрос не отвечает.

### Интеграция Semgrep

Интеграция хранит одно: откуда читается образ сканера. Настраивается она на **группе**, чтобы установка сказала это один раз, а не повторяла в каждой политике; в проекте интеграция видна без полей — так читатель узнаёт, что сканирование настраивается выше него.

Откройте на группе «Настройки» → «Интеграции» → «Semgrep» и заполните любое из двух полей — оба необязательны:

| Поле | Что задаёт |
|------|------------|
| «Реестр» | Реестр, куда скопирован образ сканера, без тега. Например, `registry.example.com` или `registry.example.com/mirror`. Сканирование берёт образ отсюда, а не из поставки продукта, в версии, которую запрашивает политика. |
| «Подготовленный образ» | Один образ, указанный полностью и с тегом или дайджестом, — для установки, которая собирает его сама. Например, `registry.example.com/ci-images/semgrep:6.25.0`. Используется ровно так, как написан, поэтому версия из политики больше не применяется. Имеет приоритет над полем «Реестр». |

Если оба поля пусты, сканирование выполняется в образе из поставки продукта. Ничего про то, что сканирование ищет, здесь не задаётся — это живёт в политике.

### Версия из поставки продукта

По умолчанию используется конкретная версия, а не плавающий тег: этот релиз поставляет `registry.gitlab.com/security-products/semgrep:6.25.0`. Один тег фиксирует сразу обе половины сканера — движок и наборы правил, вложенные в образ, — потому что обе лежат в одном образе.

Поле «Версия сканера» в политике принимает обе формы фиксации версии:

- номер версии, например `6.25.0`, — его читает человек и с ним можно сравнивать;
- дайджест, например `sha256:aafbcaff…`, — он называет одну сборку, и подменить её нельзя.

Плавающие теги (`latest`, `stable`, тег из одного мажорного номера — например, `6`) и ссылки с адресом реестра отклоняются: реестр называет интеграция, а политика называет только версию.

Версия, поставляемая с релизом, пересматривается при обновлении Deckhouse Code, поэтому она движется вместе с продуктом, а не застывает.

### Закрытый контур

Образ по умолчанию загружается из `registry.gitlab.com`. Установке без доступа в интернет нужно сначала зеркалировать его в свой реестр — ровно так, как предписывает офлайн-инструкция GitLab для его аналитических образов, — а затем указать этот реестр в поле «Реестр» интеграции. Deckhouse Code образ называет, но не поставляет.

{% alert level="info" %}
Dependency proxy здесь не помогает. Это pull-through cache для образов, лежащих на Docker Hub, а образ сканера публикуется в `registry.gitlab.com`, поэтому предложить ему прокси нечего. Установке, которая хочет перестать загружать образ извне при каждом запуске — в закрытом контуре или нет, — подходит тот же ответ: зеркалировать образ в свой реестр и указать его в поле «Реестр».
{% endalert %}

## Платные возможности Semgrep

Всё описанное на этой странице работает на открытой версии сканера. Ряд возможностей Semgrep в неё не входит:

| Возможность | В открытой версии | Чем закрывается в Deckhouse Code |
|-------------|-------------------|----------------------------------|
| Анализ потока данных между файлами | Нет, только внутри одного файла | Ничем; ограничение принимается |
| Правила Pro | Нет | Собственными правилами, через поле «Набор правил» |
| Анализ зависимостей (Supply Chain) | Нет | Интеграцией CodeScoring или сканированием `dependency_scanning` |
| Проверка валидности найденных секретов | Нет | Ничем |

{% alert level="warning" %}
Платные возможности работают через облако вендора. Их включение означает, что сканирование выгружает находки — и контекст кода вокруг них — на серверы Semgrep, за пределы вашей установки. В закрытом контуре они недоступны по более простой причине: до них нет сети.
{% endalert %}

Обязательное сканирование не отправляет наружу ничего. Оно выполняет `semgrep scan` с флагами `--metrics=off` и `--disable-version-check`, а не `semgrep ci`, поэтому задачу не покидают ни находки, ни телеметрия использования. Прежде чем сканер вообще будет найден, задача очищает все унаследованные переменные `SEMGREP_*` и `PYTHON*`: две из них, `SEMGREP_RULES` и `SEMGREP_BASELINE_COMMIT`, документированы как эквиваленты `--config` и `--baseline-commit`, и оставленные на месте они позволили бы настройкам CI/CD проверяемого проекта подменить набор правил или базу сравнения того сканирования, которое его проверяет.

## Диагностика

Ниже перечислены типичные проблемы и то, что нужно проверить в каждом случае.

### Сканирование не появляется в пайплайне

Проверьте, что:

- функциональный флаг `fe_security_scan_policies` включён на инстансе;
- проект политик безопасности привязан к проекту, а `policy.yml` содержит действие `- scan: sast`;
- правила политики совпадают с пайплайном (ветка, тип пайплайна);
- доступен GitLab Runner с executor `docker`.

### Задача завершается с ошибкой «no rule set at … in this image»

Пути, указанного в поле «Путь к набору правил в образе», в разрешённом образе нет. Сверьте путь с таблицей выше и проверьте, какой образ используется на самом деле: у «Подготовленного образа», заданного на интеграции, раскладка может быть другой.

### Задача завершается с ошибкой «semgrep read no files at all»

Сканирование не осмотрело ничего и поэтому отказывается отчитываться об успехе. Обычные причины — шаблон в поле «Только эти пути», не совпавший ни с чем; фильтры, убравшие весь репозиторий; либо пустая рабочая копия. В логе задачи напечатано, сколько файлов она обработала и сколько из них убрали фильтры.

### Сканирование завершается успешно, но ничего не находит

Чаще всего набор правил не покрывает язык репозитория — см. предупреждение в разделе «Наборы правил в образе». Посмотрите лог задачи: в нём напечатан используемый путь к набору правил и число загруженных правил. Тот же результат по другой причине даёт сужение поля «Уровни правил»: уровень, который не выбран, не выполняется вовсе, поэтому его находки отсутствуют в отчёте, а не просто не блокируют.
