CodeScoring — это инструмент анализа состава программного обеспечения (SCA/OSA) для проверки сторонних зависимостей на наличие уязвимостей, лицензионных рисков и нарушений политик безопасности.

Интеграция CodeScoring в Deckhouse Code позволяет использовать возможности CodeScoring в CI/CD-пайплайнах и покрывает следующие SCA/OSA-сценарии:

- анализ зависимостей;
- обнаружение уязвимостей;
- генерация Software Bill of Materials (SBOM);
- разбор результатов на стороне платформы.

Статический (SAST) и динамический анализ (DAST) в эту интеграцию не входят.

{% alert level="warning" %}
Интеграция CodeScoring находится в статусе бета. Она включается функциональным флагом `codescoring_integration`, который **по умолчанию отключён**. Перед настройкой интеграции попросите администратора Deckhouse Code включить его.
{% endalert %}

## Возможности интеграции

Интеграция предоставляет следующие возможности:

- анализ зависимостей приложения (пакеты, библиотеки, версии);
- обнаружение уязвимостей по базам Common Vulnerabilities and Exposures (CVE), включая ФСТЭК БДУ и Kaspersky Open Source Software Threats Data Feed;
- генерация SBOM в формате CycloneDX;
- формирование нативных отчётов GitLab за один прогон: «Dependency Scanning», «Code Quality», «JUnit», а также «SARIF» (Static Analysis Results Interchange Format) и «CycloneDX SBOM»;
- анализ результатов и применение политик (пороги серьёзности, игнорирование срабатываний) на стороне платформы CodeScoring.

## Предварительные требования

Перед настройкой интеграции убедитесь, что:

- развёрнут сервер CodeScoring (on-premise или SaaS);
- получен API-токен в профиле пользователя CodeScoring;
- в проекте или группе доступен GitLab Runner с executor `docker`. Задача сканера выполняется в контейнере `debian:bookworm-slim`.

{% alert level="info" %}
По умолчанию консольный агент Johnny не требуется устанавливать вручную: он скачивается автоматически с вашего сервера CodeScoring по API-токену при каждом запуске задачи сканера. Это поведение задаётся параметром «Доставка агента» в настройках интеграции (см. ниже); вместо этого можно закрепить конкретную версию агента или запускать сканирование в собственном образе, где агент уже установлен.
{% endalert %}

## Настройка интеграции в проекте

Форма интеграции только активирует CodeScoring и хранит параметры подключения к серверу и способ доставки агента сканирования. Она **не** содержит параметров сканирования (название проекта, стадия сканирования, режим сканирования и т. д.) — они задаются отдельно, в политике исполнения сканирования (см. раздел «Запуск сканирования» ниже).

Параметры подключения задаются через настройки проекта или группы:

1. Откройте проект в Deckhouse Code.
1. Перейдите в раздел «Настройки» → «Интеграции» → «CodeScoring».
1. Заполните параметры:

   | Параметр | Описание |
   |----------|----------|
   | «Активна» | Переключатель включения интеграции для проекта |
   | «URL сервера» | Адрес сервера CodeScoring. Например, `https://codescoring.example.com` |
   | «API-токен» | Токен из профиля пользователя CodeScoring (хранится в зашифрованном виде и маскируется) |
   | «Доверие сертификату» | Как проверяется TLS при подключении Deckhouse Code к серверу. Варианты: «Доверять тому, чему уже доверяет задача» (использовать системное хранилище доверия задачи или образа); «Доверять указанному ниже удостоверяющему центру» (вставить сертификат CA в формате PEM в появившееся поле); «Не проверять сертификат» |
   | «Доставка агента» | Как консольный агент Johnny передаётся в задачу сканирования. Варианты: «Соответствует версии сервера CodeScoring» (скачивать агент, соответствующий вашему серверу, при каждом запуске); «Закреплённая версия из нашего реестра» (загружать фиксированную версию агента — задайте «Версию агента»); «Собственный образ» (запускать сканирование в вашем образе, где агент уже установлен — задайте «Образ агента» и, если реестр использует частный CA, его «Удостоверяющий центр реестра образа агента» в формате PEM) |

1. Нажмите «Сохранить».
1. Нажмите «Проверить настройки», чтобы проверить URL-адрес, токен и доверие TLS на стороне сервера.

{% alert level="warning" %}
Вариант «Не проверять сертификат» ослабляет проверку TLS **только** для проверки подключения «Проверить настройки», выполняемой из Deckhouse Code. Агент сканирования в пайплайне всегда проверяет TLS, поэтому для сервера с частным или самоподписанным сертификатом необходимо всё равно предоставить его CA (см. ниже), даже если выбран этот вариант.
{% endalert %}

Интеграция автоматически передаёт параметры подключения и доставки агента в каждый пайплайн (задавать их в `.gitlab-ci.yml` не требуется): URL-адрес сервера и токен (`FE_SCANS_CODESCORING_URL`, `FE_SCANS_CODESCORING_TOKEN`), выбранный режим доверия сертификату вместе с CA и режим доставки агента. Сами параметры сканирования задаёт политика исполнения сканирования.

Для сервера с частным или самоподписанным сертификатом укажите его CA одним из двух способов:

- (рекомендуется) вариантом «Доверие сертификату» → «Доверять указанному ниже удостоверяющему центру» в форме интеграции; или
- CI-переменной типа **File** `CODESCORING_SSL_FILE` (в разделе «Настройки» → «CI/CD» → «Переменные»).

Задача `codescoring_scan` экспортирует заданное значение в `SSL_CERT_FILE`, которому доверяют и `curl`, и агент Johnny; если заданы оба, приоритет имеет CA из интеграции.

## Запуск сканирования

Сканер подмешивается в пайплайн через **scan-execution-политику**, а не ручным `include`.

Для настройки автоматического сканирования выполните следующее:

1. В проекте политик безопасности добавьте в `policy.yml` действие `codescoring`:

   ```yaml
   scan_execution_policy:
     - name: CodeScoring on every pipeline
       enabled: true
       rules:
         - type: pipeline
           branches: ["*"]
       actions:
         - scan: codescoring
   ```

1. Привяжите проект политик к целевому проекту в разделе «Настройки» → «Security policy».

После этого в каждый пайплайн автоматически добавляется задача `codescoring_scan` (стадия `fe-security-scanner`), которая:

- предоставляет консольный агент Johnny в соответствии с режимом «Доставка агента», заданным в интеграции (по умолчанию скачивает его с сервера по токену; для самоподписанного сертификата — с CA из настройки интеграции или переменной `CODESCORING_SSL_FILE`);
- запускает сканирование по одному разу для каждой стадии, выбранной в политике, и отдаёт нативные отчёты GitLab. В ветке по умолчанию сканирование записывается как версия проекта по умолчанию.

### Параметры сканирования

Все параметры сканирования задаются в политике, в действии сканирования `codescoring`. Редактор политик группирует их в два блока.

#### SCA

| Параметр | Описание |
|----------|----------|
| Стадии сканирования | Одна или несколько стадий для привязки результатов на стороне платформы: `build`, `dev`, `source`, `stage`, `test`, `prod`, `proxy`. Сканирование выполняется по одному разу для каждой выбранной стадии. |
| Режим сканирования | Как сканируется цель. |
| Цель сканирования | Путь, сканируемый агентом (по умолчанию — рабочая директория). |
| Игнорируемые пути | Пути, исключаемые из сканирования. |
| Разрешать с помощью | Пакетные менеджеры для разрешения зависимостей. |
| Спрашивать OSA о каждом компоненте | Запрашивать у CodeScoring.OSA вердикт по каждому разрешённому компоненту, чтобы проект без OSA Proxy в сборке всё равно узнал, что ответил бы прокси. |
| Прерывать задачу при отклонённом компоненте | Прерывать задачу, если OSA отклоняет хотя бы один компонент. |
| Прерывать при пустом результате | Прерывать задачу, если сканирование не разрешило ни одного компонента. |
| Дополнительные аргументы агента | Дополнительные аргументы командной строки, передаваемые агенту. |

CodeScoring.OSA входит в параметры SCA и не является отдельным модулем.

#### Secrets

| Параметр | Описание |
|----------|----------|
| Движок поиска секретов | Движок для поиска секретов: `gitleaks`, `trufflehog` или `kingfisher`. |
| Путь к исполняемому файлу движка | Путь к исполняемому файлу движка. |
| Путь к конфигурации движка | Путь к файлу конфигурации движка. |
| Игнорируемые пути | Пути, исключаемые из поиска секретов. |
| Дополнительные аргументы поиска секретов | Дополнительные аргументы командной строки, передаваемые движку. |

{% alert level="info" %}
Блок Secrets, как ожидается, изменится в одной из будущих версий Code; параметры выше описывают его текущее состояние.
{% endalert %}

Отдельный `include` и ручная установка переменных `CODESCORING_*` не требуются. Всё необходимое подставляют интеграция и политика.

## Отчёты и просмотр результатов

Одна задача `codescoring_scan` формирует все отчёты за один прогон. Deckhouse Code основан на GitLab FOSS, где часть EE-виджетов отсутствует, поэтому результаты выводятся в следующем виде:

| Отчёт | Где смотреть |
|-------|--------------|
| Тесты (JUnit) | Вкладка «Tests» пайплайна (нативно) |
| Code Quality | Виджет «Code Quality» в запросе на слияние (нативно); отражает серьёзность SCA-находок |
| Находки анализа зависимостей (SCA) | Отчёт об уязвимостях; те же находки также отображаются в виджете «Code Quality» и на вкладке «Tests» |
| SBOM (состав зависимостей) | Страница «Dependency list» по адресу `/-/security/dependencies` |
| Лицензии | Страница «License compliance» по адресу `/-/security/licenses` |
| SARIF | Загружается артефактом (отдельного SAST-виджета в FOSS нет) |

Находки также передаются в DefectDojo, если эта интеграция настроена.

Страницы «Dependency list» и «License compliance» читают SBOM в формате CycloneDX, который загружает сканирование; если в одном пайплайне работает несколько анализаторов, обе страницы показывают объединение SBOM всех анализаторов.

{% alert level="info" %}
Страницы «Dependency list» и «License compliance» — это FE-реализация Deckhouse Code. В GitLab FOSS соответствующие виджеты доступны только в EE. Обе страницы отображаются в разделе «Secure» бокового меню проекта (если для проекта включены функции compliance) и также открываются по прямому URL-адресу.
{% endalert %}

## Политики и блокировка

Задача `codescoring_scan` **приводит к сбою пайплайна**, если есть находка с серьёзностью не ниже порога `FE_SECURITY_FAIL_ON` (по умолчанию `high`) — гейт по серьёзности. Политика исполнения сканирования добавляет ещё два необязательных условия остановки: «Прерывать задачу при отклонённом компоненте» (когда OSA отклоняет компонент) и «Прерывать при пустом результате» (когда сканирование не разрешило ни одного компонента). Отчёты при этом всё равно загружаются (в том числе на упавших попытках — `artifacts:when: always`), поэтому находки не теряются.

Разбор и настройка политик (пороги серьёзности, игнорирование срабатываний) выполняются на стороне платформы CodeScoring.

## Разбор уязвимостей

Обнаруженные уязвимости можно разбирать непосредственно в интерфейсе CodeScoring. Для этого:

1. Перейдите в раздел «SCA» → «Уязвимости».
1. Выберите статус: `Активен`, `Подтверждён`, `Не затронут` или `Ложноположительный`.
1. Заполните обоснование и ответ, совместимые с форматом CycloneDX Vulnerability Exploitability eXchange (VEX).

Можно настроить временное игнорирование срабатываний — по проекту, технологии, пакету, лицензии или CVE.

{% alert level="warning" %}
На текущем этапе агент CodeScoring не заполняет поле `severity` в исходном артефакте «Dependency Scanning Report»; серьёзность присутствует в отчётах «Code Quality» и «Tests», где шаблон сканирования её нормализует. Из-за этого серьёзность может отсутствовать в инструментах, которые читают артефакт анализа зависимостей напрямую.
{% endalert %}

## Устранение неполадок

### Сканирование не запускается

Проверьте следующее:

- интеграция CodeScoring активна в настройках проекта (заданы URL-адрес и токен);
- проект политик привязан к проекту и в нём задано действие `- scan: codescoring`;
- в пайплайне присутствует задача `codescoring_scan` и доступен GitLab Runner с executor `docker`.

### Результаты не появляются на страницах Dependency list, License compliance

Проверьте следующее:

- задача `codescoring_scan` завершилась и загрузила артефакты `gl-dependency-scanning-report.json` и `gl-sbom.cdx.json` (артефакты собираются при `when: always`);
- открывается страница ветки по умолчанию (страницы читают отчёт последнего пайплайна).

### Виджет Code Quality не отображается в запросе на слияние

Проверьте, что после выполнения задачи был сформирован `gl-code-quality-report.json` и объявлен в секции `artifacts:reports:codequality`.
