# Site Header: islandKit

The header is rendered by the `site-header` component from the `@web/islandkit` package, and its appearance is defined by
the `@web/deckhouse-islands` package, which is shared with the WordPress site. Both are located in
the private fox package registry (the `web/npm-components` project). This is a **content**
island: its markup must be included in the server response, so it isn’t
assembled by a script after loading, but is rendered in advance—by the same Vue component that
later runs in the browser—via Vue server-side rendering.

One header per product and language, just like this site is structured: fragments are published in
`{ru,en}/includes/header*.html`, and nginx inserts them via SSI into the
documentation pages and module pages on Hugo.

## How This Gets Included in the Build

The `islandkit-artifact` stage (`../../werf-islandkit.inc.yaml`) installs both packages
using the specified versions, runs `render-header.mjs`, and passes four items
to the site build: fragments, their index, the bundle, and the Sass styles. The import is defined in
`../../werf-web-frontend.inc.yaml`, with no environment conditions—the header is needed in
every build.

Therefore, these paths are not stored in the repository: `_includes/_generated/`,
`assets/islandkit/`, `_data/islandkit_header.json`, and `_sass/deckhouse-islands/`
are listed in `.gitignore`. The only generated files in the repository are the
islandKit snapshot in `snapshot/`, see "Build without a token" below.

The registry is private. In the pipeline, the stage retrieves the job’s `CI_JOB_TOKEN` (the
`deckhouse/deckhouse` project is included in the registry project’s access list); the token is provided
as a Werf secret and does not enter the layer (`.werf/defines/npm-private-registry.tmpl`).
Locally, a shared registry token is required in `FOX_NPM_TOKEN`: the project’s
`npm-components` with the `read_package_registry` scope (read-only; the value is held by
the project maintainers). The Makefile passes it to Werf as `CI_JOB_TOKEN`.

The menu is fetched from the same source as Jekyll: in production environments, via an import from
`site-external-artifacts` (data from the API), otherwise from `_data/topnav*.json`
in the repository. Without this import, the header would remain frozen on a copy of the menu from the repository
while the rest of the site is being updated.

### Update the library version

1. Increase `islandkit` in `versions.json`—both
   packages have the same version number;
2. Rebuild. Everything else—the bundle URL in `head-site.html`, the list
   of products in the template—is read from `_data/islandkit_header.json`, which
   is generated by the same stage;
3. Update the snapshot with `make islandkit-snapshot` and commit it in the same
   change. A pipeline build of the site checks that the snapshot is of the
   pinned version (`../../werf-islandkit.inc.yaml`) and fails otherwise; local
   builds are not checked, so a version can be tried out first.

`vue` is specified separately there and must remain within the
`peerDependencies` of the library.

### Build without a token

A build with `DOCS_ISLANDKIT_SNAPSHOT=1` does not go to the registry: the stage runs
`use-snapshot.sh`, which puts the files from `snapshot/` where a fresh render would
be. The Makefiles set the variable when there is no token, so a page can be edited
and built with a header that may be older than the pinned one. Pipelines never set it.

`snapshot.mjs` (`make islandkit-snapshot`) writes the snapshot: it installs the pinned
packages into a temporary directory, renders the site fragments and the module
fragments of every edition from `editions.yaml`, copies the bundle, and compiles
`../../_sass/components/_islandkit-package.scss`. The Sass of the styles package is
private, so the snapshot has its compiled CSS and empty mixins with the same names
instead. That is why only this file may include the mixins of the package.

## Where Everything Is Located

| Path | What It Is |
| --- | --- |
| `render-header.mjs` | renders fragments, copies the bundle and Sass styles |
| `versions.json` | the pinned versions of the packages, read by the stage and by `snapshot.mjs` |
| `snapshot.mjs` | writes the islandKit snapshot |
| `use-snapshot.sh` | puts the snapshot in place of a fresh render in a build without a token |
| `snapshot/` | the islandKit snapshot: fragments, their indexes, the bundle, compiled styles |
| `../../_sass/components/_islandkit-package.scss` | includes the mixins of the `@web/deckhouse-islands` package with the scopes of this site |
| `../../_data/header-products.json` | “Products” mega menu by language—data that used to be hard-coded into templates |
| `../../_data/header-solutions.json` | "Solutions" for the Russian header: caption and cards. This item is in the second row of the Deckhouse Platform, after "Extensions": the `/solutions/` item from the menu bar retrieves these cards, and without it, the item itself is inserted |
| `../../images/header/` | the Russian header’s text logo, product icons, and second-row locaps |
| `../../_sass/components/_islandkit-header.scss` | integrates styling from the `@web/deckhouse-islands` package (WordPress design) with this site’s sections: English — `.header` without `.header--ik-ru`, Russian — `.header--ik-ru`. The documentation section has its own Russian header frame and section tree in the collapsed card |
| `../../_includes/header.html` | entry point for English pages: selects the product-specific snippet |
| `../../_includes/header_ru.html` | entry point for Russian pages |
| `../../assets/js/islandkit-doc-tree.js` | places the section page tree in the collapsed card of the second row (RU) |

**The Russian header is the second design for the same island.** It differs in data and
variable values, not in markup:
- the layout changes to 1200 — `breakpoint: 'xl'` in the data;
- it has its own products and “Solutions”;
- the product in the second row is rendered as a lockup (`lockup`);
- the sheet is structured as an accordion (`data-ik-sheet="accordion"`);
- there are no social media links.

The product codes, which the Russian row displays under different names
(`kubernetes-platform`, `development-platform`), are consolidated by `render-header.mjs`, just as
the previous second-row template did.

Generated files (not stored in Git): `../../_includes/_generated/`,
`../../_data/islandkit_header.json`, `../../assets/islandkit/<version>/`,
`../../_sass/deckhouse-islands/`.

## Regenerate Locally

This is rarely necessary—usually, a rebuild is enough. But if you want to take a look
at the code snippets:

```bash
npm install --no-save @web/islandkit@<version> @web/deckhouse-islands@<version> vue@3 @vue/server-renderer@3
node _tools/islandkit/render-header.mjs
```

For an unpublished library build:

```bash
node _tools/islandkit/render-header.mjs --islandkit <npm-components checkout>/packages/islandkit
```

The styling is then taken from `packages/deckhouse-islands` nearby; another option is
`--styles <package directory>`.

This flag means “package taken from the working copy,” and the asset directory is then given
the `-dev` suffix: a build from the working tree should not occupy the URL
of a published version with the same number—that’s why the path is immutable.

There is also `--site <path>` if you run the script from outside this tree.

## Building Within the Cluster

The documentation within the cluster (`site.mode == module`, module
`810-documentation`) is a separate site on the same island. It has its own menu—
`modules/810-documentation/images/web/documentation/_data/topnav.yml`—with links
prefixed by the language; some items are specific to certain editions; there are no products,
buttons, or a second row. Only the English header includes a language link and a GitHub link, and
these are not present in the CSE.

It is rendered by the same stage in `module` mode: the same `../../werf-islandkit.inc.yaml`,
linked from `modules/810-documentation/images/web/werf.inc.yaml`; when
`ModuleName == "documentation"`, it builds the `documentation/web/islandkit-artifact` image:

```bash
node _tools/islandkit/render-header.mjs --mode module --menu module-menu/topnav.yml --edition <edition>
```

This produces `_includes/_generated/header-module-{en,ru}.html` files corresponding to the build edition.
Both static builds of the cluster (`werf-documentation-static` and
`werf-modules-static`) import them into `site/` before copying the common
includes over `documentation/`. `header.html` and `header_ru.html` in this
mode include the module fragment. Hugo module documentation pages retrieve the header via SSI from
the same placeholders in `pages/includes/header*.html`, so they do not
require separate editing.

Both builds share the same version pins—`versions.json`. To parse YAML, module mode additionally
installs `js-yaml`.
