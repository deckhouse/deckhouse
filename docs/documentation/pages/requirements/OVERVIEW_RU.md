На странице описаны требования к узлам кластера и окружению, которые нужно выполнить до начала установки Deckhouse Platform.

Перед началом установки проверьте следующее:

- Выбран [вариант размещения](#варианты-размещения): сколько узлов будет в кластере, как между ними распределены роли и выдержит ли кластер отказ узла.
- Для узлов выделены CPU, память и диски по [таблицам](#требования-к-ресурсам) для выбранного варианта размещения и типа нагрузки: [запуск контейнеров](#containers), [запуск виртуальных машин](#virtual-machines) или [комбинированная нагрузка](#combined).
- Для узлов выделены быстрые диски (400+ IOPS), а разметка дисков соответствует [рекомендациям по разметке и объёму дисков](../guides/fs-requirements.html).
- Узлы соответствуют [требованиям к узлам](#требования-к-узлам): архитектура процессора, операционная система, версия ядра и установленное ПО.
- При [установке в существующий кластер](../glossary.html#existing-cluster-mode) Kubernetes его версия входит в [список поддерживаемых версий Kubernetes](../reference/supported_versions.html#kubernetes), а ОС узлов — в [список поддерживаемых ОС](../reference/supported_versions.html#linux).
- Сеть между узлами соответствует [требованиям к сети](#требования-к-сети): у узлов постоянные IP-адреса, открыты нужные порты, задержки между [master-узлами](../glossary.html#master-node) в допустимых пределах, подготовлен домен для веб-интерфейсов платформы.
- Если в кластере будут работать виртуальные машины, узлы и инфраструктура соответствуют [требованиям для запуска виртуальных машин](#требования-для-запуска-виртуальных-машин).
- Есть [доступ к инфраструктуре](#доступ-к-инфраструктуре): к хранилищу образов контейнеров, к узлам по SSH или к API [облачного провайдера](../glossary.html#cloud-provider), а хост [установщика](../glossary.html#installer) готов к запуску установки.

## Варианты размещения

[Вариант размещения](../glossary.html#deployment-scenario) определяет, сколько узлов будет в кластере, как между ними распределены роли и выдержит ли кластер отказ узла.

В кластере могут быть узлы следующих типов:

- **[Master-узлы](../glossary.html#master-node)** — узлы, на которых работают компоненты [control plane](../glossary.html#control-plane) и которые управляют кластером.
- **[Worker-узлы](../glossary.html#worker-node)** — узлы для пользовательской нагрузки: приложений в контейнерах и виртуальных машин.
- **[Системные узлы](../glossary.html#system-node)** — узлы для модулей Deckhouse Platform.
- **[Frontend-узлы](../glossary.html#frontend-node)** — узлы, которые балансируют входящий трафик. На них работают [Ingress-контроллеры](../glossary.html#ingress-controller).
- **[Узлы мониторинга](../glossary.html#monitoring-node)** — узлы для Prometheus, Grafana и других компонентов мониторинга.

Подробнее о настройке узлов каждого типа — [в разделе «Особенности конфигурации»](../guides/production.html#особенности-конфигурации) руководства «Подготовка к production».

Примеры вариантов размещения:

- **[Одноузловой кластер](../glossary.html#single-node-cluster)** (Single Node / Edge). Один узел выполняет все роли: на нём работают control plane, модули Deckhouse Platform и пользовательская нагрузка. Вариант подходит для ознакомления с платформой, тестовых окружений и edge-сценариев.

  {% alert level="warning" %}
  Одноузловой кластер не отказоустойчив. Не используйте его в production-окружениях.
  {% endalert %}

- **[Кластер с одним master-узлом](../glossary.html#single-master)**. Кластером управляет один master-узел, пользовательская нагрузка работает на одном или нескольких worker-узлах. Часть компонентов Deckhouse Platform также работает на worker-узлах. Вариант подходит для небольших проектов с невысокой нагрузкой. Кластер не отказоустойчив: при выходе из строя master-узла пострадает весь кластер.
- **Отказоустойчивый (HA) кластер с тремя master-узлами**. Control plane распределён по трём master-узлам и продолжает работать при отказе одного из них: два оставшихся узла сохраняют [кворум](../glossary.html#quorum). Пользовательская нагрузка может работать на master-узлах или на выделенных worker-узлах. Это рекомендуемый вариант для production-окружений. Для обеспечения высокой доступности в условиях ограниченных ресурсов вместо одного из master-узлов можно использовать [arbiter-узел](../admin/configuration/high-reliability-and-availability/enable.html#настройка-режима-ha-c-двумя-master-узлами-и-arbiter-узлом).
- **Кластер с разделением ролей узлов**. Control plane работает на трёх выделенных master-узлах, модули Deckhouse Platform — на системных узлах, Ingress-контроллеры — на frontend-узлах. Пользовательская нагрузка работает только на worker-узлах и изолирована от [системных компонентов](../glossary.html#system-component). В нагруженных кластерах с большим объёмом метрик компоненты мониторинга выносятся на выделенные узлы мониторинга, без них они работают на системных узлах. Вариант подходит для крупных и нагруженных кластеров.

Требования к ресурсам узлов для таких вариантов приведены в разделе [«Требования к ресурсам»](#требования-к-ресурсам).

## Требования к ресурсам

Требования к ресурсам зависят от [варианта размещения](#варианты-размещения) и от выбранного решения для инфраструктурных задач (запуск контейнеров, виртуальных машин, либо контейнеров и виртуальных машин).

{% alert level="info" %}
Приведённые ниже требования указаны в расчёте на один узел и учитывают только нагрузку системных компонентов. Ресурсы для пользовательской нагрузки необходимо учитывать дополнительно.
{% endalert %}

При подборе ресурсов учитывайте следующее:

- Значения рассчитаны для установки с [набором модулей](../admin/configuration/#наборы-модулей) `Default`.
- Значения в столбце «Диск, ГБ» учитывают 100 ГБ под системные PVC (модулей `prometheus`, `upmeter` и других) на локальном диске узла. Если системные PVC размещаются во [внешнем хранилище](../glossary.html#external-storage), этот объём на узле не нужен.
- На каждом [worker-узле](../glossary.html#worker-node) под системные сервисы (`kubelet`) и системные поды зарезервируйте не менее 1 CPU и 2 ГБ памяти.
- Для всех узлов используйте быстрые диски с производительностью не менее 400 IOPS.
- Для [arbiter-узла](../glossary.html#arbiter-node) в HA-кластере с двумя master-узлами нужно не менее 2 CPU, 4 ГБ памяти и 8 ГБ диска под etcd. Подробнее — в разделе [«Настройка режима HA c двумя master-узлами и arbiter-узлом»](../admin/configuration/high-reliability-and-availability/enable.html#настройка-режима-ha-c-двумя-master-узлами-и-arbiter-узлом).

## Требования к узлам

Серверы (ВМ) для узлов кластера должны соответствовать следующим требованиям.

Аппаратные характеристики:

- **Архитектура процессора** — на всех узлах `x86_64`.
- **Однотипные узлы** — все узлы одного типа имеют одинаковую конфигурацию: одной марки и модели, с одинаковыми процессором, памятью и хранилищем.
- **Сетевые интерфейсы** — у каждого узла есть хотя бы один сетевой интерфейс для маршрутизируемой сети.

Операционная система и ПО:

- Установлена ОС [из списка поддерживаемых](../reference/supported_versions.html#linux) или совместимая с ним.
- Ядро Linux версии 5.8 или новее.
- Установлен один из пакетных менеджеров: `apt`, `apt-get`, `yum` или `rpm`. В случае с РЕД ОС установлены `yum` и `which` (по умолчанию могут отсутствовать).
- Есть доступ к стандартным системным репозиториям для установки зависимостей.
- Доступны Python и команда `sudo`: они нужны установщику.
- Имя хоста уникально в пределах кластера и соответствует требованиям Kubernetes: не более 63 символов, только строчные буквы, дефис и точка допускаются, но не в начале и не в конце имени.
- Узел разрешает собственное имя хоста, а имя `localhost` разрешается в адрес `127.0.0.1`.
- Системное время корректно.
- На узле нет собственного container runtime (например, containerd или Docker) и компонентов Kubernetes.
- Локальные пользователь и группа `deckhouse` отсутствуют либо имеют UID и GID `64535`, а пользователь не имеет прав `sudo`. Подробнее — в разделе [«Локальная служебная учетная запись deckhouse»](../installing/#локальная-служебная-учетная-запись-deckhouse).
- **В случае использования `ContainerdV2`** в качестве container runtime по умолчанию на узлах кластера:
  - поддержка `CgroupsV2`;
  - systemd версии `244` или новее;
  - поддержка модуля ядра `erofs`;
  - версия ядра Linux не входит в диапазоны 6.12.0–6.12.28 и 6.14.0–6.14.6 (эти версии подвержены уязвимости CVE-2025-37999 в EROFS).

Установщик проверяет эти требования перед началом установки. Полный список проверок приведён в разделе [«Проверки перед началом установки»](../installing/#проверки-перед-началом-установки).

Если на узлах действуют политики безопасности или работают сканеры безопасности, учтите [параметры sysctl](../reference/sysctl.html), которые платформа задаёт на узлах, и [используемые платформой директории](../reference/used_directories.html).

## Требования к сети

Между узлами кластера должны выполняться следующие требования:

- Узлы доступны друг другу по сети. Требований к MTU нет.
- У каждого узла постоянный IP-адрес. Если адреса выдаёт DHCP-сервер, настройте в нём соответствие адресов узлам. Смена IP-адреса узла нежелательна.
- Master-узлы имеют доступ к внешним источникам времени по NTP. Остальные узлы синхронизируют время с master-узлами, но могут использовать и другие серверы времени (параметр [`ntpServers`](/modules/chrony/configuration.html#parameters-ntpservers)).
- Если в инфраструктуре есть ограничения сетевого взаимодействия, между узлами открыты порты из таблиц раздела [«Сетевое взаимодействие компонентов платформы»](../reference/network_interaction.html).
- Сумма круговой задержки (RTT) и джиттера между серверами для master-узлов и [arbiter-узлов](../glossary.html#arbiter-node) не превышает 100 мс, при планировании кластера — 50 мс. Подробнее — в разделе [«Требования к сетевым задержкам между master-узлами»](../reference/network_interaction.html#требования-к-сетевым-задержкам-между-master-узлами).
- Подготовлен домен для веб-интерфейсов платформы, который задаётся в [шаблоне DNS-имён](../glossary.html#public-domain-template): wildcard-запись, указывающая на [Ingress-контроллер](../glossary.html#ingress-controller), либо A- или CNAME-запись для каждого имени из [списка зарезервированных DNS-имён](../reference/public-domains.html).

## Требования для запуска виртуальных машин

{% alert level="warning" %}
Узлы, на которых работают виртуальные машины, должны быть физическими серверами (bare metal). Установка на виртуальные машины допустима только в демонстрационных целях, требует включённой вложенной виртуализации (nested virtualization) и не покрывается технической поддержкой.
{% endalert %}

К узлам и инфраструктуре для запуска ВМ предъявляются дополнительные требования. Учтите их при планировании кластера, так как некоторые настройки нельзя изменить после установки:

- Процессор с поддержкой инструкций Intel-VT (VMX) или AMD-V (SVM), а сама аппаратная виртуализация должна быть включена в настройках BIOS/UEFI.
- Одна версия ядра Linux на всех узлах кластера.
- Для узлов на базе Astra Linux требуется Astra Linux версии не ниже 1.8.3: в более ранних версиях есть ошибка, мешающая работе виртуализации.
- Одно или несколько [поддерживаемых хранилищ](../admin/configuration/storage/) в кластере. Задайте также [StorageClass по умолчанию](../admin/configuration/storage/supported-storage.html#назначение-storageclass-по-умолчанию).
- Подсети, из которых ВМ будут получать IP-адреса (указываются в параметре [`virtualMachineCIDRs`](/modules/virtualization/configuration.html#parameters-virtualmachinecidrs)) не должны пересекаться с адресным пространством подов ([`podSubnetCIDR`](/modules/control-plane-manager/configuration.html#parameters-network-podsubnetcidr)) и сервисов ([`serviceSubnetCIDR`](/modules/control-plane-manager/configuration.html#parameters-network-servicesubnetcidr)).

Кластер с виртуализацией рассчитан на работу до `1000` узлов и до `50000` виртуальных машин.

## Доступ к инфраструктуре

Для установки нужен следующий доступ:

- Доступ к хранилищу образов контейнеров Deckhouse Platform: публичному (`registry.deckhouse.ru` или `registry.deckhouse.io`) или его зеркалу.
- При установке на bare metal (в том числе гибридного кластера) и в неподдерживаемые облака — доступ к узлам по SSH по ключу.
- При установке [гибридного кластера](../glossary.html#hybrid-cluster) — сетевая связность между площадками по [общим сетевым требованиям к гибридным кластерам](../admin/integrations/hybrid/overview.html#общие-сетевые-требования).
- При установке в поддерживаемые облака — квоты на создание ресурсов и параметры доступа к облачной инфраструктуре. Они зависят от провайдера и описаны в разделе [«Интеграция с инфраструктурой»](../admin/integrations/integrations-overview.html).
- При [установке в существующий кластер](../glossary.html#existing-cluster-mode) Kubernetes — доступ к Kubernetes API кластера с хоста установщика с правами администратора (kubeconfig). Установка непосредственно с [master-узла](../glossary.html#master-node) не поддерживается.
- На хосте, с которого запускается [установщик](../glossary.html#installer), — container runtime для запуска контейнера установщика, доступ к хранилищу образов и сетевой доступ к серверу master-узла по порту `22/TCP`.

Требования к [bastion-хосту](../glossary.html#bastion-host) и хранилищу образов в [закрытом окружении](../glossary.html#private-environment) приведены в руководстве [«Установка Deckhouse Platform в закрытом окружении»](../guides/private-environment.html).
