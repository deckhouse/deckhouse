В Kubernetes команда `kubectl get <resource> -A` требует кластерных
прав на операцию `list`. Если кластерных прав нет, kube-apiserver возвращает ошибку `403 Forbidden`,
даже если пользователю по отдельности доступны десятки неймспейсов.

Deckhouse Platform (DP) расширяет возможности kube-apiserver: пользователь без кластерных прав может явно
запросить ответ, отфильтрованный в соответствии с его фактическими правами доступа, вместо получения отказа в доступе.

Механизм является полностью опциональным.
Если клиент не запрашивает фильтрацию, поведение остаётся идентичным поведению Kubernetes.

## Использование через ⁠Deckhouse CLI

В DP для работы с механизмом листинга с фильтрацией используется  [утилита ⁠Deckhouse CLI](../../../../cli/d8/).

### Области фильтрации ресурсов

С помощью флага `--scope` вы можете определить, из каких неймспейсов будут возвращаться ресурсы.

| Значение | Что возвращается |
|---|---|
| `accessible` | Объекты из всех неймспейсов, где RBAC пользователя разрешает данную операцию над данным ресурсом |
| `projects` | Объекты из неймспейсов, принадлежащих любому [проекту](/modules/multitenancy-manager/cr.html#project), то есть неймспейсов с непустым значением лейбла `projects.deckhouse.io/project` |
| `project:<имя>` | Объекты из неймспейсов конкретного проекта. Имя должно быть допустимым именем проекта |
| `system` | Объекты только из системных неймспейсов: `default` и неймспейсы с именами, начинающимися на `d8-` или `kube-`. Это фиксированный список неймспейсов, определяемый по их именам и не зависящий от проектов. Остальные неймспейсы, не принадлежащие проектам и не входящие в список системных, не возвращаются при установке области `system` или `projects` |

Области `projects` и `project:<имя>` работают только при включённом [модуле `multitenancy-manager`](/modules/multitenancy-manager/).
Если модуль выключен, запросы с этими областями отклоняются с ошибкой `400 Bad Request`.

### Примеры использования

Используйте флаг `--scope` в команде `d8 k get` вместе с флагом `-A` (или `--all-namespaces`).

Получение объектов из всех неймспейсов, доступных пользователю:

```shell
d8 k get pods -A --scope=accessible
```

Получение объектов только из неймспейсов проектов:

```shell
d8 k get pods -A --scope=projects
```

Получение объектов указанного проекта:

```shell
d8 k get pods -A --scope=project:my-project
```

Механизм работает и для кастомных ресурсов:

```shell
d8 k get configauditreports -A --scope=accessible
```

Фильтрация также применяется к watch-запросам:

```shell
d8 k get pods -A --scope=accessible -w
```

Особенности работы:

- Использование флага `--scope` без флага `-A` отклоняется с ошибкой, поскольку фильтровать листинг в одном неймспейсе бессмысленно.
- Если команда `d8 k get <resource> -A` без указания `--scope` завершается ошибкой `403 Forbidden`, ⁠Deckhouse CLI подсказывает подходящие варианты использования флага.
- Для значений флага `--scope` работает автоматическое дополнение в командной оболочке (shell completion), включая имена существующих проектов (`--scope=project:<TAB>`).

## Использование из собственного кода (HTTP API)

CLI является лишь транспортным механизмом. Фильтрацию включают два HTTP-заголовка запроса к
kube-apiserver. Чтобы использовать механизм из собственного сервиса, скрипта или
любого другого клиента, передавайте заголовки самостоятельно.

| Заголовок | Значение | Когда обязателен |
|---|---|---|
| `X-Deckhouse-Scope` | `accessible` \| `projects` \| `system` \| `project` | Всегда (включает механизм) |
| `X-Deckhouse-Project` | Имя проекта | Только при использовании `X-Deckhouse-Scope: project` |

Заголовки применяются только к операциям чтения (`list`, `get`, `watch`) для namespaced-ресурсов без субресурсов, выполняемым через cluster-scoped URL-адрес (то есть по пути без
`namespaces/<имя>`, который формируется при использовании флага `-A`).

Во всех остальных случаях
(мутирующие запросы, обращения к субресурсам и cluster-scoped-ресурсам) заголовки игнорируются.

Пример получения списка подов, доступных сервисному аккаунту:

```shell
curl -H "Authorization: Bearer $TOKEN" \
     -H "X-Deckhouse-Scope: accessible" \
     https://<kube-apiserver>/api/v1/pods
```

Пример получения списка объектов Deployment одного проекта:

```shell
curl -H "Authorization: Bearer $TOKEN" \
     -H "X-Deckhouse-Scope: project" \
     -H "X-Deckhouse-Project: my-project" \
     https://<kube-apiserver>/apis/apps/v1/deployments
```

Семантика ответов:

| Ситуация | Ответ |
|---|---|
| Заголовки отсутствуют | Стандартное поведение Kubernetes (ошибка `403 Forbidden` для пользователя без необходимых прав) |
| Заголовок присутствует, но RBAC отклонил запрос | Ответ `200 OK` со списком объектов из доступных неймспейсов (список может быть пустым) |
| Заголовок присутствует, и у пользователя есть кластерные права | Ответ `200 OK`. Фильтрация применяется только по классификации неймспейсов (например, `system` оставляет только неймспейсы `default`, `d8-*` и `kube-*`) |
| Некорректное значение заголовка: неизвестная область, `X-Deckhouse-Project` без `X-Deckhouse-Scope: project` или недопустимое имя проекта | Ошибка `400 Bad Request` для любого пользователя, до проверки прав |
| Область `projects` или `project` при выключенном модуле `multitenancy-manager` | Ошибка `400 Bad Request` |
| `get` объекта вне итогового множества неймспейсов | Ошибка `404 Not Found`, как для несуществующего объекта |
| RBAC отклонил запрос, и сервис `permission-browser` сейчас не может ответить: не отвечает вовремя, перегружен или недоступен | Ошибка `503 Service Unavailable` с заголовком `Retry-After`; объекты не возвращаются |
| RBAC отклонил запрос, и границу доступа нельзя вычислить по другой причине | Ошибка `403 Forbidden` (fail-closed) |

При использовании client-go добавляйте заголовки через `rest.Config.WrapTransport`.

## Принцип работы

1. **Фильтр авторизации kube-apiserver.**

   Если RBAC отклоняет запрос, фильтр
   вместо немедленного возврата ошибки `403 Forbidden` проверяет три условия:

   - выполняется операция чтения (`list`, `get` или `watch`);
   - запрос направлен к основному ресурсу, а не субресурсу;
   - для данного ресурса зарегистрирован фильтрующий
   декоратор и присутствует заголовок.

   Только при выполнении всех трёх условий запрос передаётся дальше с пометкой о необходимости фильтрации на уровне хранилища.

1. **Слой хранилища** вычисляет итоговое множество неймспейсов как
   пересечение двух независимых наборов:

   - **Классификация** — какие неймспейсы соответствуют значению
     `--scope`. Определяется лейблом `projects.deckhouse.io/project`,
     которым [модуль `multitenancy-manager`](/modules/multitenancy-manager/) помечает неймспейсы проектов.
     Резолвится прямым запросом к kube-apiserver и не зависит от пользователя.
   - **Граница доступа** (в коде механизма — RBAC floor) — какие неймспейсы
     пользователю реально доступны для *данного ресурса и данной операции*.
     Вычисляется одним запросом `SelfScopedAccessReview` к API `authorization.deckhouse.io`
     ([модуль `user-authz`](/modules/user-authz/)) по конкретным ресурсу, субресурсу и операции, тем же ответом,
     по которому веб-интерфейс решает, что показывать. Применяется всегда, когда RBAC
     отклонил запрос.

   В ответ попадают только объекты из неймспейсов итогового множества.

1. **Watch** (`-w`) — отдаёт отфильтрованный поток и, если множество доступных
   неймспейсов меняется «на лету» (например, пользователю выдали или отозвали права или неймспейс
   был перенесён в другой проект), синтезирует события `ADDED`/`DELETED` для затронутых
   объектов без повторного подключения клиента.

   Множество обновляется раз в секунду. Синтезированное событие `DELETED` несёт последний `resourceVersion` потока.
   Если обновить множество не удаётся (например, сервис `permission-browser` не отвечает), поток до 60 секунд работает с прежним множеством, затем отправляет ошибку и закрывается.
   Клиент переподключается и получает ошибку `503 Service Unavailable`, пока сервис `permission-browser` не может ответить, или ошибку `403 Forbidden`, пока множество нельзя вычислить по другой причине.
   Если модуль `multitenancy-manager` выключают, пока открыт watch-запрос с областью `projects` или `project`, поток сразу отправляет ошибку `400 Bad Request` и закрывается.
   Если сервис `permission-browser` отвечает, что теперь пользователю разрешён запрос во всём кластере, поток отправляет ошибку `410 Gone` и закрывается, а клиент заново запрашивает список.

Механизм поддерживает все встроенные namespaced-ресурсы Kubernetes, а также namespaced-ресурсы, определённые через CRD.

## Модель безопасности

- **Без заголовков используется стандартное поведение Kubernetes.**
  Контроллеры и операторы, полагающиеся на ошибку `403 Forbidden` как сигнал, продолжают работать без изменений.
- **Заголовки не расширяют права доступа.**
  Граница доступа вычисляется на сервере на основании идентичности пользователя, выполнившего запрос.
  Даже при ручной подстановке заголовков пользователь не сможет получить доступ к объектам, запрещённым его RBAC-правами.
  Проверка выполняется отдельно для каждой пары
  (`resource`, `verb`). Таким образом, например, наличие права `get secrets` в неймспейсе не предоставляет доступ к подам в нём.
- **Используется модель fail-closed.** Если API `authorization.deckhouse.io` не обслуживается
  (например, если модуль `user-authz` выключен или сервис `permission-browser` во время обновления ещё не
  обслуживает `SelfScopedAccessReview`), границу доступа вычислить нельзя — отклонённый пользователь получает
  стандартный ответ `403 Forbidden`. Тот же ответ возвращается, если `permission-browser` разрешает операцию во всём
  кластере, а kube-apiserver её отклонил: механизм никогда не отвечает списком всех неймспейсов.
  Если сервис `permission-browser` сейчас не может ответить (не отвечает вовремя, возвращает `429 Too Many Requests`
  или ошибку `5xx` либо недоступен), запрос с областью получает вместо этого ошибку `503 Service Unavailable` с заголовком
  `Retry-After`: доступ не запрещён, а неизвестен, и клиент может повторить запрос. Ни один из этих ответов не возвращает объекты.
- **Неразличимость отказа.** Запросы вида `project:<чужой>` и
  `project:<несуществующий>` дают одинаковый пустой ответ — существование
  проектов не раскрывается.

## Особый случай: namespaces

Для ресурса `namespaces` фильтрация применяется безусловно, независимо от использования флагов и заголовков.
Команда `d8 k get namespaces` возвращает пользователю только
доступные ему неймспейсы вместо ошибки `403 Forbidden`. Фильтрация произвольных
ресурсов через `--scope` является обобщением этого механизма, которое включается явно.

Если включён модуль `console` версии ниже 1.44.0, список неймспейсов не фильтруется: уровни доступа ClusterAuthorizationRule и AuthorizationRule и namespace-роли сохраняют право получать список всех неймспейсов.

Тот же список отдаёт read-only ресурс accessiblenamespaces — его может запросить любой аутентифицированный пользователь для самого себя:

```bash
d8 k get accessiblenamespaces
```

Это удобно для скриптов и интерфейсов: не нужно перебирать неймспейсы и проверять доступ к каждому.

## Особый случай: projects

Ресурс `Project` — кластерный, но его видимость определяется той же границей по
неймспейсам: пользователь видит проект, если ему доступен любой из его
неймспейсов — основной или дополнительный. Неймспейс принадлежит проекту, только
если у него есть лейбл `projects.deckhouse.io/project` с непустым значением;
по имени неймспейса проект не определяется. Неймспейс без этого лейбла показывает виртуальный
проект, к которому его относит `multitenancy-manager`: `deckhouse` для `d8-*`, `kube-*`, `upmeter-*`
и неймспейсов с лейблом `heritage: deckhouse` или `heritage: upmeter`, `default` для остальных.
Пользователь, которому разрешён `list` неймспейсов во всём кластере, видит все
проекты, включая оба виртуальных. Фильтрация здесь тоже применяется
безусловно: `d8 k get projects` возвращает доступное подмножество вместо ошибки
`403 Forbidden`, а `get` недоступного для пользователя проекта отвечает `NotFound`.

Поэтому уровни доступа, выданные через `ClusterAuthorizationRule`, больше не
включают чтение `projects` на уровне кластера: такое разрешение позволило бы
RBAC разрешить запрос раньше, чем сработает фильтр. В результате
`d8 k auth can-i list projects` отвечает `no`, хотя сам список работает и
возвращает проекты пользователя. На изменение проектов это не влияет.

## Мониторинг

kube-apiserver экспортирует метрики механизма:

| Метрика | Значение |
|---|---|
| `apiserver_scopefilter_allowed_set_failures_total` | Запросы, получившие ошибку, потому что границу доступа не удалось вычислить, с лейблом `operation` (`list`, `get`, `watch`) и лейблом `reason`: `unavailable` (сервис `permission-browser` сейчас не может ответить, запрос получил ошибку `503 Service Unavailable`) или `denied` (любой другой сбой, запрос получил ошибку `403 Forbidden`) |
| `apiserver_scopefilter_cluster_disagreements_total` | Запросы, которые kube-apiserver отклонил, а `permission-browser` разрешил во всём кластере; они получают ошибку `403 Forbidden` |
| `apiserver_scopefilter_watch_refresh_failures_total` | Неудачные обновления множества неймспейсов открытого watch-запроса, включая тайм-ауты |
| `apiserver_scopefilter_watch_closed_total` | Watch-запросы, закрытые механизмом, с лейблом `reason`: `refresh_failures` (множество не обновлялось 60 секунд), `overflow` (клиент не успевал читать события), `multitenancy_disabled` (области `projects` и `project` больше не обслуживаются) или `access_changed` (пользователю теперь разрешён запрос во всём кластере) |

## Задействованные компоненты

| Компонент | Роль |
|---|---|
| [Deckhouse CLI](../../../../cli/d8/) | Поддержка флага `--scope` и преобразование его значений в заголовки |
| kube-apiserver (патч DP) | Перехват `403 Forbidden` и фильтрация на слое хранилища |
| Модуль [`user-authz`](/modules/user-authz/) (`permission-browser`) | Определение границы доступа через `SelfScopedAccessReview` |
| Модуль [`multitenancy-manager`](/modules/multitenancy-manager/) | Классификация неймспейсов по лейблу `projects.deckhouse.io/project` |
| Модуль [`user-authz`](/modules/user-authz/) (ConfigMap `d8-user-authz-multitenancy-state`) | Сообщает kube-apiserver, включён ли модуль `multitenancy-manager`, во всех редакциях |
