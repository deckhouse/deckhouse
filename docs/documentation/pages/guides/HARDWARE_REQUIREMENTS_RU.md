Перед развёртыванием [кластера под управлением Deckhouse Platform](../glossary.html#dp-managed-cluster) необходимо определиться с конфигурацией будущего кластера и выбрать параметры для будущих узлов кластера, такие как количество RAM, CPU и так далее.

## Планирование установки

Прежде чем приступить к развёртыванию кластера, необходимо провести планирование ресурсов, которые могут потребоваться для его работы. Для этого следует ответить на несколько вопросов:

* Какая нагрузка планируется на кластер?
* Требуется ли кластеру режим повышенной нагрузки?
* Требуется ли кластеру [режим высокой доступности](../glossary.html#ha-mode)?
* Какие модули Deckhouse Platform планируется использовать?

Ответы на эти вопросы помогут определить необходимое количество узлов для развёртывания кластера. Подробнее — [в разделе «Варианты размещения»](../requirements/#варианты-размещения) на странице «Системные требования».

{% alert level="info" %}
Всё описанное дальше применимо к установке Deckhouse Platform [с набором модулей Default](../admin/configuration/#наборы-модулей).
{% endalert %}

## Сценарии развёртывания

Варианты размещения кластера ([одноузловой кластер](../glossary.html#single-node-cluster), [кластер с одним master-узлом](../glossary.html#single-master), с тремя [master-узлами](../glossary.html#master-node) или с разделением ролей узлов) и типы узлов описаны [в разделе «Варианты размещения»](../requirements/#варианты-размещения) на странице «Системные требования».

{% alert level="info" %}
Deckhouse Platform, начиная с версии 1.74, имеет механизм [контроля целостности](../glossary.html#integrity-control) модулей, который защищает их от подмены и изменения. Этот механизм включается автоматически при поддержке операционной системой на узлах, где установлен Deckhouse Platform, модуля ядра `erofs`. При отсутствии этого модуля ядра Deckhouse Platform продолжит работу без механизма контроля целостности модулей, при этом появится алерт о неработоспособности этой функциональности.
{% endalert %}

## Выбор ресурсов для узлов

Требования к ресурсам зависят от варианта размещения (одноузловой кластер, кластер с одним master-узлом, с тремя master-узлами или с разделением ролей узлов), а также от типа нагрузки (запуск контейнеров, виртуальных машин, либо контейнеров и виртуальных машин).

Таблицы с ресурсами узлов для каждого варианта размещения и типа нагрузки приведены [в разделе «Требования к ресурсам»](../requirements/#требования-к-ресурсам) на странице «Системные требования». Там же описано, что учитывают значения в таблицах и какие ресурсы нужно зарезервировать на узлах дополнительно.

### Кластер, состоящий из одного узла

{% alert level="warning" %}
У такого кластера отсутствует отказоустойчивость. Не используйте такие кластеры в production-окружениях.
{% endalert %}

В некоторых случаях кластер может состоять из одного узла, который выполняет все описанные выше роли.
Такой вариант может использоваться, например, для ознакомления с продуктом или для решения простых задач с невысокими требованиями к ресурсам.

В [«Быстром старте»](/products/kubernetes-platform/gs/bm/step5.html) есть инструкции по развёртыванию кластера на одном узле. После снятия taint с узла на нём будут запущены все компоненты кластера, входящие в выбранный [набор модулей](../glossary.html#module-bundle) (по умолчанию — [Default](/modules/deckhouse/configuration.html#parameters-bundle)). Ресурсы для такого узла приведены в строке «Одноузловой кластер» таблиц [раздела «Требования к ресурсам»](../requirements/#требования-к-ресурсам) для нужного типа нагрузки: контейнеры, виртуальные машины или комбинированная нагрузка.

Эта конфигурация позволит запускать некоторую полезную нагрузку.

В одноузловом кластере для запуска контейнеров с ресурсами из таблицы при нагрузке в 2500 RPS на условное веб-приложение (статическая страница Nginx) из 30 подов и входящем трафике в 24 Мбит/с:

* нагрузка на CPU суммарно будет повышаться до ~60%;
* значения RAM и диска не возрастают, но в реальности будут зависеть от количества метрик, собираемых с приложений, и характера обработки полезной нагрузки.

{% alert level="info" %}
Проведите нагрузочное тестирование приложения и скорректируйте мощности сервера по его результатам.
{% endalert %}

### Примеры конфигураций

Пример ниже — кластер с разделением ролей узлов без отказоустойчивости: по одному узлу каждого типа, без выделенных [узлов мониторинга](../glossary.html#monitoring-node). Ресурсы узлов взяты из таблицы [«Для контейнеров»](../requirements/#containers) для кластера с разделением ролей узлов.

Для развёртывания Deckhouse Platform для запуска контейнеров [в редакции Ultimate/Enterprise](../glossary.html#edition) с набором модулей [Default](/modules/deckhouse/configuration.html#parameters-bundle) необходима следующая конфигурация узлов:

* **[master-узлы](../glossary.html#master-node)** — 1 шт., 6 CPU, 12 ГБ RAM, 60 ГБ диска;
* **[frontend-узлы](../glossary.html#frontend-node)** — 1 шт., 2 CPU, 4 ГБ RAM, 60 ГБ диска;
* **[системные узлы](../glossary.html#system-node)** — 1 шт., 6 CPU, 12 ГБ RAM, 300 ГБ диска (на системном узле размещаются компоненты мониторинга и системные PVC);
* **[worker-узлы](../glossary.html#worker-node)** — 1 шт., 2 CPU, 4 ГБ RAM, 60 ГБ диска плюс ресурсы под пользовательскую нагрузку.

{% alert level="info" %}
При необходимости Deckhouse Platform в такой же конфигурации можно запустить и на одном узле. Ресурсы для него приведены в строке «Одноузловой кластер» той же таблицы: 12 CPU, 24 ГБ RAM и 350 ГБ диска.
{% endalert %}
