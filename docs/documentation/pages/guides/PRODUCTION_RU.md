Приведённые ниже рекомендации могут быть неактуальны для тестового кластера или кластера разработки, но важны для production-кластера.

## Канал и режим обновлений

{% alert %}
Используйте канал обновлений `EarlyAccess` или `Stable`. Установите [окно автоматических обновлений](/modules/deckhouse/usage.html#конфигурация-окон-обновлений) или [ручной режим](/modules/deckhouse/usage.html#ручное-подтверждение-обновлений).
{% endalert %}

Выберите [канал обновлений](../reference/release-channels.html) и [режим обновлений](/modules/deckhouse/configuration.html#parameters-update-mode), который соответствует вашим ожиданиям. Чем стабильнее канал обновлений, тем позже до него доходит новая функциональность.

По возможности используйте разные каналы обновлений для кластеров. Для кластера разработки используйте менее стабильный канал обновлений, нежели для тестового или stage-кластера (pre-production-кластер).

Используйте канал обновлений `EarlyAccess` или `Stable` для production-кластеров.

Если в production-окружении больше одного кластера, сделайте так, чтобы кластеры обновлялись в разное время. Тогда новая версия сначала установится в одном кластере, и вы успеете проверить её до того, как обновятся остальные. Чтобы развести обновления по времени, задайте кластерам непересекающиеся [окна обновлений](/modules/deckhouse/configuration.html#parameters-update-windows) или подключите их к разным каналам обновлений. Например, если один кластер получает обновления из канала `EarlyAccess`, а другой из канала `Stable`, новая версия придёт во второй кластер позже.

{% alert level="warning" %}
Даже в очень нагруженных и критичных кластерах не стоит отключать использование канала обновлений. Лучшая стратегия — плановое обновление. В инсталляциях Deckhouse Platform, которые не обновлялись полгода или более, могут присутствовать ошибки. Как правило, эти ошибки давно устранены в новых версиях. В этом случае оперативно решить возникшую проблему будет непросто.
{% endalert %}

Управление [окнами обновлений](/modules/deckhouse/configuration.html#parameters-update-windows) позволяет планово обновлять релизы платформы в автоматическом режиме в периоды «затишья», когда нагрузка на кластер далека от пиковой.

## Версия Kubernetes

{% alert %}
Используйте автоматический [выбор версии Kubernetes](../reference/api/cr.html#clusterconfiguration-kubernetesversion) либо установите версию явно.
{% endalert %}

В большинстве случаев используйте автоматический выбор версии Kubernetes. В платформе такое поведение установлено по умолчанию, но его можно изменить с помощью параметра [kubernetesVersion](../reference/api/cr.html#clusterconfiguration-kubernetesversion). Обновление версии Kubernetes в кластере не оказывает влияния на приложения и проходит [последовательно и безопасно](/modules/control-plane-manager/#управление-версиями).

Если указан автоматический выбор версии Kubernetes, платформа может обновить версию Kubernetes в кластере при обновлении релиза платформы (при обновлении минорной версии). Когда версия Kubernetes явно прописана в параметре [kubernetesVersion](../reference/api/cr.html#clusterconfiguration-kubernetesversion), очередное обновление платформы может завершиться неудачей, если окажется, что используемая в кластере версия Kubernetes более не поддерживается.

Если приложение использует устаревшие версии ресурсов или требует конкретной версии Kubernetes по какой-либо другой причине, проверьте, что эта версия [поддерживается](../reference/supported_versions.html), и [установите её](../admin/configuration/platform-scaling/control-plane/updating-and-versioning.html).

## Требования к ресурсам

{% alert %}
Выделяйте от 4 CPU / 8 ГБ RAM на инфраструктурные узлы (2 CPU / 4 ГБ RAM на frontend-узлы). Для master-узлов и узлов мониторинга используйте быстрые диски.
{% endalert %}

Рекомендуются следующие минимальные ресурсы для инфраструктурных узлов в зависимости от их роли в кластере:

- **Master-узел** — 8 CPU, 16 ГБ RAM, 60 ГБ дискового пространства на быстром диске (400+ IOPS);
- **Frontend-узел** — 2 CPU, 4 ГБ RAM, 50 ГБ дискового пространства;
- **Узел мониторинга** (для нагруженных кластеров) — 6 CPU, 12 ГБ RAM; <a href="#storage">50 / 150*</a> ГБ дискового пространства на быстром диске (400+ IOPS).
- **Системный узел**:
  - 4 CPU, 8 ГБ RAM, <a href="#storage">50 / 150*</a> ГБ дискового пространства — если в кластере есть выделенные узлы мониторинга;
  - 8 CPU, 16 ГБ RAM, <a href="#storage">60 / 160*</a> ГБ дискового пространства на быстром диске (400+ IOPS) — если в кластере нет выделенных узлов мониторинга.
- **Worker-узел** — требования аналогичны требованиям к master-узлу, но во многом зависят от характера запускаемой на узле (узлах) нагрузки.

Дополнительные рекомендации:<span id="storage"></span>

- Если системные PVC (модулей `prometheus`, `upmeter` и других) размещаются на локальном диске узла, необходимо дополнительно выделить не менее 100 ГБ свободного пространства. Второе значение объёма диска для узлов мониторинга и системных узлов выше (например, 150 в «50 / 150») учитывает эти 100 ГБ.
- Для системных сервисов (kubelet) и системных подов на каждом worker-узле зарезервируйте не менее 1 CPU и 2 ГБ оперативной памяти.
- Для всех узлов используйте быстрые диски с производительностью не менее 400 IOPS.

Примерный расчёт ресурсов, необходимых для кластера:

- **Типовой кластер**: 3 master-узла, 2 frontend-узла, 2 системных узла. Такая конфигурация потребует **от 44 CPU и 88 ГБ RAM**, плюс быстрые диски с 400+ IOPS для master-узлов.
- **Кластер с повышенной нагрузкой** (с выделенными узлами мониторинга): 3 master-узла, 2 frontend-узла, 2 системных узла, 2 узла мониторинга. Такая конфигурация потребует **от 48 CPU и 96 ГБ RAM**, плюс быстрые диски с 400+ IOPS для master-узлов и узлов мониторинга.
- Для компонентов платформы выделите отдельный [storageClass](../reference/api/global.html#parameters-modules-storageclass) на быстрых дисках.
- Добавьте к этому worker-узлы с учётом характера полезной нагрузки.

Также ознакомьтесь [с инструкцией](hardware-requirements.html) по аппаратным требованиям к ресурсам кластера, в которой подробно описано, как подобрать необходимые ресурсы в зависимости от предполагаемой нагрузки.

## Особенности конфигурации

### Master-узлы

{% alert %}
В кластере должно быть три master-узла с быстрыми дисками 400+ IOPS.
{% endalert %}

Всегда используйте три master-узла — такое количество обеспечит отказоустойчивость и позволит безопасно выполнять обновление master-узлов. В большем числе master-узлов нет необходимости, а два узла не обеспечат кворума.

Конфигурация master-узлов для облачных кластеров настраивается в параметре [masterNodeGroup](/modules/cloud-provider-aws/cluster_configuration.html#awsclusterconfiguration-masternodegroup).

Может быть полезно:

- [Как добавить master-узлы в облачном кластере...](../admin/configuration/platform-scaling/control-plane/scaling-and-changing-master-nodes.html#добавление-master-узлов-в-облачном-кластере).
- [Работа со статическими узлами...](/modules/node-manager/#работа-со-статическими-узлами).

### Frontend-узлы

{% alert %}
Выделите два или более frontend-узла.

Используйте инлет `LoadBalancer` для OpenStack и облачных сервисов, где возможен автоматический заказ балансировщика (Yandex Cloud, VK Cloud, Selectel Cloud, AWS, GCP, Azure и т. п.). Используйте инлет `HostPort` с внешним балансировщиком для bare metal или vSphere.
{% endalert %}

Frontend-узлы балансируют входящий трафик. На них работают Ingress-контроллеры. У [NodeGroup](/modules/node-manager/cr.html#nodegroup) frontend-узлов установлен лейбл `node-role.deckhouse.io/frontend`. Читайте подробнее про [выделение узлов под определённый вид нагрузки...](../admin/configuration/#выделение-узлов-под-определенный-вид-нагрузки)

Используйте более одного frontend-узла. Frontend-узлы должны выдерживать трафик при отказе как минимум одного frontend-узла.

Например, если в кластере два frontend-узла, то каждый frontend-узел должен справляться со всей нагрузкой на кластер в случае, если второй выйдет из строя. Если в кластере три frontend-узла, то каждый frontend-узел должен выдерживать увеличение нагрузки как минимум в полтора раза.

Выберите [тип инлета](/modules/ingress-nginx/cr.html#ingressnginxcontroller-v2-spec-inlet) (определяет способ поступления трафика).

При развёртывании платформы в облачной инфраструктуре, в которой поддерживается заказ балансировщиков (например, решения на базе OpenStack, сервисы Yandex Cloud, VK Cloud, Selectel Cloud, AWS, GCP, Azure и т. п.), используйте инлет `LoadBalancer` или `LoadBalancerWithProxyProtocol`.

В средах, в которых автоматический заказ балансировщиков недоступен (в bare-metal-кластерах, vSphere, некоторых решениях на базе OpenStack), используйте инлет `HostPort` или `HostPortWithProxyProtocol`. В этом случае можно либо добавить несколько A&#8209;записей в DNS для соответствующего домена, либо использовать внешний сервис балансировки нагрузки (например, взять решения от Cloudflare, Qrator или настроить metallb).

{% alert level="warning" %}
Инлет `HostWithFailover` подходит для кластеров с одним frontend-узлом. Он позволяет сократить время недоступности Ingress-контроллера при его обновлении. Такой тип инлета подойдёт, например, для важных сред разработки, но **не рекомендуется для production**.
{% endalert %}

### Узлы мониторинга

{% alert %}
Для нагруженных кластеров выделите два узла мониторинга с быстрыми дисками.
{% endalert %}

Узлы мониторинга служат для запуска Grafana, Prometheus и других компонентов мониторинга. У [NodeGroup](/modules/node-manager/cr.html#nodegroup) узлов мониторинга установлен лейбл `node-role.deckhouse.io/monitoring`.

В нагруженных кластерах со множеством алертов и большими объёмами метрик выделите под мониторинг отдельные узлы. Если этого не сделать, компоненты мониторинга будут размещены на [системных узлах](#системные-узлы).

При выделении узлов под мониторинг важно, чтобы на них были быстрые диски. Для этого можно привязать `storageClass` на быстрых дисках ко всем компонентам платформы (глобальный параметр [storageClass](../reference/api/global.html#parameters-modules-storageclass)) или выделить отдельный `storageClass` только для компонентов мониторинга (параметры [storageClass](/modules/prometheus/configuration.html#parameters-storageclass) и [longtermStorageClass](/modules/prometheus/configuration.html#parameters-longtermstorageclass) модуля `prometheus`).

Если кластер изначально создаётся с узлами, выделенными под определённый вид нагрузки (системные узлы, узлы под мониторинг и т. п.), то для модулей, использующих тома постоянного хранилища (например, для модуля `prometheus`), явно укажите соответствующий `nodeSelector` в конфигурации модуля. Например, для модуля `prometheus` это параметр [nodeSelector](/modules/prometheus/configuration.html#parameters-nodeselector).

### Системные узлы

{% alert %}
Выделите два системных узла.
{% endalert %}

Системные узлы предназначены для запуска модулей платформы. У [NodeGroup](/modules/node-manager/cr.html#nodegroup) системных узлов установлен лейбл `node-role.deckhouse.io/system`.

Выделите два системных узла. В этом случае модули платформы будут работать на них, не пересекаясь с пользовательскими приложениями кластера. Читайте подробнее про [выделение узлов под определённый вид нагрузки...](../admin/configuration/#выделение-узлов-под-определенный-вид-нагрузки).

Выделите компонентам платформы быстрые диски (глобальный параметр [storageClass](../reference/api/global.html#parameters-modules-storageclass)).

### Подсети кластера

{% alert %}
Спланируйте подсети кластера до установки, потому что после неё их нельзя изменить.
{% endalert %}

Подсеть подов ([`podSubnetCIDR`](/modules/control-plane-manager/configuration.html#parameters-network-podsubnetcidr)), подсеть сервисов ([`serviceSubnetCIDR`](/modules/control-plane-manager/configuration.html#parameters-network-servicesubnetcidr)) и размер подсети, которую получает каждый узел ([`podSubnetNodeCIDRPrefix`](/modules/control-plane-manager/configuration.html#parameters-network-podsubnetnodecidrprefix)), задаются при установке кластера. Подберите подсети подов и сервисов так, чтобы они не пересекались друг с другом и с сетью узлов. Изменение этих параметров в работающем кластере может вывести его из строя, поэтому платформа блокирует такое изменение. Если подсети всё же нужно изменить, пересоздайте кластер.

Размер подсети узла определяет, сколько подов поместится на узле. По умолчанию лимит подов на узле, параметр [`kubelet.maxPods`](/modules/node-manager/cr.html#nodegroup-v1-spec-kubelet-maxpods) группы узлов, вычисляется из этого размера. Соответствие размера подсети и лимита подов приведено в разделе [«Лимит подов на узел»](high-pod-density.html#лимит-подов-на-узел).

### Хранилище

{% alert %}
Для данных production-нагрузки используйте реплицируемое хранилище и назначьте StorageClass по умолчанию.
{% endalert %}

Рабочие нагрузки хранят постоянные данные в томах PersistentVolume, поэтому подключите к кластеру хотя бы одно из [поддерживаемых хранилищ](../admin/configuration/storage/). Для production выбирайте хранилище, которое реплицирует данные между узлами, например [реплицируемое хранилище на основе DRBD](../admin/configuration/storage/sds/lvm-replicated.html), чтобы данные оставались доступными при отказе узла. Если используете программно-определяемое хранилище (SDS), выделите на его узлах отдельные диски под данные.

Назначьте StorageClass по умолчанию в глобальном параметре [`defaultClusterStorageClass`](../reference/api/global.html#parameters-defaultclusterstorageclass). Этот класс хранения получают тома, для которых класс не указан явно.

### Виртуализация

Если в кластере будут работать виртуальные машины (ВМ), учтите рекомендации этого раздела вместе с остальными рекомендациями руководства.

#### Требования к узлам для ВМ

Кластер с ВМ должен соответствовать следующим требованиям:

- ВМ запускаются на физических серверах (bare metal).
- Процессоры узлов для ВМ поддерживают инструкции Intel-VT (VMX) или AMD-V (SVM), а аппаратная виртуализация включена в настройках BIOS или UEFI.
- На всех узлах кластера установлена одна и та же версия ядра Linux.

Одна версия ядра нужна для стабильной живой миграции ВМ, потому что системные вызовы и работа с ресурсами в разных версиях ядра различаются.

{% alert level="warning" %}
Использовать виртуальные машины вместо физических серверов в качестве узлов допустимо только в демонстрационных целях. В этом случае включите вложенную виртуализацию (nested virtualization).
{% endalert %}

#### Число ВМ на узле

Число ВМ на узле ограничено [лимитом подов](#подсети-кластера), общим для ВМ, контейнеров и системных компонентов. Работающая ВМ с дисками обычно занимает два пода, потому что кроме пода самой ВМ на узле работает служебный под, через который подключаются её диски и образы. Он нужен дискам, добавленным ресурсом [VirtualMachineBlockDeviceAttachment](/modules/virtualization/cr.html#virtualmachineblockdeviceattachment), и всем дискам ВМ с включённой паравиртуализацией (параметр [`.spec.enableParavirtualization`](/modules/virtualization/cr.html#virtualmachine-v1alpha2-spec-enableparavirtualization), включён по умолчанию). Во время живой миграции такие же поды запускаются на целевом узле, поэтому учитывайте их, когда выбираете размер подсети узла.

#### Подсети ВМ

ВМ получают IP-адреса в основной сети кластера из подсетей, перечисленных в параметре [`virtualMachineCIDRs`](/modules/virtualization/configuration.html#parameters-virtualmachinecidrs) модуля `virtualization`. Подберите их так, чтобы они не пересекались с сетью узлов и [подсетями кластера](#подсети-кластера), иначе возникнут конфликты адресов.

Указывайте подсеть адресом её начала, выровненным по маске, например `192.168.1.192/27`, а не `192.168.1.190/27`. Подсетей можно указать несколько и добавлять новые позже, но удалить подсеть нельзя, пока в ней есть адреса, занятые ресурсами [VirtualMachineIPAddress](/modules/virtualization/cr.html#virtualmachineipaddress).

Параметр `virtualMachineCIDRs` необязательный. Без него ВМ не могут работать в основной сети кластера и получать адреса ресурсом VirtualMachineIPAddress, поэтому их можно подключить только к дополнительным сетям. Настройка сетей ВМ описана в разделе [«Сеть виртуальных машин»](../admin/configuration/network/vm-network.html).

#### Сеть для живой миграции

По умолчанию трафик живой миграции идёт по основной сети узлов, конкурирует с рабочей нагрузкой за полосу пропускания и ограничен скоростью 640 МиБ/с на одну миграцию. Чтобы миграции не мешали рабочей нагрузке и шли быстрее, направьте их в выделенную сеть в параметре [`liveMigration.network`](/modules/virtualization/configuration.html#parameters-livemigration-network) модуля `virtualization`, где платформа по умолчанию не ограничивает скорость. Для этого необходимо, чтобы был включён модуль [`sdn`](/modules/sdn/), а ресурс [SystemNetwork](/modules/sdn/cr.html#systemnetwork) находился в состоянии `Ready`. Настройка описана в разделе [«Выделенная сеть для миграции»](../admin/configuration/platform-scaling/node/vm-node-maintenance.html#выделенная-сеть-для-миграции).

#### Запуск ВМ на master-узлах

Запускать ВМ на master-узлах приходится, если в кластере нет отдельных узлов для рабочей нагрузки, например в одноузловом кластере. Чтобы ВМ работали на master-узлах, снимите taints с группы узлов `master` в параметре [`nodeTemplate.taints`](/modules/node-manager/cr.html#nodegroup-v1-spec-nodetemplate-taints) или задайте tolerations для выбранных ВМ. Tolerations задаются в ВМ параметром [`.spec.tolerations`](/modules/virtualization/cr.html#virtualmachine-v1alpha2-spec-tolerations) или в классе ВМ параметром [`.spec.tolerations`](/modules/virtualization/cr.html#virtualmachineclass-v1alpha3-spec-tolerations). Снятие taints разрешает запуск на master-узлах любой рабочей нагрузки, а tolerations разрешают его только ВМ, которым они заданы.

#### Хранилище для дисков ВМ

Диски и образы ВМ хранятся в томах PersistentVolume, поэтому выбирайте для них хранилище по рекомендациям раздела [«Хранилище»](#хранилище). Если диски ВМ будут размещаться в программно-определяемом хранилище, учитывайте их объём, когда выделяете диски на узлах этого хранилища.

Живая миграция ВМ с локальными дисками доступна только в коммерческих редакциях Deckhouse Platform, в которых диски переносятся вместе с ВМ. В Deckhouse Platform Open ВМ с локальным диском нельзя перенести на другой узел, поэтому на время обслуживания узла её придётся остановить.

#### Хранилище образов

Платформа хранит образы ВМ во внутреннем хранилище образов (DVCR), которое работает в одном экземпляре на одном постоянном томе. Класс хранения и размер этого тома задаются в параметре [`dvcr.storage`](/modules/virtualization/configuration.html#parameters-dvcr-storage) модуля `virtualization`. После создания тома его размер можно только увеличить, а класс хранения сменить нельзя, поэтому выберите класс заранее. Используйте для DVCR реплицируемое хранилище, чтобы образы оставались доступными при отказе узла.

#### Классы ВМ

Создайте собственные классы ВМ (ресурс [VirtualMachineClass](/modules/virtualization/cr.html#virtualmachineclass)) и не используйте для production-нагрузки класс `generic`. Платформа создаёт класс `generic` при установке с моделью процессора Nehalem. Эта модель поддерживает наименьший набор инструкций, поэтому ВМ класса `generic` запускаются на любом узле, но не получают инструкций современных процессоров.

Отметьте свой основной класс аннотацией `virtualmachineclass.virtualization.deckhouse.io/is-default-class` со значением `true`, и платформа будет подставлять его в ВМ, для которых класс не указан. Не ставьте эту аннотацию на класс `generic`, потому что при обновлении модуля она может пропасть.

Тип процессора класса задаётся параметром [`.spec.cpu.type`](/modules/virtualization/cr.html#virtualmachineclass-v1alpha3-spec-cpu-type) и определяет, между какими узлами ВМ смогут мигрировать. Изменить его после создания класса нельзя, поэтому выберите тип заранее:

- `Host` даёт ВМ набор инструкций, близкий к процессору узла. ВМ мигрируют только между узлами с похожими процессорами. Миграция между процессорами Intel и AMD или между разными поколениями процессоров невозможна.
- `HostPassthrough` передаёт ВМ процессор узла без изменений. ВМ мигрируют только на узлы с точно таким же процессором.
- `Discovery` составляет общий набор инструкций для выбранных узлов и подходит для кластера с разными процессорами. Набор фиксируется при создании класса и не меняется при добавлении узлов в кластер.

Остальные типы процессора описаны в разделе [«Виртуальный процессор виртуальных машин»](../admin/configuration/virtualization/vm-classes-cpu.html).

Политики сайзинга класса задаются параметром [`.spec.sizingPolicies`](/modules/virtualization/cr.html#virtualmachineclass-v1alpha3-spec-sizingpolicies). Они ограничивают число ядер, объём памяти и долю ядра для ВМ этого класса. Доля ядра — это часть процессорного времени физического ядра, которая гарантирована ВМ. Допустимые значения доли в параметре `coreFractions` определяют, насколько сильной может быть переподписка на CPU. Настройка переподписки описана в разделе [«Переподписка на CPU для виртуальных машин»](../admin/configuration/virtualization/cpu-oversubscription.html).

## Разграничение доступа

{% alert %}
Настройте аутентификацию пользователей и выдавайте права с помощью гранулярной ролевой модели. Для команд создавайте проекты.
{% endalert %}

Пользователей и группы можно создать в кластере ресурсами [User](/modules/user-authn/cr.html#user) и [Group](/modules/user-authn/cr.html#group) модуля `user-authn` или получать из внешних провайдеров аутентификации. Платформа поддерживает провайдеры по протоколам OIDC, SAML и LDAP, а также GitHub, GitLab, Atlassian Crowd и Bitbucket Cloud. К кластеру можно подключить несколько провайдеров одновременно. Настройка провайдеров описана в разделе [«Интеграция с внешними провайдерами аутентификации»](../admin/configuration/access/authentication/external-authentication-providers.html), а создание пользователей в кластере — в разделе [«Локальная аутентификация»](../admin/configuration/access/authentication/local.html).

Чтобы изолировать рабочие нагрузки команд друг от друга, создавайте для них проекты (ресурс [Project](/modules/multitenancy-manager/cr.html#project) модуля `multitenancy-manager`). Проект создаётся по шаблону, который задаёт ограничения ресурсов, сетевую изоляцию и профиль безопасности. Работа с проектами описана в разделе [«Управление проектами»](../admin/multitenancy/project-management.html).

Права выдавайте с помощью [гранулярной ролевой модели](/modules/user-authz/#гранулярная-ролевая-модель) модуля `user-authz`. Модель использует стандартные ресурсы RBAC Kubernetes и роли, которые создаёт модуль. Каждая роль действует в одной из четырёх областей:

- **Неймспейс.** Роли `d8:namespace:<LEVEL>` дают права пользователям приложений в одном неймспейсе и назначаются ресурсом RoleBinding.
- **Проект.** Роли `d8:project:<LEVEL>` дают права командам сразу во всех неймспейсах проекта и назначаются ресурсом [ProjectRoleBinding](/modules/multitenancy-manager/cr.html#projectrolebinding).
- **Подсистема.** Роли `d8:subsystem:<SUBSYSTEM>:<LEVEL>` дают права администраторам части платформы, например сети, и назначаются ресурсом ClusterRoleBinding.
- **Вся платформа.** Роли `d8:system:<LEVEL>` дают права администраторам платформы и назначаются ресурсом ClusterRoleBinding.

Здесь `<LEVEL>` обозначает уровень доступа, например `viewer` или `manager`, а `<SUBSYSTEM>` обозначает имя подсистемы.

Упрощённая ролевая модель на ресурсах ClusterAuthorizationRule и AuthorizationRule тоже работает, но в будущих релизах платформа перестанет её поддерживать.

## Уведомление о событиях мониторинга

{% alert %}
Настройте отправку алертов через [внутренний](/modules/prometheus/faq.html#как-добавить-alertmanager) Alertmanager или подключите [внешний](/modules/prometheus/faq.html#как-добавить-внешний-дополнительный-alertmanager).

С помощью кастомного ресурса [CustomAlertmanager](/modules/prometheus/cr.html#customalertmanager) можно настроить отправку уведомлений на [электронную почту](/modules/prometheus/cr.html#customalertmanager-v1alpha1-spec-internal-receivers-emailconfigs), в [Slack](/modules/prometheus/cr.html#customalertmanager-v1alpha1-spec-internal-receivers-slackconfigs), в [Telegram](/modules/prometheus/usage.html#отправка-алертов-в-telegram), через [webhook](/modules/prometheus/cr.html#customalertmanager-v1alpha1-spec-internal-receivers-webhookconfigs), а также другими способами.

Список всех доступных алертов системы мониторинга Deckhouse Platform приведён на [отдельной странице документации](../reference/alerts.html).

## Резервное копирование

{% alert %}
Настройте [резервное копирование etcd](/modules/control-plane-manager/faq.html#как-сделать-резервную-копию-etcd-вручную). Напишите план восстановления.
{% endalert %}

**Важно.** Обязательно настройте [резервное копирование данных etcd](/modules/control-plane-manager/faq.html#как-сделать-резервную-копию-etcd-вручную) — это ваша последняя возможность восстановить кластер в случае непредвиденных событий. Храните резервные копии как можно *дальше* от кластера.

Резервные копии не помогут, если они не работают или вы не знаете, как их использовать для восстановления. Составьте план восстановления на случай аварии (Disaster Recovery Plan, DRP), содержащий конкретные шаги и команды по развёртыванию кластера из резервной копии. Процедуры восстановления описаны [в разделе «Резервное копирование и восстановление»](../admin/configuration/backup/backup-and-restore.html).

Этот план должен периодически актуализироваться и проверяться учебными тревогами.
