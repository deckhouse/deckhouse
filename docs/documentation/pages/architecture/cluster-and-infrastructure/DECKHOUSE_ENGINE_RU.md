При загрузке проверяется системный образ. От разметки диска зависит, какие данные сохраняются после перезагрузки.

## Загрузка и цепочка доверия

Узел загружается только через UEFI. Единый образ ядра (Unified Kernel Image, UKI) объединяет ядро, initramfs и
командную строку ядра в одном подписанном файле. В ядро встроен корневой сертификат
Deckhouse, и это единственный ключ, которому ядро доверяет.

Тем же ключом подписаны:

- корневой хэш образа корня: ядро проверяет подпись до того, как смонтировать корень;
- модули ядра: неподписанный модуль не загрузится;
- системные расширения: расширение без подписи не будет подключено.

Образ корня собран в формате erofs и монтируется через dm-verity. Каждый прочитанный блок
сверяется с деревом хэшей, поэтому изменение корня на диске обнаруживается при чтении, а не
при следующей проверке.

## Диск

Установщик размечает системный диск. При установке с ISO и при загрузке с готового диска qcow2 размеры разделов различаются:

| Раздел | Установка с ISO | Диск qcow2 | Назначение |
|---|---|---|---|
| `BOOT` | 512 МиБ | 120 МиБ | UKI и два слота образа корня (A и B) |
| `CONFIG` | 10 МиБ | 16 МиБ | Конфигурация узла и сведения об установленном образе |
| `DATA` | Остаток диска | 512 МиБ до первого запуска | `/var`: контейнеры, образы, состояние kubelet и журналы |

При первом запуске узла с диска qcow2 раздел `DATA` расширяется на оставшееся место.

Дополнительные диски, например отдельный диск под etcd на master-узле, подключаются
параметром `spec.storage.mounts` ресурса NodeConfig.

## Доступные для записи директории

Корень, включая `/etc` и `/usr`, только для чтения. Запись возможна в четыре места:

| Путь | Что это | Переживает перезагрузку |
|---|---|---|
| `/var` | раздел `DATA` | да |
| `/run` | tmpfs | нет |
| `/tmp` | tmpfs | нет |
| `/mnt` | tmpfs, поверх подключаются разделы из `spec.storage.mounts` | разделы — да |

`/var/run` — ссылка на `/run`, поэтому всё, что записано по этому пути, перезагрузку не
переживает.

## Компоненты узла

PID 1 — systemd. Набор юнитов на узле закрыт: запускается только то, что разрешено в образе
корня. containerd, kubelet и остальные компоненты Kubernetes подключаются системными
расширениями (systemd-sysext). Расширение подключается, только если его подпись проверена.
Какие расширения нужны узлу, задаёт кластер в NodeConfig.

## Механизм получения конфигурации узлом

Конфигурация узла хранится в NodeConfig. При добавлении машины источник конфигурации зависит от способа установки:

- для первых master-узлов — `dhctl bootstrap`;
- для статических узлов после установки кластера — плагин `node` для Deckhouse CLI;
- для облачных узлов — облачный провайдер через cloud-init.

Дальше NodeConfig узла ведёт кластер: контроллер `node-controller` модуля `node-manager`
пересчитывает его при изменении NodeGroup и параметров кластера. Машинная часть документа
(диск, сеть) задаётся при установке и сохраняется.

Изменения, которые прерывают работу узла (например, обновление образа корня с
перезагрузкой), `nodelet` применяет только после разрешения кластера, по тем же правилам
[`disruptions`](/modules/node-manager/cr.html#nodegroup-v1-spec-disruptions), что и для
остальных узлов.

Для настройки узлов используйте [руководство по установке и добавлению узлов](../../../installing/deckhouse-engine.html).
