На этой странице описано, как Deckhouse Platform (DP) запускает экземпляр приложения и какие инструменты помогают отлаживать пакет.

## Проверки при создании и изменении

Когда [Application](../../reference/api/cr.html#application) создаётся или изменяется, validating-вебхук DP проверяет, что:

- имя Application не длиннее 24 символов;
- ApplicationPackage существует, а ApplicationPackageVersion для указанных репозитория, пакета и версии существует и метаданные для неё загружены;
- настройки соответствуют схеме настроек версии пакета (см. [«Настройки приложения»](settings.html#когда-проверяются-настройки));
- кластер удовлетворяет [требованиям пакета](application-development.html#требования): версиям Kubernetes и DP и зависимостям от модулей. В сообщении об отказе указываются невыполненное требование, требуемое значение и значение в кластере.

## Этапы установки

DP обрабатывает каждый экземпляр приложения в отдельной очереди по шагам:

1. **Загрузка.** DP загружает bundle пакета указанной версии из репозитория.
2. **Чтение пакета.** DP читает `package.yaml`, схемы и `images_digests.json` и находит хуки.
3. **Планирование.** DP ждёт, пока не выполнятся требования пакета: бутстрап кластера завершён, версии Kubernetes и DP соответствуют ограничениям, а модули из `requirements.modules` включены. Пока DP ждёт модули, от которых зависит приложение, это отражается в summary ресурса Application.
4. **Конфигурация.** DP проверяет и применяет настройки.
5. **Инициализация хуков.** DP включает привязки `schedule` и мониторы Kubernetes хуков и выполняет `Synchronization` привязок Kubernetes. В первый раз после чтения пакета DP также запускает хуки `onStartup`.
6. **Применение.** DP запускает хуки `beforeHelm`, рендерит шаблоны и применяет их с помощью Nelm, а затем запускает хуки `afterHelm`. Если хуки `afterHelm` меняют values, DP применяет шаблоны ещё раз.

Шаги 4–6 составляют цикл согласования. На шаге применения DP обновляет Helm-релиз, только если это нужно: при первой установке, если последняя ревизия релиза не развёрнута, если отрендеренные манифесты изменились или если каких-то ресурсов нет в кластере.

Порядок привязок хуков и обработка ошибок хуков описаны в разделе [«Хуки»](hooks.html#привязки-и-порядок-выполнения).

## События и реакции

| Событие | Реакция DP |
|---|---|
| Меняется поле `spec.settings` или `spec.maintenance` ресурса Application | Новый цикл согласования |
| Хук `schedule` или хук с привязкой Kubernetes меняет values | Новый цикл согласования |
| Меняется поле `spec.packageVersion` | DP останавливает хуки текущей версии, сохраняя её ресурсы, и проходит все шаги с новой версией. Шаблоны новой версии применяются как обновление того же Helm-релиза |
| DP перезапускается | DP заново читает пакет и проходит все шаги, включая хуки `onStartup` |
| Ресурс приложения удалён из кластера | DP восстанавливает его (см. [«Восстановление ресурсов»](#восстановление-ресурсов)) |
| Требования пакета перестают выполняться, например, отключается модуль из `requirements.modules.mandatory` | DP удаляет приложение, но сохраняет Application (см. [«Приостановка»](#приостановка)) |
| Application удаляется | DP запускает хуки `beforeDeleteHelm`, удаляет Helm-релиз и ждёт удаления ресурсов, запускает хуки `afterDeleteHelm`, а затем удаляет Application |

## Приостановка

DP проверяет требования пакета не только при создании Application, но и постоянно. Если требования установленного приложения перестают выполняться, DP:

1. Запускает хуки `beforeDeleteHelm`.
2. Удаляет Helm-релиз, из-за чего удаляются ресурсы приложения.
3. Запускает хуки `afterDeleteHelm`.

Application остаётся в кластере в состоянии `Suspended`. Когда требования снова выполняются, DP заново устанавливает приложение с теми же настройками.

{% alert level="warning" %}
Ресурсы удаляются вместе с Helm-релизом, включая PersistentVolumeClaim. Чтобы сохранить данные, добавьте к PersistentVolumeClaim аннотацию `helm.sh/resource-policy: keep` (см. [«Аннотации Nelm»](nelm-annotations.html#2-сохранение-ресурса-при-удалении-или-uninstall)).
{% endalert %}

## Восстановление ресурсов

DP запоминает ресурсы, отрендеренные из шаблонов, и каждые 4–5 минут проверяет, что все они есть в кластере. Если какого-то ресурса нет, DP запускает цикл согласования, и ресурс создаётся заново.

DP проверяет только наличие ресурсов, но не их содержимое. Проверка приостанавливается, пока работают хуки, и отключена в [режиме обслуживания](#режим-обслуживания).

## Отслеживание деплоя

Когда DP применяет шаблоны, Nelm ждёт, пока ресурсы станут готовыми. Ожиданием управляют [аннотации трекинга](nelm-annotations.html#аннотации-трекинга). Логи подов не собираются, поэтому [аннотации логов](nelm-annotations.html#аннотации-логов) не действуют.

Ход текущего применения публикуется в поле `status.tracking` ресурса Application: список операций Nelm с их состояниями и зависимостями.

Одно применение ограничено 30 минутами. Если лимит превышен, DP отменяет применение, а в сообщении условия указываются до пяти ресурсов, готовности которых ждал DP, например:

```text
install nelm release 'my-namespace.myapp': apply timed out after 30m0s, waiting for Job/d8a-myapp-migrate
```

Работает ли приложение после применения, определяется по его Deployment и StatefulSet (см. [«Состояние рабочих нагрузок»](templates.html#состояние-рабочих-нагрузок)).

## Режим обслуживания

Чтобы отлаживать или вручную донастраивать установленное приложение, переведите его в режим обслуживания:

```yaml
spec:
  maintenance: NoResourceReconciliation
```

В режиме обслуживания:

- DP перестаёт применять шаблоны: изменения настроек и values не отражаются на ресурсах. Хуки продолжают работать.
- Удалённые ресурсы не восстанавливаются.
- DP добавляет к ресурсам, отрендеренным из шаблонов, метку `maintenance.deckhouse.io/no-resource-reconciliation`, и admission-политики перестают их защищать, поэтому ресурсы можно менять вручную. Чтобы добавить метку, DP один раз применяет шаблоны при включении режима.
- Срабатывает алерт `ApplicationIsInMaintenanceMode`.

Чтобы вернуть приложение к обычной работе, удалите поле `spec.maintenance`. DP применит шаблоны, что восстановит управляемое состояние ресурсов и удалит метку.

## Отладка

### Статус Application

При разработке пакета полезны следующие поля статуса Application:

| Поле | Описание |
|---|---|
| `status.summary` | Общее состояние приложения, причина и подсказка о том, что делать |
| `status.conditions` | Подробные условия (см. [«Установка и управление приложениями»](../../user/marketplace/applications.html#условия-conditions)) |
| `status.currentVersion.version` | Установленная версия пакета |
| `status.lastAppliedConfiguration` | Итоговые настройки последнего успешного применения |
| `status.urls` | [Адреса приложения](templates.html#адреса-приложения) |
| `status.tracking` | Отчёт Nelm о ходе текущего или последнего применения |

Пример:

```bash
d8 k -n <NAMESPACE> get applications <INSTANCE_NAME> -o jsonpath='{.status.summary}'
```

### Состояние в DP

Команды `deckhouse-controller packages` показывают состояние приложения в DP. Имя пакета в этих командах — `<NAMESPACE>.<INSTANCE_NAME>`. Выполняйте команды в контейнере `deckhouse` пода-лидера DP.

{% alert level="warning" %}
Вывод содержит values и учётные данные реестра. Доступ к нему должен быть только у администраторов кластера.
{% endalert %}

- Отрендерить шаблоны с текущими values:

  ```bash
  d8 k -n d8-system exec svc/deckhouse-leader -c deckhouse -- deckhouse-controller packages render <NAMESPACE>.<INSTANCE_NAME>
  ```

- Показать загруженный пакет: путь, описание, дайджесты образов, репозиторий, values, хуки и внутренние условия:

  ```bash
  d8 k -n d8-system exec svc/deckhouse-leader -c deckhouse -- deckhouse-controller packages dump --name <NAMESPACE>.<INSTANCE_NAME>
  ```

- Показать снапшоты привязок Kubernetes хуков:

  ```bash
  d8 k -n d8-system exec svc/deckhouse-leader -c deckhouse -- deckhouse-controller packages snapshots <NAMESPACE>.<INSTANCE_NAME>
  ```

- Показать очереди задач приложения:

  ```bash
  d8 k -n d8-system exec svc/deckhouse-leader -c deckhouse -- deckhouse-controller packages queue dump --name <NAMESPACE>.<INSTANCE_NAME>
  ```

- Показать состояние приложения в планировщике, например, какое требование не выполнено:

  ```bash
  d8 k -n d8-system exec svc/deckhouse-leader -c deckhouse -- deckhouse-controller packages scheduler dump --name <NAMESPACE>.<INSTANCE_NAME>
  ```

### Логи

DP записывает события обработки приложения, включая вывод хуков, в свой лог:

```bash
d8 k -n d8-system logs svc/deckhouse-leader -c deckhouse | grep '<NAMESPACE>.<INSTANCE_NAME>'
```
