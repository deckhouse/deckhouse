Обеспечивает синхронизацию времени на всех узлах кластера с помощью утилиты [chrony](https://chrony.tuxfamily.org/).

## Как работает

Модуль запускает `chrony` агенты на всех узлах кластера.
По умолчанию используется NTP сервер `pool.ntp.org`. NTP сервер можно изменить через [настройки](/modules/chrony/configuration.html) модуля.

Для просмотра используемых NTP серверов можно воспользоваться командой:

```bash
d8 k exec -it -n d8-chrony ds/chrony-master -- chronyc -N sources
```

Пример вывода:

```text
MS Name/IP address         Stratum Poll Reach LastRx Last sample
===============================================================================
^* pool.ntp.org.                 2  10   377   171   -502us[ -909us] +/- 5388us
^- pool.ntp.org.                 2  10   377   666  -5317us[-5698us] +/-  103ms
^+ pool.ntp.org.                 2  10   377   938   -201us[ -567us] +/- 5346us
^+ pool.ntp.org.                 2  10   377   843   -159us[ -530us] +/-   12ms
```

{% alert level="info" %}  
`^+` - комбинируемый NTP сервер(`chrony` комбинирует информацию из `combined` серверов для уменьшения неточностей);  
`^*` - текущий NTP сервер;  
`^-` - некомбинируемый NTP-сервер.  
Подробную информацию о значениях столбцов можно получить с помощью флага `-v`: `chronyc sources -v`.  
{% endalert %}

`chrony` агенты на мастер узлах и на остальных узлах имеют одно главное отличие - на всех узлах, которые не являются мастерами, в списке NTP серверов находятся не только NTP сервера из `module config`, но и адреса всех мастер узлов кластера.  

Таким образом, агенты на мастер узлах синхронизируют время только из списка хостов, указанных в `module config`(по умолчанию с `pool.ntp.org`). А агенты на остальных узлах синхронизируют время со списком NTP серверов из `module config` плюс с `chrony` агентов на мастер узлах.  

Это сделано для того, чтобы в случае недоступности NTP серверов, указанных в `module config`, время синхронизировалось с мастер узлами.

## Синхронизация времени при загрузке master-узлов

На master-узлах модуль также один раз устанавливает время при загрузке, до запуска `kubelet`.
Это нужно, чтобы статические поды control plane не запускались с неверным временем от аппаратных часов (RTC) или гипервизора.

Если большинство ответивших NTP-серверов сходятся во времени с точностью до 1 секунды, `kubelet` запускается сразу после установки времени.
Если ни один NTP-сервер не ответил или ответившие серверы расходятся, `kubelet` ждёт до 30 секунд и запускается с непроверенным временем. На узлах под управлением bashible лимит можно увеличить до 60 секунд параметром [`earlyTimeSync.timeoutSeconds`](configuration.html#parameters-earlytimesync-timeoutseconds).
На узлах под управлением bashible ожидание сети узла в это время не входит.
На этих узлах systemd ждёт сигнала о готовности `nodelet.service` после проверки. Проверку выполняет основной процесс nodelet.
На узлах Deckhouse Engine отсчёт начинается при запуске nodelet и может включать ожидание сети узла.
Отключить синхронизацию времени при загрузке можно параметром [`earlyTimeSync.enabled`](configuration.html#parameters-earlytimesync-enabled).

Синхронизация времени при загрузке использует сеть узла и его настройки DNS.
Kubernetes DNS и NTP-серверы внутри кластера в этот момент недоступны.

Если master-узел с настроенной ранней синхронизацией не может связаться с NTP-серверами, проверка откладывает запуск `kubelet` до таймаута. Алерт срабатывает, когда мониторинг соберёт результат проверки.
Это касается изолированного кластера, в котором остался сервер по умолчанию `pool.ntp.org`.
В этом случае укажите в параметре [`ntpServers`](configuration.html#parameters-ntpservers) NTP-серверы, доступные с master-узлов, или отключите синхронизацию времени при загрузке.

Включение синхронизации времени при загрузке и изменение её параметров применяются при следующей загрузке.
На работающем узле время сразу не меняется, потому что перевод часов назад на работающем control plane может нарушить аутентификацию и выбор лидера.
Отключение через `earlyTimeSync.enabled: false` действует сразу, как только конфигурация применится на master-узлах.

Если при загрузке время не синхронизировалось, для master-узла срабатывает [алерт `NodeTimeNotSynchronizedAtBoot`](/products/kubernetes-platform/documentation/v1/reference/alerts.html#chrony-nodetimenotsynchronizedatboot).
Алерт остаётся активным, пока не произойдёт одно из событий:

- узел загрузится снова, и синхронизация пройдёт успешно;
- синхронизация времени при загрузке будет отключена (на узлах Deckhouse Engine алерт после этого сбросится при следующей загрузке);
- вы сбросите алерт, как указано в его описании.

Алерт работает только при включённом модуле [`monitoring-kubernetes`](/modules/monitoring-kubernetes/), который собирает результат с узла.

### Ограничения

У синхронизации времени при загрузке есть следующие ограничения:

- На узлах Deckhouse Engine параметр `earlyTimeSync.timeoutSeconds` не действует: `kubelet` ждёт не больше 30 секунд.
  Из `ntpServers` там используются только первые 16 имён хостов и IPv4-адресов.
  Если master-узел загружается в новый образ ОС, это ожидание входит в 15 минут, за которые узел должен подтвердить образ.
  Если NTP-серверы недоступны, укажите доступные серверы в `ntpServers` или отключите синхронизацию времени при загрузке.
- Значения `ntpServers`, отличные от имени хоста или IPv4-адреса, например IPv6-адрес или значение с портом, пропускаются.
- Синхронизация не охватывает первую загрузку нового master-узла, в том числе при развёртывании кластера.
  Конфигурация попадает на узел во время этой загрузки, когда `kubelet` уже запущен.
- На узлах под управлением bashible после отключения модуля файлы синхронизации времени при загрузке остаются на узлах.
  Узлы Deckhouse Engine сами перестают синхронизировать время со следующей загрузки.
  Перед отключением модуля установите для `earlyTimeSync.enabled` значение `false` и дождитесь, пока конфигурация применится на master-узлах.
  Если модуль уже отключён, удалите файлы с помощью NodeGroupConfiguration, как показано [в FAQ](faq.html#как-запретить-использование-chrony-и-использовать-ntp-демоны-на-узлах).
