## Гранты на кластерные ресурсы

### Мой PVC отклонён с ошибкой "resource not available to project" — что делать?

Указанный в `spec.storageClassName` `StorageClass` отсутствует в allow-списке вашего проекта. Проверьте,
что разрешено:

```shell
d8 k get available storageclasses -n <имя-проекта> -o yaml
```

Если нужного имени нет, попросите администратора кластера добавить его в `ClusterResourceGrantPolicy`,
совпадающий с вашим проектом (или используйте имя из списка). То же относится к другим грантуемым
ресурсам (`ClusterIssuer`, `ClusterRole`, `LoadBalancerClass`) — проверьте соответствующий
`AvailableClusterResource`.

### Как узнать, какие grant-политики влияют на мой проект?

`ClusterResourceGrantPolicy` — кластерный ресурс; политика влияет на ваш проект, когда её
`projectSelector` совпадает с метками неймспейса вашего проекта. Выведите все политики и проверьте их
селекторы:

```shell
d8 k get clusterresourcegrantpolicies -o yaml
```

Также контроллер формирует каталог `AvailableClusterResource` в вашем неймспейсе для каждого
зарегистрированного определения — это эффективное, по-проектное представление того, что разрешено.

### Я изменил grant-политику, но существующие объекты используют старое значение — это баг?

Нет. Это **grandfathering**: при UPDATE уже присутствующие в объекте значения сохраняются, поэтому сужение
политики не ломает существующие объекты. Валидации подвергаются только CREATE и изменения полей при
UPDATE. Чтобы существующий объект использовал новое значение, обновите поле явно.

Алерт `ClusterResourceGrantPolicyViolation` срабатывает, когда существующие объекты нарушают текущие
гранты — он информационный; объекты продолжают работать.

### Сработал алерт `ClusterResourceGrantPolicyViolation` — что это значит?

Это значит, что один или несколько существующих объектов в проекте ссылаются на значение кластерного
ресурса, которое текущие гранты больше не разрешают. Объекты **не сломаны** (grandfathering), но
администратор оповещается о расхождении. Решите это, расширив политику на существующие значения или
обновив объекты на разрешённое значение. См. Grafana-дашборд *Security → Cluster Resource Grant
Violations* и метрику `d8_cluster_objects_grant_violated`.

### Как выдать все StorageClasses кроме конкретных?

Используйте список `denied` (или `deniedSelector`), оставив ресурс в остальном открытым:

```yaml
resources:
  - resourceName: storageclasses
    denied:
      - expensive-nvme
      - archived-hdd
```

`denied` перекрывает `allowed`/`allowedSelector`: имя, совпавшее с обоими, запрещается.

### Grant-политик нет — значит, ничего не работает?

Нет — наоборот. Без `ClusterResourceGrantPolicy` **все** ресурсы доступны (разрешающий дефолт).
Grant-политики — единственный способ сузить доступ; система сама ничего не ограничивает.

### Я создал grant-политику, но ничего не изменилось — как отлаживать?

Проверьте по порядку:

1. **Совпадение селектора** — совпадает ли `projectSelector` политики с метками неймспейса вашего проекта?
   (`d8 k get ns <проект> --show-labels`).
2. **AvailableClusterResource** — отражает ли каталог в неймспейсе проекта политику?
   (`d8 k get available <ресурс> -n <проект> -o yaml`).
3. **Определение существует** — существует ли `GrantableClusterResourceDefinition` для `resourceName`, и
   привязана ли его `GrantableClusterResourceReference`? (`...status.conditions[Bound]` = `Resolved`).
4. **Путь зарегистрирован** — покрыто ли поле, которое вы ожидаете валидировать/подставлять, записью
   `fieldPaths` ссылки.

### Как гранты взаимодействуют с `ClusterAuthorizationRule` / `AuthorizationRule`?

Это независимые механизмы. RBAC (через `ClusterAuthorizationRule`, `AuthorizationRule`, `RoleBinding`)
решает, **кто может создать** объект. Гранты решают, **какие кластерные ресурсы** этот объект может
ссылать. Пользователю нужно и то, и другое: RBAC-право на создание PVC *и* грант, разрешающий
`StorageClass`.

### Что произойдёт при отключении модуля `multitenancy-manager`?

CRD и вебхуки грантов удаляются, поэтому **валидация и подстановка дефолтов** кластерных ссылок не
выполняется — всё разрешено. Существующие объекты не затронуты. Расширение `x-deckhouse-grantable-resource`
в настройках DKP-приложений деградирует беззвучно (без валидации). Роль `d8:use:dict` в `user-authz`
независима и продолжает работать.

### Включение грантов на существующем кластере — что произойдёт?

Grandfathering защищает существующие объекты: их уже заданные значения сохраняются при UPDATE. Только
новые объекты и изменения полей при UPDATE валидируются по новым грантам. «Обратной заливки» нет —
мигрировать существующие объекты перед созданием политик не нужно.

### Я сузил грант — что будет с объектами, созданными при более широкой политике?

Они продолжат работать (grandfathering). Новые объекты и изменения полей при UPDATE валидируются по
суженным грантам. Если удалить политику, ресурс снова станет полностью открытым.
