Это единственный источник правды о файле, который модуль cloud-провайдера поставляет как
`capi/template.yaml`. **Чего нет в этом документе — того нет в контракте**: node-controller не даёт
шаблону ничего сверх описанного здесь, а расширение контракта требует повышения `version`.

## Что node-manager делает с вашим файлом

Для каждой зоны NodeGroup node-controller решает, нужно ли пересоздавать машины, и только если
нужно — рендерит ваш шаблон в новый инфраструктурный MachineTemplate и переключает на него
MachineDeployment. CAPI пересоздаёт машины потому, что изменилось **имя** объекта, на который
ссылается MachineDeployment: это контракт CAPI, и поэтому же объекты неизменяемы.

Следствия, под которые нужно проектировать шаблон:

- **Шаблон рендерится один раз на поколение.** Отрендеренный объект заморожен на всё время жизни
  поколения; node-controller никогда не перерендеривает и не патчит его.
- **Новый текст шаблона или новый конфиг провайдера сами по себе до существующих машин не
  доезжают.** Они подхватываются следующим поколением — когда пользователь изменит поле из
  `rolloutFields` либо оператор принудительно вызовет перекат аннотацией `manual-rollout-id` на
  NodeGroup.
- **Рендер обязан быть чистой функцией от контекста.** Всё остальное (время, случайность, сеть,
  переменные окружения) недоступно и сделало бы вопрос «изменилось ли что-нибудь» неразрешимым.

## Структура файла

```yaml
version: v2

# Обязательно. Поля спеки InstanceClass, изменение которых требует пересоздания машин,
# в виде путей через точку.
rolloutFields:
  - flavorName
  - rootDisk.size

# Необязательно. Дополнительные поля, которые node-controller проставит в собираемый им
# MachineDeployment (сам MachineDeployment — generic, ваш шаблон его не рендерит).
# Ключ — путь внутри spec.template.spec. Значение — go-template с той же песочницей
# и тем же контекстом, что и шаблон машины ниже.
machineDeployment:
  additionalFields:
    failureDomain: "{{ .zone }}"

# Обязательно. go-template вашего инфраструктурного MachineTemplate.
template: |
  apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
  kind: OpenStackMachineTemplate
  spec:
    template:
      spec:
        flavor: {{ .instanceClass.flavorName | quote }}
```

Файл доставляется в CAPI-секрете провайдера ровно так же, как раньше: для встроенных модулей это
`d8-cloud-provider-<type>-capi` в `kube-system`, для внешних — любой секрет с меткой
`cloud-provider.deckhouse.io/ephemeral-nodes-templates: capi` (см. ADR «External cloud provider
module»). Положите файл в каталог `capi/` своего модуля — helm-шаблон секрета подхватит его по
имени файла.

Разбор строгий: неизвестный ключ, пустой шаблон, отсутствующий `rolloutFields`, некорректный путь
поля или непарсящийся шаблон делают контракт невалидным, и reconcile падает с громкой ошибкой.

## Контекст рендера — пять корней, и ничего больше

| Корень | Тип | Что это |
|---|---|---|
| `.instanceClass` | map | **Спека** вашего `<Provider>InstanceClass` как есть. Числа приходят как JSON-числа (float64) — для целочисленного вывода используйте `\| int`. |
| `.provider` | map | Поддерево вашего провайдера в секрете `d8-node-manager-cloud-provider`. Собственное имя внутри собственного файла больше писать не нужно. |
| `.zone` | string | Зона, для которой рендерится поколение. |
| `.nodeGroup.name` | string | Имя NodeGroup — для тегов и меток внутри `spec`. |
| `.cluster` | map | `{uuid, podSubnet}`. |

Ни `.Values`, ни `.Chart`, ни `.Files`, ни `.Release`: node-manager — не helm, а v1-движок лишь
имитировал values-дерево, чтобы при миграции не пришлось переписывать шаблоны.

## Правила

1. **Рендерьте только `apiVersion`, `kind` и `spec`.** `metadata` отвергается: node-controller
   владеет именем (в нём закодировано поколение), метками (`heritage`, `module`, `node-group` — по
   ним идут все выборки, прюн и уборка) и аннотациями (в них хранится снимок для решения о
   перекате).
2. **Отрендеренные `apiVersion`/`kind` должны совпадать с `capiMachineTemplateAPIVersion`/
   `capiMachineTemplateKind` из вашего registration-секрета**, иначе reconcile упадёт.
3. **Опциональные поля читайте через `get` или защищайте `hasKey`.** Песочница работает с
   `missingkey=error`, поэтому `.instanceClass.maybeAbsent` — это ошибка рендера, а не пустая
   строка. Так задумано: в v1 опечатка отдавала `<no value>` прямо в облако.
4. **Будьте детерминированы.** Двойной рендер с тем же контекстом обязан дать тот же объект.
5. **Падайте громко, если входных данных не хватает** — `fail "…"` или `required "…" value`. Не
   заминайте проблему дефолтом, который молча создаст не ту машину. Имя NodeGroup, InstanceClass и
   зону в сообщение добавит node-controller — повторять их не нужно.

## Функции

Песочница — это [sprig](https://masterminds.github.io/sprig/) плюс helm-овские `toYaml`,
`fromYaml`, `toJson`, `fromJson`, `required`. Удалены и недоступны по построению:

| Группа | Примеры |
|---|---|
| часы | `now`, `date`, `dateInZone`, `ago`, `toDate`, `duration` |
| случайность | `randAlphaNum`, `randBytes`, `shuffle`, `uuidv4` |
| криптография и секреты | `genPrivateKey`, `genCA`, `genSelfSignedCert`, `encryptAES`, `bcrypt`, `htpasswd` |
| окружение хоста | `env`, `expandenv`, `getHostByName` |
| только helm | `include`, `tpl`, `lookup` |

Использование любой из них — ошибка парсинга, поэтому в кластер такой шаблон не попадёт. Точный
набор функций зафиксирован голден-тестом
(`internal/machinetemplate/testdata/sandbox_functions.txt`), так что обновление sprig, добавляющее
функцию, проходит через ревью, а не принимается молча.

Ловушки, о которых стоит знать:

- `default` срабатывает на **любое** falsy-значение: `0`, `false` и `""` тоже берут дефолт. Это то
  же поведение helm, которое было и в вашем v1-шаблоне, — помните о нём, когда `0` осмыслен.
- `get dict "key"` возвращает пустое значение для отсутствующего ключа — именно это позволяет
  `get .instanceClass "diskType" | default "network-hdd"` работать при `missingkey=error`.
- Обход возможно отсутствующего списка: `{{- range (get .instanceClass "subnets" | default list) }}`.

## rolloutFields — что пересоздаёт машины

`rolloutFields` — это ваш ответ на один вопрос: *какие поля InstanceClass нельзя изменить на живой
VM?* Знает это только ваша команда. Поля вне списка по-прежнему рендерятся в объект — они просто
сами по себе не создают новое поколение, и изменение доезжает до машин со следующим перекатом.

Как node-controller это использует:

- На объекте поколения хранится **вся** спека InstanceClass
  (`node.deckhouse.io/applied-instance-class`, рядом с `applied-rollout-id` и
  `applied-generation`), а `rolloutFields` применяется только в момент сравнения. Поэтому **изменение списка релизом провайдера само по себе никогда не катит машины** —
  границу можно свободно двигать от релиза к релизу.
- Сравнение идёт **по значениям** после нормализации: `50` — это `50` независимо от Go-типа и
  способа сериализации. Байтовых голденов, которых нужно бояться, больше нет.
- Отсутствующее поле и явный `null` считаются одинаковыми.
- `manual-rollout-id` на NodeGroup обрабатывает сам node-controller для всех провайдеров; в вашем
  файле его не должно быть.

Как выбирать список:

- Включайте всё, что облако не умеет менять на живой машине: flavor/CPU/память, образ, диски, сети,
  группы безопасности, теги, задаваемые при создании.
- Исключайте поля, описывающие не VM. Реальные примеры из миграции: `capacity` у openstack
  (подсказка автоскейлеру для scale-from-zero) и `etcdDisk` у DVP (параметр мастеров) в списке не
  значатся — иначе правка, не относящаяся к воркерам, перекатила бы весь парк.
- Когда облако научится менять поле на лету (hotplug памяти, изменяемые теги), удаление поля из
  списка — однострочный релиз, и он ни у кого ничего не перекатит.

## machineDeployment.additionalFields

MachineDeployment собирает node-controller, а не ваш шаблон. Если вам нужны дополнительные поля в
нём — объявите их здесь: ключ — путь внутри `spec.template.spec`, значение — go-template,
рендерящийся в той же песочнице и с теми же пятью корнями контекста, что и шаблон машины. Сегодня
это нужно одному провайдеру и для одного поля:

```yaml
machineDeployment:
  additionalFields:
    failureDomain: "{{ .zone }}"
```

Значение компилируется при загрузке контракта, поэтому сломанное выражение падает так же, как
сломанный шаблон машины. Результат всегда записывается строкой.

## Миграция с v1

| v1 | v2 |
|---|---|
| `.Values.nodeManager.internal.cloudProvider.<type>.…` | `.provider.…` |
| `.nodeGroup.instanceClass.…` | `.instanceClass.…` |
| `.zoneName` | `.zone` |
| `.Values.global.discovery.clusterUUID` / `.podSubnet` | `.cluster.uuid` / `.cluster.podSubnet` |
| `.nodeGroup.name` | `.nodeGroup.name` (без изменений) |
| блок `metadata:` + `include "helm_lib_module_labels"` | — (metadata ставит node-controller) |
| `instance-class.checksum` | `rolloutFields` |
| `machine-deployment-spec-patch.yaml` | `machineDeployment.additionalFields` |
| прямой путь к опциональному полю | `get` / `hasKey` (missingkey=error) |

Переключение живого кластера **не перекатывает** машины: при первом v2-reconcile node-controller
находит шаблон, на который уже ссылается MachineDeployment (объект с хэш-именем эры v1), записывает
снимок в его аннотации и объявляет его текущим поколением. Нумерация поколений
(`<ng>-<хэш-зоны>-gen1`) начинается со следующего реального изменения.

## Как проверить свой шаблон

Каждый `capi/template.yaml` в репозитории разбирается тестом, который ищет их глобом, — так новый
провайдер получает валидацию контракта сразу, как только положит файл. Сверх этого харнесс
паритета в
`modules/040-node-manager/images/node-controller/src/internal/machinetemplate/provider_parity_test.go`
берёт по одной фикстуре на провайдера и требует:

1. чтобы v2-шаблон рендерил ровно то же, что рендерил архивный v1-шаблон, и
2. чтобы решение по `rolloutFields` совпадало с решением v1-чексуммы для каждого изменённого поля,
   а каждое осознанное расхождение было перечислено и обосновано в тесте.

Добавьте своего провайдера туда до мержа миграции. Чеклист самопроверки:

- [ ] `version: v2`, непустой `template`, непустой `rolloutFields`.
- [ ] В отрендеренном объекте нет `metadata`.
- [ ] `apiVersion`/`kind` совпадают с registration-секретом.
- [ ] Каждое опциональное поле читается через `get`/`hasKey`.
- [ ] Нет функций времени/случайности/окружения/криптографии (они и не распарсятся).
- [ ] `rolloutFields` покрывает всё, что облако не меняет на живой VM, и не содержит того, что не
      является свойством VM.
- [ ] Фикстура паритета добавлена, оба теста паритета зелёные.
