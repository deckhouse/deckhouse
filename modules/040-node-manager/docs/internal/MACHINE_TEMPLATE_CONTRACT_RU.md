Это полное описание файла `capi/template.yaml`, который поставляет модуль cloud-провайдера.
**Чего нет в этом документе — того нет в контракте**: ничего сверх описанного здесь шаблону не
дают, а чтобы расширить контракт, придётся поднять `version`.

## Что node-manager делает с вашим файлом

Для каждой зоны NodeGroup node-controller сначала решает, нужно ли пересоздавать машины. Если
нужно — собирает по вашему шаблону новый объект MachineTemplate и переключает на него
MachineDeployment. Машины пересоздаются именно из-за смены **имени**: так устроен CAPI, и по той
же причине сами объекты менять нельзя.

Из этого следуют три вещи, которые нужно держать в голове, когда пишете шаблон:

- **Шаблон применяется один раз — при создании поколения.** Дальше объект остаётся таким,
  каким его собрали: node-controller не пересобирает его и ничего в нём не меняет.
- **Новый текст шаблона или новый конфиг провайдера сами по себе до существующих машин не
  добираются.** Их подхватит следующее поколение. Создать его могут три события: пользователь
  меняет поле из `rolloutFields`, оператор ставит на NodeGroup аннотацию `manual-rollout-id`,
  либо релиз провайдера добавляет в `rolloutFields` поле, которое пользователь уже успел
  изменить (см. ниже).
- **Результат должен зависеть только от входных данных.** Ко времени, случайным числам, сети и
  переменным окружения шаблон доступа не имеет. Иначе на вопрос «изменилось ли что-нибудь»
  ответить было бы нельзя: каждая сборка давала бы новый результат.

## Структура файла

```yaml
version: v2

# Обязательно. Поля InstanceClass, изменение которых требует пересоздания машин,
# записанные путями через точку.
rolloutFields:
  - flavorName
  - rootDisk.size

# Необязательно. Дополнительные поля для MachineDeployment: его собирает node-controller,
# ваш шаблон его не описывает.
# Ключ — путь внутри spec.template.spec, значение — такой же go-template
# и с теми же данными, что и шаблон машины ниже.
machineDeployment:
  additionalFields:
    failureDomain: "{{ .zone }}"

# Обязательно. Сам шаблон машины.
template: |
  apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
  kind: OpenStackMachineTemplate
  spec:
    template:
      spec:
        flavor: {{ .instanceClass.flavorName | quote }}
```

Файл читается строго. Неизвестный ключ, пустой шаблон, отсутствующий `rolloutFields`, неверно
записанный путь поля или шаблон с синтаксической ошибкой делают весь файл негодным — работа
завершается ошибкой, и это видно сразу.

## Доставка

Файл доставляется в CAPI-секрете провайдера — тем же путём, что и раньше:

- встроенные модули: `d8-cloud-provider-<type>-capi` в `kube-system`;
- внешние модули: любой секрет с меткой
  `cloud-provider.deckhouse.io/ephemeral-nodes-templates: capi` (см. ADR «External cloud
  provider module»).

Положите файл в каталог `capi/` своего модуля — helm-шаблон секрета подхватит его по имени
файла.

## Данные, доступные шаблону, — пять корней и ничего больше

| Корень | Тип | Что это |
|---|---|---|
| `.instanceClass` | map | Содержимое `spec` вашего `<Provider>InstanceClass` как есть. Числа приходят как float64 — чтобы вывести целое, используйте `\| int`. |
| `.provider` | map | Поддерево вашего провайдера в секрете `d8-node-manager-cloud-provider`. Собственное имя внутри собственного файла больше писать не нужно. |
| `.zone` | string | Зона, для которой собирается объект. |
| `.nodeGroup.name` | string | Имя NodeGroup — для тегов и меток внутри `spec`. |
| `.cluster` | map | `{uuid, podSubnet}`. |

Ни `.Values`, ни `.Chart`, ни `.Files`, ни `.Release`: node-manager — не helm. Старый движок
подделывал привычное helm-дерево только затем, чтобы при переезде не пришлось переписывать
шаблоны.

## Правила

1. **Выводите только `apiVersion`, `kind` и `spec`.** `metadata` в шаблоне запрещена: имя,
   метки и аннотации ставит node-controller. В имени закодировано поколение, по меткам
   (`heritage`, `module`, `node-group`) он находит свои объекты при очистке, а в аннотациях
   хранит снимок, по которому решает, нужно ли пересоздавать машины.
2. **`apiVersion` и `kind` в собранном объекте должны совпадать с
   `capiMachineTemplateAPIVersion` и `capiMachineTemplateKind`**, которые ваш модуль публикует в
   своём секрете при регистрации, — иначе работа завершится ошибкой.
3. **Необязательные поля читайте через `get` или проверяйте `hasKey`.** Обращение к полю,
   которого нет (`.instanceClass.maybeAbsent`), считается ошибкой, а не пустой строкой. Так
   сделано намеренно: раньше опечатка превращалась в текст `<no value>` и уезжала прямо в
   облако.
4. **Шаблон должен быть предсказуем.** Дважды применив его к одним и тем же данным, вы обязаны
   получить один и тот же объект.
5. **Если данных не хватает, скажите об этом явно** — через `fail "…"` или `required "…" value`.
   Не подставляйте вместо них значение по умолчанию: так вы молча создадите не ту машину. Имя
   NodeGroup, InstanceClass и зону к сообщению добавит node-controller, повторять их не нужно.

## Функции

Шаблону доступны функции [sprig](https://masterminds.github.io/sprig/) и привычные по helm
`toYaml`, `fromYaml`, `toJson`, `fromJson`, `required`. Убраны — и обойти это нельзя:

| Группа | Примеры |
|---|---|
| часы | `now`, `date`, `dateInZone`, `ago`, `toDate`, `duration` |
| случайность | `randAlphaNum`, `randBytes`, `shuffle`, `uuidv4` |
| криптография и секреты | `genPrivateKey`, `genCA`, `genSelfSignedCert`, `encryptAES`, `bcrypt`, `htpasswd` |
| окружение хоста | `env`, `expandenv`, `getHostByName` |
| только helm | `include`, `tpl`, `lookup` |

Любая из них — ошибка при чтении шаблона, так что в кластер он не попадёт. Полный список
доступных функций записан в файле `internal/machinetemplate/testdata/sandbox_functions.txt`, и
тест сверяется с ним: если обновление sprig принесёт новую функцию, тест упадёт, и её придётся
разрешить осознанно.

О чём стоит помнить:

- `default` срабатывает на **любое** пустое значение: `0`, `false` и `""` тоже заменяются на
  значение по умолчанию. Так же вёл себя и ваш прежний шаблон — помните об этом, когда `0` для
  вас осмыслен.
- `get dict "key"` возвращает пустое значение для отсутствующего ключа — именно это позволяет
  `get .instanceClass "diskType" | default "network-hdd"` работать при `missingkey=error`.
- Обход возможно отсутствующего списка: `{{- range (get .instanceClass "subnets" | default list) }}`.

## rolloutFields — что пересоздаёт машины

`rolloutFields` — это ваш ответ на один вопрос: *какие поля InstanceClass нельзя изменить на
живой машине?* Знает это только ваша команда. Поля вне списка по-прежнему попадают в объект —
просто сами по себе они не создают новое поколение, и правка дойдёт до машин при следующем
пересоздании.

Как node-controller использует список:

- На объекте поколения хранится снимок **всего** `spec` из InstanceClass
  (`node.deckhouse.io/applied-instance-class`, рядом с `applied-rollout-id` и
  `applied-generation`); `rolloutFields` фильтрует сравнение, а не снимок.
- Поэтому **убрать** поле из списка можно всегда — машины от этого не пересоздаются.
- **Добавить** поле безопасно, только пока оно не менялось с момента создания текущего
  поколения: в снимке лежит значение на тот момент, и расширенный список сравнивается именно с
  ним. Если пользователь успел это поле изменить, машины его NodeGroup пересоздадутся при
  ближайшей проверке. Убедитесь в этом перед тем, как расширять список, либо предупредите об
  этом в release note.
- Сравниваются **значения**, приведённые к общему виду: `50` — это `50`, каким бы типом оно ни
  пришло и как бы ни было записано. Тестов, сверявших побайтово, больше нет, и бояться их не
  нужно.
- Отсутствующее поле и явный `null` считаются равными.
- `manual-rollout-id` на NodeGroup обрабатывает сам node-controller для всех провайдеров; в
  вашем файле его не должно быть.

Как выбирать список:

- Включайте всё, что облако не умеет менять на живой машине: flavor, CPU, память, образ, диски,
  сети, группы безопасности, теги, которые задаются при создании.
- Не включайте поля, которые описывают не саму машину. Два примера из переезда: `capacity` у
  openstack (подсказка автоскейлеру, чтобы поднять группу с нуля) и `etcdDisk` у DVP (параметр
  мастеров) в списки не попали — иначе посторонняя правка пересоздавала бы весь парк машин.
- Когда облако научится менять поле на лету — добавлять память, править теги, — достаточно
  убрать его из списка: правка в одну строку, и ни одна машина не пересоздастся.

## machineDeployment.additionalFields

MachineDeployment собирает node-controller, а не ваш шаблон. Если вам нужны в нём свои поля,
объявите их здесь: ключ — путь через точку внутри `spec.template.spec`, значение — такой же
go-template с теми же пятью корнями данных, что и шаблон машины. Сегодня это нужно одному
провайдеру и ради одного поля:

```yaml
machineDeployment:
  additionalFields:
    failureDomain: "{{ .zone }}"
```

Выражение компилируется вместе с контрактом, поэтому ошибка в нём видна сразу — так же, как
ошибка в шаблоне машины. Результат всегда записывается строкой.

## Миграция с v1

| v1 | v2 |
|---|---|
| `.Values.nodeManager.internal.cloudProvider.<type>.…` | `.provider.…` |
| `.nodeGroup.instanceClass.…` | `.instanceClass.…` |
| `.zoneName` | `.zone` |
| `.Values.global.discovery.clusterUUID` / `.podSubnet` | `.cluster.uuid` / `.cluster.podSubnet` |
| `.nodeGroup.name` | `.nodeGroup.name` (без изменений) |
| блок `metadata:` + `include "helm_lib_module_labels"` | — (metadata ставит node-controller) |
| `instance-class.checksum` | `rolloutFields` |
| `machine-deployment-spec-patch.yaml` | `machineDeployment.additionalFields` |
| прямой путь к опциональному полю | `get` / `hasKey` (missingkey=error) |

Переход живого кластера на v2 машины **не пересоздаёт**: node-controller находит объект, на
который уже ссылается MachineDeployment (тот самый, с чексуммой в имени), дописывает в его
аннотации снимок и считает его текущим поколением. Нумерация поколений
(`<ng>-<хэш-зоны>-gen1`) начинается со следующего реального изменения.

## Как проверить свой шаблон

Отдельный тест сам находит все `capi/template.yaml` в репозитории и читает их, так что новый
провайдер получает проверку своего файла сразу, как только его добавит. Кроме того, есть тесты,
которые сравнивают старый и новый движок; они лежат в
`modules/040-node-manager/images/node-controller/src/internal/machinetemplate/provider_parity_test.go`
берут по одному набору данных на провайдера и требуют:

1. чтобы новый шаблон давал ровно тот же объект, что и сохранённый старый;
2. чтобы для каждого изменённого поля ответ «пересоздавать машины или нет» совпадал с ответом
   старой чексуммы, а любое осознанное расхождение было перечислено и обосновано в тесте.

Добавьте туда своего провайдера до того, как переезд попадёт в main. Что проверить самому:

- [ ] `version: v2`, непустой `template`, непустой `rolloutFields`.
- [ ] В собранном объекте нет `metadata`.
- [ ] `apiVersion`/`kind` совпадают с registration-секретом.
- [ ] Каждое опциональное поле читается через `get`/`hasKey`.
- [ ] Нет функций времени/случайности/окружения/криптографии (они и не распарсятся).
- [ ] `rolloutFields` покрывает всё, что облако не меняет на живой машине, и не содержит того,
      что саму машину не описывает.
- [ ] Данные для сравнения старого и нового движка добавлены, оба теста проходят.
