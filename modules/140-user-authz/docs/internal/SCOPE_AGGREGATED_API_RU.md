# Чтение агрегированных API с областью фильтрации (`--scope` для расширений APIService)

**Кому:** командам, которые поддерживают агрегированный API-сервер (`APIService` с полем `spec.service`)
и хотят, чтобы для его ресурсов работала команда `d8 k get <ресурс> -A --scope=...`, а также
мейнтейнерам патча kube-apiserver `scope-aggregated-api.patch` из команды platform-security.

Пользовательская сторона `--scope` (области фильтрации, заголовки `X-Deckhouse-Scope` и
`X-Deckhouse-Project`, ответы) описана в документе
[Листинг ресурсов с фильтрацией по правам доступа](../../../../docs/documentation/pages/admin/configuration/access/authorization/FILTERED-LISTING_RU.md).
Здесь описано только то, что меняется, когда ресурс обслуживает агрегированный API-сервер.

## Проблема

Для встроенных ресурсов и CRD фильтр областей работает в хранилище kube-apiserver: запрос на чтение,
который RBAC отклонил, фильтр авторизации пропускает дальше, а декоратор хранилища фильтрует ответ.
У агрегированного API в kube-apiserver нет хранилища — kube-aggregator только проксирует запрос. Без
патча запрос `list` такого ресурса с `--scope` от пользователя без прав получает обычный `403`, а
запрос пользователя с правами уходит в расширение без фильтрации.

С патчем kube-apiserver сам вычисляет разрешённый набор неймспейсов и передаёт его серверу расширения
в доверенных заголовках. Фильтрует расширение.

## Как это работает

1. **Включение.** У `APIService` есть аннотация `scope.deckhouse.io/resources: <plural>[,<plural>...]` —
   имена ресурсов во множественном числе внутри `spec.group`. Пробелы по краям отбрасываются,
   повторы удаляются, каждое имя должно быть DNS-меткой. Некорректные элементы (с `/`, пустые)
   пропускаются с предупреждением в логе kube-apiserver. Аннотация задаётся на уровне `APIService`, то
   есть для каждой версии отдельно: ресурс считается подключённым, пока его указывает хотя бы один
   `APIService` группы, но прокси каждой версии фильтрует только то, что указано в её собственном
   `APIService`.
2. **Обход отказа авторизации.** Для `list`, `get` или `watch` без субресурса с корректным заголовком
   `X-Deckhouse-Scope` фильтр авторизации проверяет, хранится ли ресурс в kube-apiserver с фильтром
   областей, а если нет — подключил ли его какой-либо `APIService`. Если RBAC отклонил запрос, а ресурс
   подключён, запрос с отметкой об обходе передаётся в kube-aggregator. Ресурс, который хранится в
   kube-apiserver, всегда имеет приоритет над аннотацией.
3. **Разрешённый набор.** kube-aggregator вычисляет набор той же функцией, что и декоратор хранилища:
   - классификация по области (`projects`, `project:<имя>`, `system`); для `accessible` не
     вычисляется;
   - только для запроса с обходом — нижняя граница RBAC (RBAC floor): неймспейсы, где разрешены именно этот ресурс
     и эта операция, по одному запросу `SelfScopedAccessReview` к `permission-browser-apiserver`;
   - если применимы обе части, набор — их пересечение. Результат с `allowed: false` не даёт ничего,
     какие бы неймспейсы в нём ни были перечислены.

   `permission-browser-apiserver` читает ту же аннотацию из своего индекса `APIService` и отвечает на
   такой запрос неймспейсами, где RBAC разрешает операцию; чтение ресурса aggregated API без
   подключения по-прежнему получает `NotFilterable` (в kube-apiserver — 403). Индекс следит за
   объектами `APIService` через informer, поэтому подключение начинает действовать в течение
   нескольких секунд; до этого пользователи без прав получают 403, но никогда не нефильтрованный
   ответ. На cluster-scoped ресурс, указанный в аннотации, индекс отвечает `NotFilterable` и один раз
   пишет предупреждение в лог. После снятия аннотации kube-apiserver сразу перестаёт пропускать
   запросы, а консоль может видеть неймспейсы, пока индекс не получит событие.
4. **Режим.** `filtered` — RBAC отклонил запрос, набор задаёт границу того, что вообще можно отдать.
   `narrowed` — RBAC разрешил запрос, пользователь только сужает выборку.
5. **Заголовки.** kube-aggregator устанавливает в проксируемом запросе:

   | Заголовок | Значение |
   |---|---|
   | `X-Deckhouse-Scope-Mode` | `filtered` или `narrowed` |
   | `X-Deckhouse-Scope-Namespaces` | Отсортированные имена неймспейсов через `,`. Пустое значение — пустой набор |

   Оба заголовка всегда передаются вместе. Заголовки идентичности (`X-Remote-User`, `X-Remote-Group`,
   `X-Remote-Extra-*`) и клиентский сертификат front-proxy добавляются, как для любого проксируемого
   запроса.

### Когда передаются заголовки

| Пользователь | `accessible` | `projects`, `project:<имя>`, `system` |
|---|---|---|
| RBAC разрешает запрос | Заголовков нет, запрос передаётся без изменений | `narrowed` + классификация |
| RBAC отклоняет запрос | `filtered` + нижняя граница RBAC | `filtered` + классификация ∩ нижняя граница RBAC |

Если у пользователя есть права, а ресурс не подключён в `APIService` этой версии, запрос передаётся без
заголовков — область игнорируется, как для встроенного ресурса без фильтра. Запрос без
`X-Deckhouse-Scope` никогда не получает этих заголовков.

### Что kube-apiserver отвечает сам

| Ситуация | Ответ |
|---|---|
| URL с неймспейсом, `get`, неймспейс вне набора, режим `filtered` | `404 NotFound`, запрос не передаётся |
| URL с неймспейсом, `list`/`watch`, неймспейс вне набора (любой режим) | Передаётся с пустым набором; расширение должно вернуть пустой результат |
| URL с неймспейсом, `get`, неймспейс вне набора, режим `narrowed` | Передаётся с пустым набором; расширение должно ответить `404` |
| Заголовки превысят лимит получателя (см. ниже) | `400 BadRequest` с просьбой указать более узкую область |
| Имя неймспейса в наборе не является DNS-меткой | `500 InternalError`; открытый watch-запрос завершается |
| Область `projects`/`project` при выключенном multitenancy-manager | `400 BadRequest` |
| `permission-browser-apiserver` не ответил вовремя, вернул `429` или `5xx` | `503` с `Retry-After` |
| RBAC отклоняет запрос, а сервис прав разрешает его во всём кластере | `403` (две цепочки расходятся) |
| Любая другая ошибка вычисления набора | `403` |
| Запрос с обходом дошёл до версии `APIService`, которая не фильтрует ресурс (аннотацию удалили, ресурс подключён в другой версии) | `403` «the aggregated API server does not filter this resource by scope» |
| Запрос с обходом, для которого не вычислена нижняя граница RBAC | `403` |
| Некорректный `X-Deckhouse-Scope`/`X-Deckhouse-Project` | `400` до авторизации (как раньше) |

Ни один из этих ответов не называет область и набор. kube-aggregator никогда не передаёт запрос,
отклонённый RBAC, без набора, по которому его нужно фильтровать.

**Лимит размера заголовков.** Защищённый сервер `k8s.io/apiserver` выставляет `MaxHeaderBytes` в 1 МиБ,
и его HTTP/2-сервер выводит лимит списка заголовков из этого значения. kube-aggregator оценивает размер
заголовков исходящего запроса — строка запроса, `Host`, все заголовки, включая добавляемые транспортом
`X-Remote-*`, плюс 32 байта на каждое поле — и отклоняет запрос с `400`, если размер больше 1 МиБ за
вычетом запаса в 16 КиБ. Сервер расширения с меньшим лимитом будет сам отклонять большие наборы.

### Когда поведение остаётся стандартным

- Ни один `APIService` не подключил ресурс: запрос с областью от пользователя без прав получает обычный
  `403`.
- kube-aggregator запущен без резолверов областей (нет loopback-конфигурации): аннотации всех
  `APIService` игнорируются с записью в лог на уровне `V(2)`, запросы с областью работают как без
  патча.
- Локальный `APIService` (без `spec.service`) подключить нельзя, см. [Модель угроз](#модель-угроз).

## Контракт получателя

Сервер расширения, который указал ресурс в `scope.deckhouse.io/resources`, ОБЯЗАН:

1. **Доверять заголовкам только в запросе, который аутентифицировал его аутентификатор requestheader
   (front-proxy):** клиентский сертификат выпущен requestheader CA (опубликован в
   `kube-system/extension-apiserver-authentication`, ключ `requestheader-client-ca-file`), CN входит в
   `requestheader-allowed-names`, если этот список не пуст, а заголовок имени пользователя не пуст
   (по умолчанию `X-Remote-User`; имена заголовков берите из того же ConfigMap). В любом другом запросе —
   прямой клиент, bearer-токен, сертификат другого CA — заголовки игнорируются, запрос авторизуется
   как обычно. kube-apiserver удаляет клиентские копии только из запросов, которые проксирует сам;
   запрос, пришедший в Service напрямую, может содержать что угодно.
2. **Нет `X-Deckhouse-Scope-Mode`:** ограничений нет, запрос обслуживается как обычно.
3. **Есть `X-Deckhouse-Scope-Mode`:** отдавать только объекты из неймспейсов, перечисленных в
   `X-Deckhouse-Scope-Namespaces`. Пустой или отсутствующий `X-Deckhouse-Scope-Namespaces` — пустой
   набор: не отдавать ничего.
4. **Неизвестное значение режима:** отклонить запрос (например, с `400`) и ни в коем случае не
   отдавать его без фильтрации.
5. **Cluster-scoped объекты** (без неймспейса) никогда не входят в набор: ограниченный запрос не отдаёт
   ни одного из них.
6. **Режим `filtered`:** собственный делегированный `SubjectAccessReview` расширения для запроса по всему
   кластеру вернёт отказ — RBAC уже отклонил этот запрос в kube-apiserver. Пропуск этой проверки и
   делает механизм рабочим, но он допустим только при выполнении правила 1, только для
   `list`/`get`/`watch` подключённого ресурса и только для неймспейсов из набора. Всё остальное
   остаётся запрещённым.
   **Режим `narrowed`:** авторизовать как обычно, затем фильтровать.
7. **Фильтровать до преобразования в Table.** `kubectl` и `d8 k` запрашивают `as=Table`. Фильтруйте в
   хранилище (`List`/`Get`/`Watch` REST-хранилища или предикат по `metadata.namespace`), а не в уже
   сериализованном ответе. События watch-запроса фильтруются по одному.
8. **`get` вне набора** отвечает `404 NotFound` так же, как для несуществующего объекта, и не называет
   область и набор.

### Рекомендуемая реализация

Этот контракт реализует библиотека получателя [`github.com/deckhouse/deckhouse/pkg/api-extension-sdk/scope`](../../../../pkg/api-extension-sdk/scope/README.md); расширение, которое не может её использовать, реализует проверку так, как описано ниже.

**Расширение на `k8s.io/apiserver`.** `WithAuthentication` удаляет заголовки `X-Remote-*` после
аутентификации, поэтому проверка должна выполняться раньше — фильтром обработчиков снаружи
`WithAuthentication` в `Config.BuildHandlerChainFunc`:

- Соберите верификатор из `Config.Authentication.RequestHeaderConfig` так же, как
  `DelegatingAuthenticatorConfig.New` собирает аутентификатор requestheader:
  `headerrequest.NewDynamicVerifyOptionsSecure(cfg.CAContentProvider.VerifyOptions, cfg.AllowedClientNames, cfg.UsernameHeaders, cfg.UIDHeaders, cfg.GroupHeaders, cfg.ExtraHeaderPrefixes)`.
  Он оборачивает `x509request.NewDynamicCAVerifier`: CA перечитывается вместе с ConfigMap, CN
  сверяется со списком разрешённых имён (при пустом списке подходит любое имя), а при пустом
  заголовке имени пользователя аутентификация не проходит.
- Вызывайте `AuthenticateRequest` для копии запроса, `req.Clone(ctx)` (она копирует заголовки
  целиком): при успешной проверке аутентификатор удаляет заголовки `X-Remote-*` из переданного ему
  запроса, а `WithAuthentication` дальше по цепочке они ещё нужны.
- Если `RequestHeaderConfig` равен nil или `VerifyOptions()` сообщает об отсутствии CA, заголовкам не
  доверять никогда.
- При успешной проверке перенесите режим и набор в контекст запроса. В обоих случаях удалите из
  запроса `X-Deckhouse-Scope-Mode` и `X-Deckhouse-Scope-Namespaces`: `WithAuthentication` их не
  удаляет, а код дальше по цепочке должен читать только значение из контекста.
- Оберните авторизатор: для запроса с режимом `filtered` в контексте разрешайте `list`/`get`/`watch`
  подключённых ресурсов без делегированной проверки; фильтрует хранилище по набору.

**Сервер на `net/http`.** Запрашивайте клиентский сертификат в `tls.Config` (`VerifyClientCertIfGiven`
или строже). Проверяйте `r.TLS.PeerCertificates[0]` через `leaf.Verify` по пулу из requestheader CA с
`KeyUsages: []x509.ExtKeyUsage{x509.ExtKeyUsageClientAuth}`, остальные сертификаты цепочки передавайте
как промежуточные. Сверяйте CN с `requestheader-allowed-names` (если список не пуст) и требуйте
непустой заголовок имени пользователя. Перечитывайте CA при изменении ConfigMap. TLS должен
завершаться в том же процессе, где выполняется проверка: sidecar, который завершает TLS перед
сервером, нарушает контракт.

## Семантика watch-запросов

- Набор, переданный с watch-запросом, фиксирован на всё время жизни потока. Пока поток открыт,
  kube-aggregator в фоне пересчитывает набор с теми же входными данными через каждый интервал
  обновления.
- Поток завершается, когда пересчитанный набор отличается от переданного, когда запрос больше не
  фильтруется или не разрешён (например, пользователь получил права на весь кластер или области
  проектов отключили), когда `APIService` удалён или больше не указывает ресурс в аннотации, а также
  когда пересчёт не удаётся в течение периода ожидания. Единичные ошибки
  пересчёта поток не закрывают, он работает со старым набором.
- `timeoutSeconds` фильтруемого watch-запроса ограничен сверху: отсутствующее, нулевое, отрицательное,
  нечисловое или большее значение заменяется на предельное.
- Завершение потока отменяет контекст проксируемого запроса. Перед этим обычный HTTP watch-запрос в
  JSON или protobuf получает событие `ERROR` со Status `410 Expired`: kube-aggregator передаёт ответ
  только целыми фреймами, отбрасывает фрейм, оборванный отменой, и дописывает событие в кодировке
  потока. Рефлектор client-go после этого заново запрашивает список, и кэш информера получает объекты
  нового набора и теряет выпавшие. CBOR, другие типы содержимого, сжатые ответы, ответы не с кодом 200,
  потоки, которые не удаётся разобрать, и фреймы больше 16 МиБ передаются как есть и просто
  завершаются, без события; ответ 1xx перед 200 не учитывается.
- Watch-запрос через websocket после hijack на контекст не смотрит, поэтому kube-aggregator явно
  закрывает перехваченное клиентское соединение, без события. Клиент websocket должен сам запросить
  список заново после закрытия соединения, иначе его кэш сохранит объекты из выпавших неймспейсов и не
  получит уже существующие объекты из вошедших.
- Задержка отзыва доступа: примерно интервал обновления + TTL кэша резолвера + время распространения
  изменений в `permission-browser-apiserver`; пока пересчёт не удаётся — до периода ожидания.

Параметры задаются переменными окружения процесса kube-apiserver и читаются один раз при старте.
Некорректное или неположительное значение заменяется значением по умолчанию с предупреждением в логе.
DKP эти переменные не задаёт.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SCOPEFILTER_WATCH_POLL_INTERVAL` | `1s` | Интервал обновления набора фильтруемых watch-запросов, общий с watch-запросами из хранилища |
| `SCOPEFILTER_RESOLVE_CACHE_TTL` | `1s` (не больше `30s`) | TTL общего кэша ответов классификации и нижней границы RBAC |
| `SCOPEFILTER_PROXIED_WATCH_TIMEOUT` | `5m` | Предел `timeoutSeconds` фильтруемого watch-запроса к агрегированному API |
| `SCOPEFILTER_PROXIED_WATCH_REFRESH_GRACE` | `60s` | Сколько фильтруемый watch-запрос к агрегированному API живёт при неудачных пересчётах |

## Модель угроз

- **Подделка заголовков.** kube-aggregator удаляет клиентские копии `X-Deckhouse-Scope-Mode` и
  `X-Deckhouse-Scope-Namespaces` из каждого проксируемого запроса, независимо от аннотации. Копией
  считается любой заголовок, имя которого совпадает без учёта регистра, если `_` читать как `-`
  (`x-deckhouse-scope-mode`, `X_Deckhouse_Scope_Mode`). Эти имена удаляются и из `Connection`: иначе
  reverse proxy отбросил бы значение, выставленное kube-apiserver, как hop-by-hop заголовок. Остальные
  элементы `Connection`, включая `Upgrade`, сохраняются.
- **Прямое обращение к Service** минует kube-apiserver. Поэтому получатель должен проверять сертификат
  front-proxy (правило 1), а не наличие заголовков.
- **Аннотация включения — это выдача прав уровня администратора.** Тот, кто может изменять
  `APIService`, может открыть данные расширения для запросов с областью от пользователей, которым RBAC
  отказывает. Выборка ограничена их нижней границей RBAC, но отдаёт её расширение, которое может не
  выполнять контракт. В установке по умолчанию это SuperAdmin и другие субъекты с `cluster-admin`
  (включая `system:sudouser` и компоненты платформы, привязанные к `cluster-admin`, например
  multitenancy-manager), группа административного kubeconfig `kubeadm:cluster-admins` (через роль
  `d8:control-plane-manager:admin-kubeconfig-supplement`), а также ServiceAccount cainjector модуля
  cert-manager (`d8-cert-manager/cainjector`), если CA injection включён.
- **Перенаправление `spec.service`** у `APIService` на другой бэкенд — риск стандартного Kubernetes с
  тем же набором субъектов; этот патч его не закрывает.
- **`authorization.deckhouse.io` подключить нельзя:** его `SelfScopedAccessReview` вычисляет нижнюю
  границу RBAC, и запрос с областью к нему вычислял бы границу, вызывая сам себя.
- **Локальные `APIService` подключить нельзя:** их обслуживает сам kube-apiserver, доверенные заголовки
  им не передаются, а запрос с обходом уходит в хранилище, которое отвечает `403`, если ресурс не
  фильтрует декоратор хранилища.
- При изменении `APIService` реестр, к которому обращается фильтр авторизации, и прокси версии могут
  ненадолго расходиться. Обе стороны отклоняют то, что не фильтруют, поэтому в этот момент запрос
  отклоняется, а не обслуживается без фильтрации.

## Наблюдаемость

Метрики (подсистема `apiserver_scopefilter`, все ALPHA):

| Метрика | Значение |
|---|---|
| `apiserver_scopefilter_proxied_namespaces` | Гистограмма размера переданного набора (бакеты 0, 1, 10, 100, 1000, 10000) |
| `apiserver_scopefilter_proxied_watch_closed_total{reason}` | Watch-запросы, завершённые фоновым пересчётом: `set_changed` (набор изменился или запрос больше не фильтруется или не разрешён), `refresh_failed` (истёк период ожидания), `opt_in_withdrawn` (`APIService` удалён или больше не указывает ресурс) |
| `apiserver_scopefilter_proxied_header_limit_rejections_total` | Запросы, отклонённые с `400` из-за лимита заголовков |
| `apiserver_scopefilter_watch_refresh_failures_total` | Неудачные пересчёты; теперь учитывает и watch-запросы к агрегированным API |
| `apiserver_scopefilter_allowed_set_failures_total{operation,reason}` | Новая причина `no_resolvers` (фильтр подключён без резолверов, `403`) |

Ответы, которые kube-aggregator формирует сам, учитываются также в `apiserver_request_terminations_total`.

Аннотации аудита:

| Ключ | Значение |
|---|---|
| `authorization.k8s.io/decision` | `allow-scoped-proxied` для запроса с обходом, который обслуживает агрегированный API (или отклоняет kube-aggregator) |
| `authorization.k8s.io/reason` | `scope filtering mode, aggregated API` |
| `scope.deckhouse.io/proxied-mode` | `filtered` или `narrowed`; только если запрос передан с заголовками |
| `scope.deckhouse.io/proxied-namespaces` | Количество неймспейсов в наборе (число, а не имена); только если запрос передан с заголовками |

Если в группе есть и ресурс, который хранится в kube-apiserver, и такой же ресурс, подключённый
аннотацией в другой версии, фильтр авторизации оставляет решение kube-aggregator, и тот записывает путь
той версии, которая обслужила запрос.

## Проверка расширения

В [scope-aggregated-api-e2e/](scope-aggregated-api-e2e/README_RU.md) лежат тестовое расширение,
манифесты для него и `test/e2e.sh`, который автоматизирует большую часть проверок ниже. Тестовое расширение
построено на `pkg/api-extension-sdk/scope`.

Проверки выполняются на кластере с пропатченным kube-apiserver и аннотацией на `APIService`:

1. **Поддельные заголовки через Service.** Обратитесь к Service расширения напрямую (port-forward или
   из пода) с bearer-токеном пользователя без прав RBAC и заголовками
   `X-Deckhouse-Scope-Mode: filtered`, `X-Deckhouse-Scope-Namespaces: <ns>`. Запрос должен
   авторизоваться как обычно (отказ), а не фильтроваться. Повторите с клиентским сертификатом другого
   CA.
2. **Поддельные заголовки через kube-apiserver.** Передайте те же заголовки, в том числе в вариантах с
   `_` и в нижнем регистре и с перечислением в `Connection`, через kube-apiserver без
   `X-Deckhouse-Scope`. Расширение не должно получить заголовков области.
3. **Пользователь без прав с `--scope`.** `d8 k get <ресурс> -A --scope=accessible --as=<пользователь>`
   возвращает только объекты неймспейсов, где у пользователя есть `list` на этот ресурс;
   `--scope=system` и `--scope=projects` возвращают пересечение. Пользователь совсем без доступа
   получает пустой список, а не `403` и не все объекты.
4. **Вывод в Table.** Те же команды с выводом по умолчанию (Table) и с `-o yaml` возвращают одни и те же
   объекты.
5. **`get` вне набора.** `d8 k` не принимает `--scope` без `-A`, поэтому используйте HTTP API:
   `curl -H "Authorization: Bearer $TOKEN" -H "X-Deckhouse-Scope: accessible" https://<kube-apiserver>/apis/<группа>/<версия>/namespaces/<ns>/<ресурс>/<имя>`.
   Для пользователя без прав и `<ns>` вне набора kube-apiserver отвечает `404`. Для пользователя с
   правами с `X-Deckhouse-Scope: system` и несистемным `<ns>` ответ `404` должно сформировать
   расширение.
6. **Cluster-scoped объекты** никогда не возвращаются в ответ на запрос с областью.
7. **Отзыв доступа в watch-запросе.** Откройте `d8 k get <ресурс> -A --scope=accessible -w --as=<пользователь>`,
   затем выдайте или отзовите RoleBinding в одном из неймспейсов. Поток должен завершиться за
   несколько секунд, `apiserver_scopefilter_proxied_watch_closed_total{reason="set_changed"}` растёт.
   Проверьте, что watch-запрос через websocket тоже завершается.

## Ограничения и дальнейшая работа

- **Watch-запросы через websocket** завершаются без события `410 Expired` (см.
  [Семантика watch-запросов](#семантика-watch-запросов)).
- **Дескриптор решения (вариант B2 из дизайна)** не реализован. Набор передаётся в заголовках и
  ограничен лимитом в 1 МиБ. В варианте B2 kube-apiserver вместо набора передаёт короткоживущий
  непредсказуемый идентификатор решения, привязанный к пользователю. Расширение получает решение по
  этому идентификатору через API (по аналогии с TokenReview) и периодически запрашивает его повторно.
  Это снимает ограничение на размер заголовка и проблему фиксированного набора у watch-запроса, но
  требует нового API и хранилища решений. Интерфейс библиотеки для получателя («дай набор
  неймспейсов для запроса») проектируется так, чтобы переход с заголовков на B2 оставался внутренним
  делом библиотеки.
- Фильтруются только `list`, `get` и `watch` верхнего уровня; субресурсы и изменяющие операции — нет.
