Этот модуль решает, откуда кластер загружает образы и каким путём.

По умолчанию он не решает ничего. Включение модуля само по себе ничего не меняет: при
`mode: Unmanaged` — это значение по умолчанию — компоненты не создаются, конфигурация узлов
не пишется, и кластер продолжает загружать образы из того registry, с которым был
установлен. Управление включается осознанно: `mode: Managed` вместе с указанием registry.

```yaml
apiVersion: deckhouse.io/v1alpha1
kind: ModuleConfig
metadata:
  name: registry
spec:
  version: 1
  enabled: true
  settings:
    mode: Managed
    primary:
      upstream:
        host: registry.deckhouse.io
        path: /deckhouse/ee
        scheme: HTTPS
        auth:
          license: <LICENSE_KEY>
```

Выбирать реализацию не нужно. Кластер, в котором предыдущая реализация этого модуля никогда
не работала, сразу использует текущую. Кластер, в котором работала, использует предыдущую до
перевода её в состояние `Unmanaged`, после чего миграция завершается сама — см.
[как завершить миграцию](faq.html#как-завершить-миграцию).

{% alert level="info" %}
Настройки без `mode: Managed` отвергаются, а не игнорируются. Конфигурация, которая записана
и не действует, хуже ошибки: кластер продолжает загружать образы как раньше, и ничто не
объясняет почему.
{% endalert %}

## Два решения, которые вы принимаете

Всё остальное следует из двух независимых ответов.

**Откуда берутся образы.** `primary.upstream` задаёт один авторитетный registry для образов
компонентов Deckhouse. Если его не указать, кластер считается изолированным (air-gap):
единственным источником становится внутрикластерный кэш, который наполняется командой
`d8 mirror push`.

**Идут ли загрузки через внутрикластерный кэш.** `storage.cache` поднимает registry на
master-узлах. Все узлы читают из него, а upstream остаётся резервным путём, пока кэш
наполняется.

Вместе они покрывают все поддерживаемые конфигурации:

| `primary.upstream` | `storage.cache` | Что делает кластер |
|---|---|---|
| задан | `false` | Узлы загружают образы напрямую из upstream'а. На master-узлах ничего не поднимается. |
| задан | `true` | Кэш на проход: наполняется из upstream'а по запросу и заранее. |
| не задан | `true` | Air-gap. Кэш — единственный источник, путь внутрь — `d8 mirror push`. |
| не задан | `false` | Отвергается: узлам было бы неоткуда загружать образы. |

Включение и выключение кэша — безопасная идемпотентная перенастройка, её можно делать в любой
момент. Удаление upstream'а при включённом кэше — единственное изменение с условием: оно
вступает в силу только когда кэш держит весь ожидаемый набор образов, чтобы узлы не остались
без источника. До этого модуль продолжает использовать upstream и сообщает об этом — см.
[`D8RegistryAirGapTransitionHeld`](faq.html#что-означают-алерты-модуля-registry).

Кэш освобождает свой диск сам. Больше ничто и никогда ничего из него не удаляет — каждый релиз
добавляет срез репозитория, — поэтому ночная сборка удаляет срезы релизов, которые кластер
прошёл, сохраняя развёрнутый релиз и предыдущий. На время работы одна реплика уходит в read-only,
поэтому по умолчанию это тихий час; см.
[`storage.garbageCollection`](#parameters-storage-garbagecollection) и
[FAQ](faq.html#кэш-растёт-что-его-чистит).

{% alert level="warning" %}
Используйте отдельные диски для данных кэша (`/opt/deckhouse/registry`) и для данных etcd.
Общий диск приводит к деградации etcd во время наполнения кэша.
{% endalert %}

## Дополнительные registry

`primary.upstream` намеренно единственный registry, который настраивается здесь, и он — для
образов компонентов Deckhouse. Всё остальное — registry вендора, нужный какому-то модулю, или
ваш собственный — объявляется отдельным ресурсом
[RegistryUpstream](cr.html#registryupstream):

```yaml
apiVersion: deckhouse.io/v1alpha1
kind: RegistryUpstream
metadata:
  name: virtualization-images
spec:
  match: images.virtualization.example.com
  upstream:
    host: vendor.example.com
    path: /virtualization
    auth:
      username: robot
      password: <PASSWORD>
```

Именно ресурс, а не ещё одно поле: модуль или пользователь, приносящий свой registry, не
должен для этого править ModuleConfig, которым владеет кто-то другой. Такие registry всегда
транзитные: они маршрутизируются через агент на узле, чтобы учётные данные и удостоверяющие
центры лежали в одном месте, но никогда не кэшируются.

## Загрузка из registry, о котором модуль ничего не знает

Ничего объявлять не нужно. Когда модуль управляет путём загрузки образов, агент на узле —
это то, о чём container runtime спрашивает про любой registry, включая те, о которых модуль
никогда не слышал. Ненастроенный registry проксируется без изменений, вместе с теми учётными
данными, которые уже были в запросе.

Поэтому обычный `imagePullSecret` работает точно так же, как на кластере, где этот модуль
никогда не включался:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  imagePullSecrets:
  - name: my-private-registry
  containers:
  - name: app
    image: private.example.com/team/app:v1
```

Объявлять `RegistryUpstream` стоит только если вы хотите, чтобы учётные данные хранил
кластер, а не каждая нагрузка по отдельности, или если registry требует удостоверяющий центр,
которого на узлах нет.
