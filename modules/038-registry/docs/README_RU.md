## Описание

Этот модуль решает, откуда кластер загружает образы контейнеров и каким путём.

По умолчанию он не решает ничего. Включение модуля само по себе ничего не меняет: при
`mode: Unmanaged` кластер продолжает загружать образы из того registry, с которым был
установлен, и никакие компоненты не создаются. Управление путём загрузки передаётся модулю
осознанно, через `mode: Managed` — см. [настройки](configuration.html).

Когда модуль управляет путём загрузки, всё, что он умеет, описывается двумя независимыми
настройками:

- задаёт ли `primary.upstream` registry, откуда загружать образы, или кластер изолирован;
- поднимает ли `storage.cache` внутрикластерный кэш на master-узлах.

Режимов, между которыми нужно переключаться, и конечного автомата, который нужно держать в
голове, здесь нет. Включение и выключение кэша, смена registry, смена учётных данных — каждое
из этих действий обычная перенастройка, возможная в любой момент и в любом порядке. Условие
привязано ровно к одному изменению: удаление upstream'а для перехода в air-gap ждёт, пока кэш
не будет держать весь ожидаемый набор образов, потому что это единственное изменение, которое
иначе могло бы оставить все узлы без источника образов.

### Агент на узле

На каждом узле работает небольшой агент — статическим подом. Container runtime один раз
направляется на него (`127.0.0.1:5001`, через каталог-фолбэк `_default` в containerd) и дальше
спрашивает у него про любой registry, передавая в запросе исходное имя registry.

На этом одном факте держится всё остальное:

- **Конфигурация узла статична.** Добавление registry, включение кэша, смена учётных данных —
  ничто из этого не переписывает ничего ни на одном узле, потому что runtime и так смотрит
  только в агент. Чтобы изменение вступило в силу, на узле не нужно перенастраивать ничего.
- **Учётные данные registry не попадают в конфигурационные файлы runtime.** Их держит агент и
  подставляет на каждый запрос.
- **Загрузка образов работает, когда API-сервер недоступен.** Агент держит копию своей
  маршрутизации на диске и переходит на неё, потому что среди образов, которые он отдаёт, есть
  и те, что нужны для восстановления сломанного control plane. Узел, который никогда не
  дозвонился до API, использует маршрутизацию, с которой был установлен.

Ненастроенный registry проксируется без изменений, вместе с теми учётными данными, которые уже
были в запросе, — поэтому обычный `imagePullSecret` для какого-нибудь сторонного registry
продолжает работать, и объявлять для этого ничего не нужно.

### Внутрикластерный кэш

При включённом `storage.cache` на каждом master-узле работает registry, который держит блобы
на хосте в `/opt/deckhouse/registry`. Одна реплика держит lease и наполняется из upstream'а,
остальные реплицируют из неё заранее — чтобы потеря лидера не означала наполнение с нуля.

Это не обычные выборы lease. За него борется только реплика, которая держит весь ожидаемый
набор образов, а реплика, которая его держит, уступает, когда набор появляется у другой: роль
лидера здесь несимметрична — именно из него реплицируют остальные, и именно его полнота
открывает переход в air-gap. Без этого условия изолированный кластер мог бы застрять:
`d8 mirror push` попадает на ту реплику, которую выбрал ingress, а пустому лидеру не из чего
наливаться.

Агенты обращаются к реплике по адресу узла, а не по имени сервиса.
`registry.d8-system.svc:5001` — это то, из чего строится каждая ссылка на образ в кластере, и
то, с чем сопоставляется запрос, но никто по этому имени не дозванивается: агент работает в
сетевом пространстве хоста, где имя cluster DNS не разрешается.

{% alert level="warning" %}
Используйте отдельные диски для данных кэша (`/opt/deckhouse/registry`) и для данных etcd.
Общий диск приводит к деградации etcd во время наполнения кэша.
{% endalert %}

### Изолированные кластеры

Если upstream не задан, кэш — единственный источник образов, а
[`d8 mirror push`](/products/kubernetes-platform/documentation/v1/cli/d8/) — единственный путь
внутрь. Он приходит через endpoint публикации, который помимо учётных данных требует
клиентский сертификат от ingress: это единственный путь, по которому образ можно заменить, и
утёкшего пароля не должно быть достаточно, чтобы им воспользоваться.

Этот endpoint существует только в такой конфигурации. Кластер, который просто кэширует, не
получает доступной извне точки записи, о которой не просил.

## Требования

- На узлах используется containerd или containerd v2. См.
  [`ClusterConfiguration`](/products/kubernetes-platform/documentation/v1/reference/api/cr.html#clusterconfiguration-defaultcri).
- Кластер полностью управляется DKP. В Managed Kubernetes модуль не работает.
- Внутрикластерный кэш использует диски master-узлов и поддерживается на статических кластерах.

## Предыдущая реализация

Всё, что ниже, описывает реализацию, от которой модуль уходит. Она сохранена, потому что на
ней всё ещё работают кластеры и потому что уход с неё — осознанный шаг, а не то, что
обновление делает молча.

Она настраивается через [ModuleConfig `deckhouse`](/modules/deckhouse/configuration.html#parameters-registry),
а не через настройки самого модуля, и работает как конечный автомат с четырьмя режимами:

- `Direct` — прямой доступ к внешнему registry по фиксированному адресу
  `registry.d8-system.svc:5001/system/deckhouse`. Фиксированный адрес — это то, что позволяет
  избежать повторного скачивания образов Deckhouse и перезапуска компонентов при смене
  параметров registry.
- `Proxy` — внутренний кеширующий прокси-registry на master-узлах, доступный по тому же
  фиксированному адресу; сокращает количество запросов к внешнему registry.
- `Local` — полная локальная копия registry внутри кластера, для изолированных окружений.
- `Unmanaged` — без внутреннего registry; кластер обращается к внешнему напрямую. Существует в
  настраиваемой форме, управляемой через ModuleConfig `deckhouse`, и в устаревшей
  ненастраиваемой, задаваемой при
  [установке](/products/kubernetes-platform/documentation/v1/reference/api/cr.html#initconfiguration-deckhouse-imagesrepo).

Кластер, работающий в любом из них, продолжает работать так до перевода в `Unmanaged`, после
чего передача текущей реализации происходит сама — см.
[как завершить миграцию](faq.html#как-завершить-миграцию). Обе реализации никогда не управляют
кластером одновременно: то, какая из них активна, определяет, что вообще создаётся, поэтому
состояния, в котором обе настраивают один узел, не существует.

### Ограничения переключения режимов

- Смена параметров registry и переключение режимов доступны только после полного завершения
  bootstrap-фазы.
- Для первого переключения нужно выполнить миграцию пользовательских конфигураций registry.
  См. [FAQ](faq.html).
- Переключение в ненастраиваемый режим `Unmanaged` доступно только из `Unmanaged`.
- Переключение между `Local` и `Proxy` возможно только через промежуточный `Direct` или
  `Unmanaged`. Например: `Local` → `Direct` → `Proxy`.
- Bootstrap в режимах `Local` и `Proxy` поддерживается только на статических кластерах.

### Архитектура режима Direct

В режиме `Direct` запросы к registry обрабатываются без промежуточного кеширования. Запросы
CRI перенаправляются на основании конфигурации containerd. Компоненты, обращающиеся к registry
напрямую — `operator-trivy`, `image-availability-exporter`, `deckhouse-controller` и другие, —
идут через внутрикластерный прокси на master-узлах.

### Архитектура режима Proxy

{% alert level="warning" %}
Рекомендуется использовать отдельные диски для хранения данных registry
(`/opt/deckhouse/registry`) и данных etcd. Использование одного диска может привести к
деградации производительности etcd во время работы registry.
{% endalert %}

Кеширующий прокси-registry запускается статическими подами на master-узлах и хранит кешируемые
данные в `/opt/deckhouse/registry`. Перед ним на каждом узле стоит балансировщик, и
конфигурация containerd указывает на этот балансировщик. Компоненты, обращающиеся к registry
напрямую, идут через кеширующий прокси-registry.

### Архитектура режима Local

{% alert level="warning" %}
Рекомендуется использовать отдельные диски для хранения данных registry
(`/opt/deckhouse/registry`) и данных etcd. Использование одного диска может привести к
деградации производительности etcd во время работы registry.
{% endalert %}

Режим `Local` держит полную копию registry внутри кластера, синхронизированную между репликами
на master-узлах и наполняемую утилитой
[`d8`](/products/kubernetes-platform/documentation/v1/cli/d8/) командами
`d8 mirror push`/`d8 mirror pull`. В остальном работает так же, как кеширующий прокси.
